# Notch — 3 つ目のサーフェス

> Status: Draft (要件・設計。実装は P4 以降)
> Related: [`launcher-requirements.md`](./launcher-requirements.md) / [`launcher.md`](./launcher.md) /
> [`explorer-essentials.md`](./explorer-essentials.md) / [`os-integration.md`](./os-integration.md) / [`migration.md`](./migration.md)

本書は MacBook の **notch (カメラハウジング周辺)** を nohrs の 3 つ目のサーフェスとして扱うための要件と設計を定めます。
explorer window / launcher window に続く常駐サーフェスで、**「今なにが起きているか」と「一時的に物を置く場所」**を担当します。

---

## 1. なぜ notch を第一級にするのか

notch アプリ (NotchNook / Boring Notch / Alcove など) は現在、**ランチャーとは別プロセスの 4 つ目の常駐アプリ**として
存在しています。nohrs は既に

- 常駐してファイルインデックスを持ち ([`search.md`](./search.md))、
- ファイル操作を実行し ([`explorer-essentials.md`](./explorer-essentials.md))、
- ドラッグ & ドロップの送り手と受け手の両方であり、
- notch の前フェーズ (P3.5) でクリップボード履歴を持つ ([`launcher-requirements.md`](./launcher-requirements.md) §5.4)

ため、notch v1 に着手する時点で、**notch に出したいものをすでに全部持っている**ことになります。
別プロセスを増やさずに出せるのは構造的な優位です。

逆に言えば、nohrs の notch は「メディアコントロールの置き場所」ではなく、
**Explorer × Launcher の常駐面**として設計します。他社の notch アプリが持てないのは次の 3 つです。

1. **シェルフと explorer が同じファイル操作基盤を共有する** (シェルフから explorer へ、explorer からシェルフへ)。
2. **長時間のファイル操作 / インデックス作成の進捗が出る** (コピー・移動・ゴミ箱・プラグイン導入)。
3. **さっきコピーしたものとシェルフが地続き** (Supaste の "notch shelf" が単体で売れている領域)。

## 2. サーフェスモデル

notch は 4 つの状態を持ちます。**ポインタとドラッグだけで全部の状態に行ける**ことを要件にします
 (キーボードに触らずに完結する)。そのうえでキーボードからも同じ操作ができ、ホットキーで開き、
`Esc` で閉じ、`1`-`9` でシェルフの n 番目を開けます ([§4](#4-ジェスチャとキー))。
「ポインタだけでも足りる」であって「ポインタでなければ駄目」ではありません。

| 状態 | 見え方 | 入り方 | 出方 |
|------|--------|--------|------|
| **Hidden** | 何も描かない (物理 notch のまま) | 既定 / 設定で無効化時 | — |
| **Idle (pill)** | notch の左右にごく小さいインジケータ。**出すのは「存在」だけで「中身」ではない** ([§3.8](#38-プライバシー)) | 進行中・要確認のことがあるとき、またはシェルフが空でないとき | アクティビティが片付いたら Hidden。シェルフが空でない間は残る |
| **Tray** | notch が下に広がり、**そのまま使えるトレイ**が出る。シェルフの中身・ドロップ先・進行中の帯 | ホバー ([§2.1](#21-ホバーの誤爆を防ぐ) の条件を満たしたとき) / クリック / ドラッグ / ホットキー | **ホバーで開いたときだけ**、**notch 帯とトレイを合わせた領域**からポインタが出ると閉じる (トレイの中へ下りるのは「離れる」ではない。ドラッグ中を除く)。クリック・ホットキー・キーで開いたときはポインタ位置に関係なく開いたまま / `Esc` / 外側クリック / ドロップ完了 |
| **Expanded** | トレイが縦に伸びる。**入り切らないときだけ** | トレイのスクロール、または `↓` | 上スワイプ / `Esc` / 外側クリック |

**Tray が本体です。** ホバーで「要約 1 行」を見せて、クリックで初めて使える、という二段構えにはしません。
上端まで往復した時点でコストは払い終わっているので、着いた先はすぐ落とせて、すぐ掴めるべきです。
`Expanded` は**件数が入り切らないときの延長**でしかなく、別の画面ではありません。

**Tray には 2 つの開き方があります。**

| | 大きさ | タブ | フォーカス |
|---|---|---|---|
| **ホバー / ドラッグで開く** (シェルフ) | 中身の件数で伸びる。入り切らなければ `Expanded` | 出さない | **奪わない** |
| **キーで開く** (クリップ履歴・スニペット・絵文字) | **760 × 440 固定** ([§3.6](#36-クリップ履歴パネル-p4))。伸びず、一覧が送られる | 出す | **奪い、閉じたら返す** ([§5.1](#51-ウィンドウ)) |

掴んでいる最中はタブを踏めないので、タブはキーで開いたときだけ出します。
検索バーはキー入力を受けるので、そこだけフォーカスを取ります — notch が**常に**フォーカスを奪わない、
という前提はここで終わります。§5.1 に書き直してあります。

**ドラッグ中の特別扱い**: ファイルをドラッグしたまま画面上端に入ると、トレイが
**複数のドロップ先に展開**します ([§3.3](#33-ドラッグ時のドロップ先ファンアウト-p4))。的に合わせずに離せばシェルフ行きです。
これが notch の最頻ユースケースなので、他のどの遷移よりも速くする。上端に**近づいた**段階で先に
開き始められるかはプラットフォーム次第で、そこは §3.3 で分けています。

**notch が自分からトレイを開くのは、このドラッグのときだけ**です ([§3.7](#37-同時に起きたときの捌き方))。
進捗も新着も Idle (pill) 止まりで、開くかどうかはユーザーが決めます。**何も無かったところから**パネルが降りてきて
メニューバーとウィンドウの上端を覆うので、自発的に開くものは「作業を止めるもの」になります。

### 2.1 ホバーの誤爆を防ぐ

**ここを決めずに「ホバーで開く」と実装すると、必ず失敗します。** メニューバーの左右を行き来すると、
ポインタは notch 帯を横切ります。素直に反応させると、**メニューを開こうとしただけでトレイが降ってくる**。
この種のアプリが嫌われる筆頭がこれで、しかも「たまに出る」ので設定で切るまで直りません。

3 つ重ねて塞ぎます。

| 規則 | 内容 |
|------|------|
| **武装していなければ反応しない** | ホバーが効くのは、① ドラッグ中 ② シェルフが空でない ③ 要確認のアクティビティがある、のいずれか。**何も無いときの notch は不活性**で、その場合はホットキーかクリックで開く |
| **滞留を要求する** | 武装していても、notch 帯に**250ms 留まる**まで開かない。横断は通過であって滞在ではない |
| **下から入ったときだけ** | メニューバーに沿った水平移動では開かない。画面内側から上端に向かう動きだけを入り口とする |

ドラッグ中はこの 3 つとも緩めます (滞留 80ms、方向を問わない)。手に荷物がある時点で意図は明確だからです。

**受け入れ基準**: メニューバーの左右を 20 往復して、トレイが **0 回**開く。
シェルフに 1 件入れた状態で同じことをしても **0 回**。

### 2.2 非 notch マシン / Linux でのフォールバック

notch が無い Mac (Air 2020, 外部ディスプレイ, Mac mini) と Linux でも**同じ機能が使える**必要があります。
無いものを理由に機能ごと落とすと、クロスプラットフォーム原則 (原則 5) が崩れます。

| 環境 | 形態 |
|------|------|
| notch あり (内蔵ディスプレイ) | 物理 notch に重ねる |
| notch なし / 外部ディスプレイ | 画面上端中央に**同じ形の浮遊バー**を出す (Idle 時は数 px の細い帯) |
| Linux (X11) | 同上。`_NET_WM_WINDOW_TYPE_DOCK` + `_NET_WM_STATE_ABOVE` |
| Linux (Wayland) | `wlr-layer-shell` が使えるコンポジタでのみ同等。使えなければ **notch サーフェスを提供しない**と明示し、シェルフは launcher と explorer から使えるようにする |

**設計上の帰結**: シェルフとアクティビティの**中身のビューは notch 専用にしない**。
launcher からも、explorer のサイドバーパネルとしても同じビューを出せるようにする
(= `nohrs-ui` のコンポーネントとして作り、`nohrs-notch` はそれを載せる器に徹する)。
notch が使えない環境で機能ごと消えないのは、この分離があるからです。

## 3. 何を載せるか

### 3.0 判断基準

notch は「小さい画面」ではありません。**普段は何も出ていない**場所です。物理的な notch は常にそこにありますが、
nohrs が描くものは、ポインタを置いて初めて出てきます (§2 の Hidden → Idle → Tray)。
この**出方**が、何を載せてよいかをほぼ決めます。

- **一瞥で読めることに価値がある機能は、この出方だと価値が消える。** 時計・天気・バッテリー・システム統計は
  「視界の端に勝手に映っているから意味がある」ものです。ホバーして初めて読める時計は、メニューバーの時計に
  **劣ります**。席が狭いから外すのではなく、**この surface では成立しないから**外す。
- **狙うのに 1 往復かかる。** ポインタを画面上端まで運ぶコストが先払いなので、着いた先が「見るだけ」で
  終わるものは往復に見合いません。だから「そこで何かできる」ことが要る。
- **出てくる瞬間が作業を遮る。** 何も無いところからパネルが降りてきて、メニューバーとウィンドウの上端を覆います。
  z-order 上はどのアプリよりも手前なので、出す判断は保守的にします ([§3.7](#37-同時に起きたときの捌き方))。

他社の notch アプリがウィジェットホスト (天気・時計・統計・ミラー) に寄っていくのは、この席を**表示**に
使っているからです。nohrs は**操作**に使います。

launcher と notch の役割はこう分かれます。

| | launcher | notch |
|---|---|---|
| 起点 | **引く** (pull) — 自分が呼ぶ。何が欲しいか分かっている | **押される / 抱える** (push / carry) — 向こうで何かが起きる。または手に持っている最中 |
| 寿命 | 呼んだ数秒 | 作業の裏でずっと |
| 失敗の形 | 出てこない・遅い | **邪魔** |

そのうえで、notch に載せてよいものは**次の 4 つを全部満たすもの**だけとします。

| # | テスト | 落ちる例 |
|---|--------|---------|
| **T1** | **自分が見に行かなくても起きる** (push)。見に行くものは launcher に置く | 天気・時計・システム統計 — 見たいときに見るもの = pull |
| **T2** | **見て終わりではなく、その場で次の操作がある** (ドラッグ・取り消し・開く・止める) | CPU 使用率グラフ — 上端まで往復した先が「見るだけ」では割に合わない |
| **T3** | **一過性か、携行中か**。常設の表示にならない | カレンダーの今日の予定 — 常設のものは「常に見えている」ことが価値で、ホバーで初めて出る場所とは噛み合わない |
| **T4** | **nohrs しか知らない**、または nohrs が既に持っている情報である | Now Playing・音量・バッテリー — Control Center が 20px 隣で出しており、**しかもあちらは一瞥で読める**。重複な上に劣る |

T4 が効く場面は多く、結果として**メディア・HUD・バッテリー・カレンダー・統計はコアから落ちます**
([§3.10](#310-コアに載せないもの))。これらを欲しい人が居ることは否定しません。置き場所を
plugin にする、というのが答えです ([§3.9](#39-プラグインが載せるもの))。

### 3.2 ファイルシェルフ (P4, 最優先)

**要件**

- 任意のアプリからドラッグしたファイル / テキスト / 画像を**一時的に保持**する。実体は移動せず、パス参照
  (アプリ外から来た生データのみ `$XDG_DATA_HOME/nohrs/shelf/` に退避)。
- **その退避先は所有者のみです。** 中身はユーザーがコピーした本文そのもの (選択したテキスト、貼った画像)
  なので、ログと同じ扱いにします ([`logging.md`](./logging.md)): ディレクトリは `0700`、blob は `0600`。
  起動時に既存のパーミッションを見て、緩ければ**締め直してから使い**、締め直せなければ**使いません**
  (シェルフを無効にして理由を出す)。Windows は mode が無いので、ユーザープロファイル配下の ACL を
  継ぐ場所に置きます。
- macOS の promise ドラッグ (メールの添付や写真アプリから出てくるもの) は、ドロップした時点ではまだ
  実体がありません。**実体化中の項目**として進捗付きで並べ、済むまではドラッグアウト・AirDrop・zip の
  対象にしません。失敗したらエラーの項目として残し ([§3.4](#34-ライブアクティビティ-p4))、黙って消しません。
- シェルフからのドラッグアウトは、**受け手が期待する形**で出す。中身の種別で変わります。

  | シェルフの中身 | macOS | Linux |
  |---------------|-------|-------|
  | ファイル / フォルダ | `NSFilenamesPboardType` (`public.file-url`) | `text/uri-list` |
  | テキスト | `public.utf8-plain-text` | `text/plain;charset=utf-8` |
  | 画像 | `public.png` / `public.tiff` | `image/png` |

  受け手がどれも受け取らない場合は、**一時ファイルに書き出してファイルとして渡す**のを最後の手段にします
  (テキストエディタしか受け付けない相手にも、少なくともファイルは落とせる)。これは中身の**二つ目の複製**を
  ディスクに作る操作なので、作りっぱなしにしません: 専用ディレクトリ (`0700`) に `0600` で作り、
  ドラッグが完了・キャンセル・失敗のいずれで終わっても消します。
  ただし**ドラッグが終わった時点では消せません**。受け手は非同期に読むことがあり、
  `draggingSession(_:endedAt:operation:)` が返った後に読みに来ます。そこで消すと、
  **相手が読んでいる最中にファイルを抜く**ことになります。

  **そして「受け手が読み終えた」を知る手段はありません。** 普通のファイル URL のドラッグに、
  受け手から送り手への読了通知はありません (`NSFilePromiseReceiver` の `reader` は
  *受け手側*が読むためのもので、こちらには届きません)。なので**受け手の合図を前提にした設計は書けません**。
  出し方を 2 つに分け、それぞれ別の畳み方にします。

  **相手が何を受け取れるかは、こちらからは分かりません。** ドラッグ元に「この受け手は promise を
  受け付けない」を知らせる仕組みはないので、「駄目だったら一時ファイルに切り替える」は書けません。
  代わりに**両方を最初から出します**。

  | 出す表現 | 実体を作る時点 | 消す時点 |
  |---------|--------------|---------|
  | **`NSFilePromiseProvider`** | 受け手が promise を選び、こちらの `writePromiseTo:completionHandler:` が呼ばれたとき | 書いた先は受け手の管理下なので**こちらは消しません** |
  | **`public.file-url`** | 受け手が**この型を要求したとき**。`pasteboardPropertyList(forType:)` が呼ばれた時点で一時ファイルを書き、その URL を返す | **ドラッグが終わってから 10 分** |

  どちらを使うかは**受け手が選びます**。こちらは判定しません。

  **「promise を選んだ相手には一時ファイルを作らない」とは言えません。** 受け手がどの順で型を要求するかは
  こちら側で決められず、`public.file-url` を先に引いてから promise を使うことがあり得ます。言えるのは
  **要求されるまで作らない**ことと、**1 つのドラッグ項目につき高々 1 回しか作らない**こと (生成した URL は
  項目ごとにキャッシュし、同じ型を再度引かれても作り直さない) です。
  結果として、**要求されなかった項目には作られず、要求された項目にも 1 つしか作られません**。
  作られた分は下の期限と上限の対象になります。

  - **10 分の期限はドラッグが終わってから**数えます (`draggingSession(_:endedAt:operation:)` が返った時点が起点)。
    ドラッグ中の項目は、何分掴んでいても消えません。1 時間掴み続けたら消えていた、を作らないためです。
  - **一時ファイル置き場にも上限を置きます。** ここはシェルフの blob とは別の場所なので、
    1 アイテム 50MB / 総量 500MB の外側です。上限なしだと、大きいファイルを繰り返しドラッグしただけで
    掃除が回る前にディスクを使い切ります。**総量 1GB / 200 ファイル**を上限にし、
    **書き始める前に**新しいファイルの分を足して超えるかを見ます。超えるなら
    `public.file-url` の提供を断ります (promise 側は影響を受けません)。
  - **この上限が縛るのは「いま名前があるファイル」だけです。** 期限切れで消す操作はパス名を外すだけで、
    受け手がその一時ファイルを**開いたまま**なら中身はディスクに残ります
    (Unix では最後の記述子が閉じるまで実体が解放されません)。受け手が記述子を持っているかどうかを
    こちらから知る方法は無いので、**「この置き場が 1GB を超えることはない」とは言えません**。
  - **会計と掃除については、満たすべき性質だけを決めます。** どう満たすかは実装が決めます ([§9](#9-未解決--要調査) の R25)。
    持ち主の識別子の取り方や失敗時の後始末まで**実機で確かめずにここで決め切ると、動かない機構が仕様として固まります**。
    - **A** 名前のあるファイルの合計は **1GB / 200 ファイル**を超えない。上限の検査と作成は**不可分**に行う。
    - **B** 名前を外した後に受け手が抱えている分は**約束しない**。受け手の寿命が決めるもので、こちらに手は無い。
    - **C** ドラッグの途中のファイルは、何分掴んでいても**消えない**。
    - **D** ドラッグが終わった後、受け手が読むための時間 (**10 分**) を置く。こちらが落ちてもこの時間は**縮めない**。
    - **E** どんな落ち方をしても、**掃除が到達できないファイルを残さない**。必ず有限時間で消える。
    - **F** A〜E の判断に、**壁時計**と**落ちたプロセスの中にしか無い値**を使わない。
    - **G** 書き込みが失敗したら、**理由を問わず**書きかけと予約を残さず、その型の提供を失敗として返す。
      切り詰められたファイルを受け手に渡さない (promise 側は影響を受けません)。
  - **設計中に踏んだ罠**を、実装が同じ穴に落ちないように残します。どれも一見動いて、ある状況で上を破ります。
    - 期限をドラッグ終了から数えると、**終わらずに落ちた分に期限が来ません** (E)。
    - 持ち主を pid だけで識別すると使い回されます。pid と開始時刻でも、Linux の開始時刻は
      boot からの相対値なので**再起動を跨いで一致し得ます** (E)。
    - その識別子が取れない環境で「判断できないから消さない」とだけ決めると、**永久に残ります** (E)。
    - 期限を壁時計で持つと、NTP が前に飛ばせば**読んでいる最中に消え**、後ろに戻せば**期限が来ません** (D, F)。
    - 「外した分もあと N 分は数える」という猶予は、N を過ぎて掴まれていると**会計が実際より少なくなります** (A)。
    - `pasteboardPropertyList(forType:)` は項目ごとに、しかも同時に呼ばれ得ます。検査と作成を分けると、
      **まだ 1 バイトも現れていない書き込みどうしが互いに見えず**、全部が検査を通ります (A)。
    - 後始末を `ENOSPC` だけに書くと、他の理由 (権限・I/O・クォータ・元のファイルが消えた) で落ちたときに
      **予約が残り、後から来た正当な要求が上限超過で断られます** (G)。
    - 本体の名前を付け替えて状態を記録すると、**パスを控えている受け手が開けなくなります**。
  - **補助の歯止め — 上限ではありません**: 書き始める前に対象ボリュームの空きを見て、
    **2GB を切っていたら `public.file-url` を断ります**。見た後に他のプロセスが空きを食えば書き込みは
    `ENOSPC` で落ちるので、これは事前の一瞥です。掃除が回るのは**起動時と 1 時間ごと**。
- アクション: explorer で開く / Reveal / まとめてコピー・移動 (explorer のファイル操作基盤を呼ぶ) / AirDrop 送信 (macOS) /
  クリップボードにパスをコピー / 削除 (シェルフからだけ外す) / まとめて zip。
- **explorer 側との往復**: explorer の選択を `Cmd+Shift+S` 等でシェルフに送れる。シェルフから explorer の
  現在ディレクトリにドロップできる。
- シェルフの内容は再起動を跨いで復元する (redb `shelf.items`)。ただし存在しなくなったパスは復元時に落とす。
- **シェルフが持つ実体には上限を置きます。** `max_items` は件数しか縛らないので、それだけでは
  `$XDG_DATA_HOME/nohrs/shelf/` が無制限に育ちます。1 アイテム **50MB** / 総量 **500MB**、超えるものは
  **受け取らずに理由を出す** (黙って切り詰めない)。パス参照しか持たないアイテムはこの計算に入りません。
- **実体の後片付けを定義します。** シェルフから外したとき、復元時に存在しないパスとして落としたとき、
  `noh shelf clear` のとき — いずれも対応する blob を削除します。参照だけのアイテムは**元ファイルに触りません**
  (シェルフから外すことは、ファイルを消すことではない)。
- **複数の出どころから溜められる**こと。ブラウザから 1 つ、Slack から 1 つ、explorer から 3 つ、と別々に放り込んで
  最後に 1 回で落とす、が主用途です。1 回のドラッグを中継するだけなら、シェルフは要りません。
- **CLI から入れられる**: `noh shelf add <path>...` / `noh shelf list` / `noh shelf clear`。ターミナルで見つけた
  ファイルを GUI のアプリに渡す導線がここで繋がります ([`cli.md`](./cli.md) に追加)。
- **シェルフが空でないことだけは、Idle でも出す**。これは「普段は何も出ていない」([§3.0](#30-判断基準)) の
  **唯一の例外**です。ホバーするまで見えないと、携行していること自体を忘れます — そして忘れたシェルフは
  事故になります (古いファイルを掴んだまま次の作業に入り、意図しないものを渡す)。「そこに何かある」ことは
  ホバー前に分かる必要があり、「それが何か」はホバーしてからで十分です。出すのは**件数だけで、
  中身は出しません** ([§3.8](#38-プライバシー))。設定で消せます。

**受け入れ基準**

- ドラッグ開始から notch が Tray になるまで **< 150ms** (事前武装できない環境の扱いは
  [§3.3](#33-ドラッグ時のドロップ先ファンアウト-p4))。
- 100 件のファイルをシェルフに入れても一覧のスクロールが 60fps を維持する。
- シェルフ経由の移動 / コピーは explorer と**同一の** conflict 解決 UI (Rename/Overwrite/Skip + Apply to all) を使う。
- シェルフが空のとき、Idle の描画は**完全に消える** (件数バッジも出ない)。

### 3.3 ドラッグ時のドロップ先ファンアウト (P4)

シェルフ 1 つだけを的にすると、「シェルフに入れてから、改めて行き先を選ぶ」の 2 手になります。
ドラッグしたまま上端に入った時点で、notch を**複数のドロップ先に展開**します。

| ドロップ先 | 内容 |
|-----------|------|
| **シェルフ** | 既定。どの的にも合わせずに離したらここ。notch 帯そのものが常にこの的 |
| **いま開いている explorer のディレクトリ** | explorer が開いていて、そのディレクトリが書き込み可能なときだけ |
| **最近使ったフォルダ** | launcher と同じ履歴 ([`launcher-requirements.md`](./launcher-requirements.md) §7.5 の `history` テーブル、`kind="open"`) を使う。**残り枠を埋める分だけ** |
| **AirDrop** | macOS のみ。ファイル / フォルダをドラッグしているときだけ |
| **新規ファイルとして保存** | テキスト / 画像など、ファイルでないものをドラッグしているとき |

- 的は**最大 5 つ**。増やすと狙えなくなります。候補が上回るので、**優先順位で埋めます**:
  ① シェルフ (常に出す) → ② いま開いている explorer のディレクトリ → ③ AirDrop または「新規ファイルとして保存」
  (ドラッグしているものの種別で排他) → ④ 残り枠を最近使ったフォルダで埋める (最大 2)。
  ②③ が条件を満たさないときは、その枠も最近使ったフォルダに回ります。
- 各的は「落とすと何が起きるか」を書く (`移動` / `コピー` — 修飾キーで変わるので、キーを押し替えたら表示も変わる)。
  ただし**ソースが許していない動作は書きません**。移動を許さないドラッグ元に「移動」と出すと、
  落とした先で黙ってコピーになります (macOS の `NSDragOperation`、XDND の `XdndActionMove`、
  Wayland の `wl_data_offer.source_actions` で、いずれもドロップ前に分かります)。
- 的の上でホバーしている間は、その的だけを強調して他を沈める。
- **どの的に落としても、その的の処理が失敗したらペイロードはシェルフに残ります。**
  ファンアウトに落としたのに手元に何も残らない、という結果は作りません
  ([§3.4](#34-ライブアクティビティ-p4) の「失敗した操作の回収」に載ります)。
  受け取り方は [§3.2](#32-ファイルシェルフ-p4-最優先) のとおりで、ペイロードの持ち方によって 4 つに分かれます。
  1. **安定したパス参照として渡されたもの** (ファイル / フォルダのドラッグ) → 参照のままシェルフへ。
     実体を抱えないので **1 アイテム 50MB / 総量 500MB の対象外**です。ただし `max_items` (既定 100) は
     効くので、満杯なら 4 に回ります。
  2. **promise ドラッグ** → ドロップの時点ではパスがありません。§3.2 のとおり実体化を待ち、
     落ちた先への**参照**にします。実体化に失敗したら 4 に回ります。
  3. **生データ** (ブラウザで選択したテキスト、Slack から落とした画像など) → §3.2 のとおり
     `$XDG_DATA_HOME/nohrs/shelf/` に blob として保存します。**ここが容量上限の対象**です。
  4. **上限に当たったもの** (1 件が 50MB 超 / 総量 500MB を空けられない / `max_items` 満杯 /
     実体化に失敗) → これだけがシェルフに残せません。§3.4 に「受け取れませんでした」と出し、
     **当たった上限はどれか**と、**元のアプリにまだあること**を書きます。
     入っていない物が入っているかのような行を作らない、というのがこの分岐の要点です。

#### 種別はドロップ前にどこまで分かるか

|  | ドラッグ開始を、ポインタが来る前に知れるか | ペイロードの**種別** | ペイロードの**中身** |
|---|---|---|---|
| **macOS** | 公開 API は無い。ドラッグ用ペーストボードの `changeCount` とポインタ位置から**推定する**のが通例 | 知れる (`NSDraggingInfo.draggingPasteboard` の型、`canReadObject(forClasses:)`) | 読まない (下記) |
| **X11** | 知れる。XFixes の `SetSelectionOwnerNotify` を `XdndSelection` に張ると、ドラッグ元が選択を取った瞬間に届く | 知れる。`XdndEnter` に 3 つまで載り、超える分はソースウィンドウの `XdndTypeList` プロパティ | 規約上ドロップ後 (`XdndDrop` → `XConvertSelection`) |
| **Wayland** | **知れない**。他クライアントの上を通っているドラッグはプロトコルに出てきません | 知れる。ただし**自分のサーフェスにポインタが入ってから** (`wl_data_device.enter` の直前に `wl_data_offer.offer` が MIME 型を並べる)。**その enter が layer surface に配送されるかは未確認** (R19) | `wl_data_offer.receive` はドロップ前でも呼べるが、使いません |

**オファーさえ届けば、種別は 3 つとも「ドロップ前に分かる」**というのが答えです。違うのは分かる**時刻**で、
中身はどこでも読めません。Wayland だけは「届くか」自体が未確認で (R19)、届かなければ種別の可否以前に
ファンアウトが成立しません。ここから 3 つ決まります。

- **中身は読みません。** macOS をサンドボックス化する場合、`draggingEntered:` の時点でファイル URL を
  読むと、ドロップしたときにそのファイルへのアクセスが張られなくなります (型の照会だけなら安全)。
  未公開の読み取りオプションで避ける手はありますが、**型しか見ない**方に倒します。
- したがって**的のラベルに件数を出しません。** macOS は `numberOfValidItemsForDrop` で件数が取れますが
  X11 / Wayland には無く、プラットフォームで表示が変わってしまいます。
- macOS の promise ドラッグ (メールの添付や写真アプリから出てくるもの) は、「ファイルであること」と UTI
  だけが分かり、実体はドロップ後に受け取ります。的としては AirDrop を出してよい。ただし実体化は
  非同期で失敗しうるので、シェルフは実体化が済むまで**進捗付きの項目**として置き、失敗したら §3.4 に載せます。
  AirDrop も実体のファイル URL を要求するので、同じく実体化を待ってから送ります。

#### 開くタイミングと、幾何を固定する理由

事前武装 (ポインタが上端に来る前に的を描き始めること) ができるのは **macOS と X11 だけ**です。
Wayland は notch 帯に入ってからしか開けません。そこで**どちらでも幾何を同じにします**。

- ファンアウトは notch 帯より**下にだけ**伸び、ポインタが載っている notch 帯そのものは常にシェルフです。
  的が「ポインタの真下に生える」ことが構造的に起きないので、開くのが遅れても誤爆になりません。
  事前武装は**早く見えるだけ**で、当て方は変わりません。
- 描き始めたら、**そのドラッグが終わるまで的の位置と数は変わりません**。変わってよいのはラベルだけです。
- ラベルの差し替えは、**ポインタがその枠の外にいる間だけ**行います。狙った的が、落とす瞬間に別物に
  変わることはありません。例外は修飾キーによる `移動` / `コピー` の切り替えで、あれはユーザー自身が
  今その場でやっている操作なので、載っている枠でも即座に反映します。
- 種別に依存する枠 (③) は、種別が決まるまで「最近使ったフォルダ」で埋めておき、上のルールに従って
  差し替えます。notch に着くまでに決まらなければ、そのまま最近使ったフォルダで確定します。

macOS の推定は、**左ボタンが押されている間だけ** 30Hz で回します (`NSEvent.pressedMouseButtons` /
`NSEvent.mouseLocation` / ドラッグ用ペーストボードの `changeCount`)。描き始めるのは `changeCount` が
動いてからで、マウスダウンから 300ms 動かなければドラッグではないと見なして止めます。ボタンが離れても
止めます。**アイドル時のポーリングは 0 です** (原則 6)。マウスイベントのグローバル監視に
アクセシビリティ権限は要りません (要るのはキー入力の監視で、そちらは使いません)。

**受け入れ基準**

- 事前武装できる環境: ドラッグ開始から的の枠が描かれるまで **< 150ms**。
- できない環境 (Wayland): ポインタが notch 帯に入ってから **< 80ms** (`notch.hover.drag_dwell_ms` と同じ)。
- 的の当たり判定は最小 44×44pt。
- 的が描かれてからドロップまで、的の**位置と数が変わらない**こと。ポインタが載っている枠のラベルが
  差し替わらないこと。
- ドラッグせずにマウスを押して動かしただけでは、ファンアウトが **0 回**開くこと。
- 的の処理が失敗した 100 回のドロップすべてで、ペイロードがシェルフに残っていること。

### 3.4 ライブアクティビティ (P4)

nohrs 自身が抱えている処理を出します。**他アプリの監視はしません** (原則 1: 常駐は軽く)。

| 種類 | 出すもの |
|------|---------|
| ファイル操作 | コピー / 移動 / ゴミ箱 / 復元 の進捗、対象数、残り時間、**キャンセル** |
| **破壊的操作の取り消し猶予** | ゴミ箱 / 上書き / 移動の直後、**既定 10 秒**だけ `取り消す` を出す (下記) |
| **失敗した操作の回収** | 失敗・部分完了の通知と、再試行 / 詳細 / 残骸の場所 (下記) |
| インデックス | 初回スキャン / 再インデックスの進捗、一時停止 |
| 検索 | 長い全文検索の実行中表示 (中断可能) |
| プラグイン | インストール / 更新の進捗 (ホスト側が出すもの)。**plugin 自身が投げるアクティビティは P5** — WIT の `notch` interface がまだ無いため ([§3.9](#39-プラグインが載せるもの)) |

#### 取り消し猶予がここにある理由

explorer の undo は**ウィンドウ単位のスタック**です ([`explorer-essentials.md`](./explorer-essentials.md) §1)。
つまり、ファイルを捨てて別のアプリに移った瞬間、取り消す手段が画面から消えます。**間違いに気づくのは
たいていその後**です。notch はウィンドウより長生きするので、ここが唯一の置き場所になります。

- 対象は破壊的操作 (ゴミ箱 / 上書き / 移動) のみ。コピーや新規作成には出しません。
- 猶予中に explorer ウィンドウを閉じても、タブを閉じても、**猶予は消えません**。
- 猶予が切れたら黙って消えます (「取り消せなくなりました」とは言わない — それは通知の無駄遣い)。

#### 失敗の回収がここにある理由

同じ理由です。`explorer` のステータスバーは、そのウィンドウが開いている間しか読めません。
[`explorer-essentials.md`](./explorer-essentials.md) の「移動しきれず元が残った」系の結果
(部分完了) は、**ウィンドウを閉じた後に効いてくる情報**なので、notch に出口を作ります。

**受け入れ基準**

- アクティビティが無いときは**何も描かず、タイマーも回さない** (アイドル CPU 0 に落ちる)。
- ゴミ箱に捨て → explorer ウィンドウを閉じる → notch の `取り消す` で元に戻る、が通ること。
- 進捗の更新で notch が**自発的に開かない** ([§3.7](#37-同時に起きたときの捌き方))。

### 3.5 見張り (P5)

**新しい常駐ポーリングは増やしません。** ただし出どころは 1 つではないので、種類ごとに分けて書きます。

| 出どころ | 使うもの |
|---------|---------|
| ファイルの新着 (ダウンロード / スクリーンショット) | [`search.md`](./search.md) §6 の watcher に相乗り。監視対象のルートを 2 つ足すだけ |
| ボリュームの着脱 | **OS のイベント**。macOS は `NSWorkspace` の `didMount` / `didUnmount`、Linux は udev / UDisks2。ポーリングではない |
| 空き容量 | **watcher ではなく、コピー / 移動を始める前の事前チェック**。常時の監視はしない (常時見張るなら T2 に落ちる) |

| 見張るもの | 出すもの | なぜ notch か |
|-----------|---------|--------------|
| **ダウンロード先の新着** | 直近の 1-3 件を、**既定 10 分**だけ取り出せる状態で置く。ドラッグで直接アプリへ、クリックで explorer | 「ダウンロード → Finder で探す → アプリにドラッグ」という毎日の 3 手を 1 手にする |
| **スクリーンショット** | 撮った直後のファイルを出す。ドラッグ / 改名 / 移動 / 破棄 | 既定の保存先はデスクトップで、散らかる。撮った直後が唯一「これが何か」を覚えている時間 |
| **ボリュームのマウント / 取り外し** | マウントは `開く` 付き。取り外しは**進行中の操作がそのボリュームを触っているときだけ**警告 | 外付けを抜いた瞬間にコピーが壊れる事故を、抜く前に止められる |
| **コピー先の空き容量** | **足りないときだけ**。開始前に「あと N GB 足りません」 | 常時のディスク表示は T2/T4 に落ちる。足りない瞬間だけは行動がある |

- どの見張りも**個別にオフ**にでき、既定は「ダウンロード」と「スクリーンショット」がオフ、残りがオン
  (前者 2 つはユーザーのフォルダを覗くので、明示的に許可を取ってから)。
- 見張りは**通知を出しません**。notch の Idle 表示に留め、開いたときに読める形にします。

### 3.6 クリップ履歴パネル (P4)

**760 × 440 の固定パネル**をノッチから出します。検索バー、タブ、左に 5 件の一覧、右にプレビュー。

かつてここには「トレイはタブを持たない / 履歴全体は launcher の仕事」と書いていました。**両方とも撤回します。**
理由は下に書きます。

#### 中身

| 位置 | 高さ | 中身 |
|------|-----:|------|
| 検索バー | 42px | 打つと絞り込む。`link:` `img:` のような接頭辞で種別も絞る |
| タブ | 34px | クリップ / シェルフ / スニペット / 絵文字。`⌘1`–`⌘4` と `⌃Tab` |
| 本体 | 364px | 左 304px に**行高 44px × 5 行**、右 455px にプレビュー |

- プレビューの描き分け (テキスト / リンクの OGP / 画像 / 色 / ファイル / コード片) は launcher と
  **同一実装**です ([`launcher-requirements.md`](./launcher-requirements.md) §5.9)。
- 右ペインの下に 1 行: いつ / どのアプリから / どのウィンドウタイトルから。
- 機微情報の除外ルールも launcher と同一実装 (同 §5.4)。

#### 高さは変わらない。一覧が送られる

**`Expanded` は使いません。** クリップ履歴の高さは常に 440 です。

- 選択は 5 行目で止まり、その先は**一覧が上へ送られます**。最初から選択を中央に固定して送る手もありますが、
  先頭の 2 行が常に空くので採りません。
- 右端の細い軌道が、全体のどこにいるかを出します。**これだけが「あと何件あるか」の手がかり**です。
- 先頭で `↑` は末尾へ、末尾で `↓` は先頭へ**巻き戻します**。248 件を `↑` で辿り直させません。
- 絞り込んで一覧が 3 件になっても**パネルは縮みません**。打鍵のたびに高さが変わると、
  下に出ている行の位置が毎回動きます。空いた分は空けたままにします。

`Expanded` (伸びる状態) はシェルフのまま残します。あちらは件数が有限で、全部見えることに意味があるからです。

#### タブを付ける理由 (前の判断を覆す)

前は「上端まで往復した先でさらに選ばせるのは、往復の代金を二度取っている」と書いて却下しました。
**検索バーが付くと、この理由は成り立ちません。** もう手はキーボードの上にあるので、タブは往復ではなく
**もう 1 打鍵**です (`⌘1`–`⌘4`)。

**もう一つの理由は今も有効です**: ドラッグ中はタブを踏めません。なので —

- **タブが出るのはキーで開いたときだけ**です。ドラッグやホバーで開くトレイにはタブを出しません。
- 直行したいときはホットキー、開いてから気が変わったときはタブ。再召喚が要らなくなります。
- 種別の絞り込み (テキスト / リンク / 画像) はタブにしません。2 段になるうえ、検索バーに `link:` と
  打つ方が速いからです。

#### なぜ launcher ではなくノッチなのか

launcher の二枚組は 1100 × 700 で、**画面の 59%** を取ります。クリップを 1 つ貼るために作業中の
ウィンドウをほぼ覆うのは割に合いません。760 × 440 なら **26%** で、メニューバーの両端も、
作業中のウィンドウの下半分も見えたままです。

**未解決**: これは [§3.0](#30-判断基準) の T3 (「一過性か、携行中か」) を満たしていません。248 件の履歴も
スニペットも一過性ではありません。T3 でメディアとウィジェットを落としているので、**基準の側を
直さないと、次に同じ理由で何かを落とす根拠が弱くなります**。基準を書き直すか、「検索して取り出すもの」
という第 2 の枠を足すか、ここは決めていません。

### 3.7 同時に起きたときの捌き方

面積が狭いので、「複数のことが同時に起きたらどうするか」を決めていないと、最初の実装で破綻します。

| 規則 | 内容 |
|------|------|
| **同時に見えるアクティビティは 1 つ** | 残りはキューに積み、pill に `+2` のように数だけ出す |
| **優先度** | ① 要確認 (失敗・容量不足・取り外し警告) → ② 取り消し猶予 → ③ 進行中の操作 → ④ 見張りの新着。上が来たら下を押しのける |
| **同種は合流** | コピー 3 件は 3 行ではなく `3 件をコピー中`。合流した行を開くと内訳が出る |
| **自発的に開かない** | notch が自分でトレイを開くのは**ドラッグのときだけ**。他はすべて Idle (pill) 止まりで、開くのはユーザー | 
| **取り消し猶予は押しのけられない** | 猶予中に別のアクティビティが来ても、猶予の行は消えない (期限が来るまで) |
| **dismiss できる** | どのアクティビティも払える。同じ種類を「今後出さない」にでき、その設定は残る |

**受け入れ基準**: 5 種類のアクティビティを同時に発生させても、Idle の高さが変わらず、取りこぼしも重なりも起きない。

### 3.8 プライバシー

普段は何も出ていないので、**漏れるのは「開いたとき」**です。そして画面共有中は**開く**: 共有相手に渡す
ファイルを探す、さっきコピーしたものを貼る — 共有の最中こそ、シェルフとクリップに手が伸びる時間です。
しかも notch はどのアプリよりも手前に出るので、共有しているウィンドウを選んでいても一緒に映ります。
「普段は出ていないから安全」ではなく、**出る瞬間が共有中に重なる**という形の事故になります。

| 規則 | 内容 |
|------|------|
| **既定は「存在」だけ、「中身」は出さない** | Idle はシェルフの**件数**とアクティビティの**種類**まで。ファイル名・クリップ本文はトレイが出てから |
| **共有中は伏せる** | 画面共有・録画・ミラーリングを検出したら、ホバーしても中身を出さない (件数のみ)。検出手段は要調査 (R15) |
| **共有が始まった瞬間に、既に開いているトレイも伏せる** | ホバー以外 (クリック / ホットキー) で開いたトレイはポインタが離れても開いたままなので、「ホバーで出さない」だけでは**既に画面に出ている中身が残ります**。共有の開始を検出した時点で、開いているトレイは**その場で中身を伏せます** (閉じません — 畳むと操作中のものが消え、共有を止めた後に何をしていたか分からなくなります)。ファイル名は種別アイコンと件数に、クリップ本文は種別と出どころアプリに置き換わり、枠と行数はそのままです |
| **手動のプレゼンモード** | 検出できない環境のための明示スイッチ。launcher のコマンドからも切り替えられる |
| **判定できないときは伏せる側に倒す** | 検出手段が無い / 結果が曖昧な環境では、**共有中とみなして中身を出しません** (件数まで)。ユーザーが明示的にオフにするまでその扱いです。ここを「分からないなら出す」にすると、事故が起きるのは必ず分からない環境です |
| **Focus 連動** | OS の集中モード中は pill を抑制する (既定オン) |

**受け入れ基準**: シェルフ 5 件 + 直近のコピー 1 件を保持した状態で、次の **2 通りとも**
ファイル名・クリップ本文が 1 文字も画面に出ないこと。

1. 先にプレゼンモードにしてから画面共有を始め、その後トレイを開く。
2. **先にトレイを開いておいてから**画面共有を始める (ホットキーで開いた、つまり閉じないトレイで)。

ここで伏せる対象は**ファイル名とクリップ本文、そして具体的なパスと行き先の名前**です。
ドロップ先には「最近使ったフォルダ」や現在の explorer のディレクトリが並び、失敗の回収には
「残骸の場所」が出ます。**これらはフォルダ名とパスそのもの**なので、ファイル名と同じだけ漏れます。
共有中は**種別と件数だけ**にします (`最近使ったフォルダ` / `いま開いているフォルダ` / `3 件をコピー中`)。
落とす操作はそのまま効きます — 押した先がどこかは、伏せていても本人は知っているからです。
ドロップ先とライブアクティビティを出したままにするのは「存在」の側だからで、出さないと、
共有中に操作できなくなります。履歴全体はそもそも notch に出ません
([§3.6](#36-クリップ履歴パネル-p4))。

### 3.9 プラグインが載せるもの

[§3.0](#30-判断基準) の T4 で落ちたもの (メディア・天気・統計・CI 監視・ポモドーロ) は、**要らないのではなく、
コアが持つべきでない**というだけです。置き場所を plugin にします。これで「ウィジェットホストにしない」と
「ウィジェットが欲しい」が両立します。

> **これは置き場所の方針であって、動作の保証ではありません。** plugin が実際にそれを作れるかは、
> ① その情報を**公開 API で取れるか** (Now Playing は取れない可能性がある — R7)、② host が
> その capability を plugin に渡すか、の 2 つに依存します。現時点で `notch` interface にメディアや
> 音量を読む手段はありません。「コアでは作らない」と「plugin なら作れる」は別の主張で、
> 後者はまだ未確定です。天気や CI のように**ネットワークから取るもの**は既存の `network` 権限で足りるので、
> この不確かさは OS の状態を読む種類のものに限られます。

plugin が寄与できるのは 3 種類:

| 種類 | 内容 | 制限 |
|------|------|------|
| **activity** | 1 行のアクティビティを投げる (進捗つき可) | 権限 `notch`。**1 plugin あたり 3 件/分**、超過は静かに drop。優先度は常に最下位 (④) |
| **shelf action** | シェルフの選択に対するアクションを足す (例: 「画像を圧縮」「Gist にアップロード」) | 実行は既存の権限モデルに従う |
| **widget** | トレイが出ている間だけ描画される小さいカード | **開いている間しか更新されない**。閉じている間にタイマーを回す手段は与えない |

widget が「開いている間だけ」なのが要点です。これが無いと、notch は**常駐ポーリングの集積所**になり、
アイドル CPU 0 という予算 ([§6](#6-非機能要件)) が初日で崩れます。

描画は plugin API と同じ「データを返させて、描画はホストが行う」モデル
([`plugin-api.md`](./plugin-api.md) §4) に乗せ、`view-node` を使い回します。WIT の `notch` interface
(`push-activity` / `update-activity` / `resolve-activity` と、export の `render-widget`) は
**P5 で [`plugin-api.md`](./plugin-api.md) に追加する**もので、まだ存在しません。

### 3.10 コアに載せないもの

| 項目 | 落ちたテスト | 置き場所 |
|------|------------|---------|
| Now Playing (再生中 + 操作) | **T4** — Control Center が同じものを 20px 隣で出している。加えて macOS の `MediaRemote` は非公開 API (R7) | plugin (R7 次第。取れなければ誰も作れない) |
| 音量・輝度 HUD の置換 | **T4** — OS の HUD を消す公開手段が無く、消せないなら**二重に出る**だけ | plugin (同上) |
| バッテリー / 充電 | T2, T4 — 見た後にできることが無く、メニューバーに出ている | plugin |
| カレンダーの次の予定 | T3, T4 — 常設表示。EventKit 権限まで取って席を占める価値がない | plugin |
| システム統計 (CPU / メモリ / ネット / GPU) | T1, T2 — pull のものを push の席に置いている。常時ポーリングも要る | plugin |
| 通知のインライン返信 / 音声返信 | 通知の傍受は macOS に公開 API が無く、権限も重い | **作らない** |
| カメラミラー / ポモドーロ / 健康系 | Launcher × Explorer の軸から遠い | plugin |
| CI / PR 監視 | 同上 | plugin (`nohrs-plugin-git` 系) |
| テーマ / GIF / 触覚フィードバックの作り込み | — | P5 のテーマ機構に相乗りする範囲に留める |

## 4. ジェスチャとキー

| 操作 | 動作 |
|------|------|
| ホバー | Tray を出す ([§2.1](#21-ホバーの誤爆を防ぐ) の条件を満たしたときだけ) |
| クリック | Tray を出す (武装していなくても開く) |
| ファイルをドラッグして上端へ | Tray + ドロップ先ファンアウト ([§3.3](#33-ドラッグ時のドロップ先ファンアウト-p4)) |
| 下スワイプ / 二本指スクロール↓ | Tray → Expanded |
| 上スワイプ | 閉じる |
| `Cmd+Shift+B` (既定、変更可) | Tray の開閉トグル (シェルフ) |
| リーダー → `v` (既定、変更可) | **クリップ履歴パネル**を開く ([§3.6](#36-クリップ履歴パネル-p4))。グローバル既定は**置きません** — 下記 |
| `Esc` | 閉じる |
| `1`-`9` | シェルフの n 番目を開く (`Cmd` 併用で Reveal) |
| `⌘1`-`⌘4` / `⌃Tab` | **キーで開いたときだけ**、タブを移動 (クリップ / シェルフ / スニペット / 絵文字) |

タブが出るのは**キーで開いたときだけ**です。ドラッグやホバーで開いたトレイには出しません —
掴んでいる最中にタブは踏めないからです ([§3.6](#36-クリップ履歴パネル-p4))。

ホットキーは launcher と**同じホットキーレジストリ**を使います ([`launcher-requirements.md`](./launcher-requirements.md) §7.2)。

**クリップ履歴パネルにグローバルの既定を置かないのは、空いている組み合わせが無いからです。**
素直な `Cmd+Shift+V` は macOS のほぼ全アプリで「ペーストしてスタイルを合わせる」に割り当たっています。
notch のホットキーは**グローバル登録**なので、既定にすると**全アプリでそれを奪います**。
修飾キーを 4 つ重ねれば空きますが、それは覚えて使うキーではありません。
そこでリーダー ([`launcher-requirements.md`](./launcher-requirements.md) §5.10) の後の 1 打鍵に置きます —
リーダー方式を入れたのは、まさにこの「グローバルが枯渇している」状況のためです。

**既定のグローバル登録は 3 つです**: launcher の summon、リーダー、そしてシェルフのトグル
(`Cmd+Shift+B`)。シェルフだけ直接キーを持つのは、**ドラッグ中にリーダーを打てない**からです
(掴んでいる手は塞がっています)。要点は「2 つ」という数ではなく、
**割り当てを何個増やしてもこの 3 つのままである**ことです — Wayland の portal に
30 個登録しに行かずに済む、という §5.10 の主張はそこに掛かっています。
`Cmd+Shift+V` を使いたい人は自分で割り当てられます。そのとき設定画面は**何を奪うかを出します**。

既定が `Cmd+Shift+B` なのは、`Cmd+Shift+N` が explorer の「新規フォルダ」
([`explorer-essentials.md`](./explorer-essentials.md) §6) だからです。notch のトグルは**グローバル**登録なので、
アプリ内キーマップと重なると explorer が前面のときに両方が走ります。既定値を選ぶときは §7.2 の衝突検出を
アプリ内キーマップに対しても通すこと — レジストリがグローバル同士の衝突しか見ないなら、この種の事故は防げません。

## 5. 実装方式

### 5.1 ウィンドウ

| 観点 | macOS | Linux |
|------|-------|-------|
| ウィンドウ種別 | `NSPanel` + `.nonactivatingPanel` (フォーカスを奪わない) | X11: override-redirect / `_NET_WM_WINDOW_TYPE_DOCK`。Wayland: `wlr-layer-shell` の `top` レイヤ |
| レベル | `.floating` 以上 (メニューバーより上) | `_NET_WM_STATE_ABOVE` |
| スペース | `.canJoinAllSpaces` + `.fullScreenAuxiliary` (全画面アプリの上でも出る) | コンポジタ依存 |
| 背景 | 透過 + 角丸。notch の「黒」と継ぎ目なく繋ぐ | 同左 (コンポジタが無ければ不透明) |
| 入力 | Tray / Expanded 時はパネル全体でクリックを受ける。Hidden / Idle 時は **notch 帯だけがクリックを受け、それ以外は透過**させたい。notch 帯まで透過させると、§2.1 と §4 の「武装していないときはクリックで開く」が押せる場所を失います (R9) | 同左 |

#### ウィンドウは動かしません。動かすのは中身だけです

**OS のウィンドウのフレームを毎フレーム変えてアニメーションさせてはいけません。** macOS では
ウィンドウのリサイズと移動はウィンドウサーバと同期するので、60fps で回すと必ずカクつきます。
gpui の性能の問題ではなく、そこを通る限り避けられません。

そこで:

- notch のウィンドウは**起動時にパネルの最大到達サイズで作り**、以後**大きさも位置も変えません**。
  背景は透過で、描いていない領域はクリック透過にします (上表の「入力」、R9)。
- Hidden → Idle → Tray → `Expanded` も、クリップ履歴パネルの開閉も、**ウィンドウの中の描画**です。
  GPU のコンポジットだけで済むので、120Hz でも滑らかに出せます。
- 最大到達サイズは「クリップ履歴パネル 760 × 440」と「`Expanded` のシェルフ」の大きい方です。
  ディスプレイが変わったとき ([§5.2](#52-notch-の幾何)) だけは作り直します。

この帰結として、**[§3.6](#36-クリップ履歴パネル-p4) の「高さが変わらない」は実装の都合とも一致します**。
逆に、ウィンドウを伸ばす書き方をしていた箇所 (かつての `List` ↔ `Split` のリサイズ) は成立しません。

**アニメーションの手札**: gpui 0.2 が持つのは `Animation { duration, oneshot, easing }` と
`AnimationExt::with_animation` だけです (`linear` / `quadratic` / `ease_in_out` / `ease_out_quint` /
`bounce`、`gpui-component` が `cubic_bezier`)。**duration + イージング曲線で、バネも速度の引き継ぎも
ありません**。パネルの開閉はこれで十分ですが、次の 2 つは素直には書けません:

- `↓` を連打したときの再照準 — duration 固定だと最初からやり直すのでカクつきます。
- ドラッグを離したあとの慣性。

`with_animation` の閉包は生の 0..1 を受け取るので、**その中で自前のバネ (位置と速度) を進めれば
速度の引き継ぎはできます**。まずはこれで書き、足りなければ外部の motion crate を検討します
(依存を 1 つ増やす判断になるので、そのときに改めて決めます)。

#### フォーカスは、開き方で変えます

`.nonactivatingPanel` は「前面アプリからフォーカスを奪わない」ためのもので、シェルフにはこれが正しい
(掴んで落とすだけで、キーを打たないため)。ですが [§3.6](#36-クリップ履歴パネル-p4) の検索バーは
**キー入力を受けるのでパネルが key になる必要があります**。

| 開き方 | フォーカス | 閉じたとき |
|--------|-----------|-----------|
| ホバー / ドラッグ (シェルフ) | 奪わない | そのまま |
| キー (クリップ履歴・スニペット・絵文字) | **奪う** | **直前のアプリに返す** |

返す仕組みは新しく作りません。[`launcher-requirements.md`](./launcher-requirements.md) §5.11 の「戻り先」を
そのまま使います (貼り戻しが既に要求しているもの)。`restores_focus` を持つコマンドだけが返す、も同じです。

**「notch は決してフォーカスを奪わない」という前提は、ここで取り下げます。**

**重要な未解決点 (R1)**: gpui 0.2 の `WindowOptions` は `window_bounds` / `kind` (`Normal` / `PopUp` / `Floating`) /
`window_background` / `window_decorations` を持ちますが、**ウィンドウレベルの直接指定・非アクティブ化パネル・
クリック透過・全スペース表示の公開 API は見当たりません**。launcher も同じ制約を受けていて、
「Wayland の activation token を渡せない」問題が既に出ています ([`launcher.md`](./launcher.md) §13)。

取り得る道は 3 つ:

| 案 | 内容 | 評価 |
|----|------|------|
| **A** | gpui に upstream で API を足す (`WindowOptions::level`, `nonactivating`, `mouse_passthrough`) | 本筋。ROADMAP Future Work の「GPUI コミュニティへの貢献」と整合。ただしマージ待ちが読めない |
| **B** | `nohrs-platform` ([`launcher-requirements.md`](./launcher-requirements.md) §7.3) から、gpui が作った `NSWindow` を取得して属性を後付けする | 実現可能だが gpui 内部表現に依存し、版上げで壊れる |
| **C** | notch 専用ウィンドウだけ gpui の外で作る | 描画基盤が二重になる。却下 |

**推奨は A を目標に B で先行**。B のコードは `nohrs-platform` の 1 モジュールに閉じ込め、
「gpui に API が入ったら消す」ことを doc comment に明記する。

### 5.2 notch の幾何

- macOS: `NSScreen.safeAreaInsets.top > 0` で notch の有無を判定し、`auxiliaryTopLeftArea` /
  `auxiliaryTopRightArea` から notch の幅・高さを求める (機種ごとの数値をハードコードしない)。
- ディスプレイ構成変更 (外部接続 / 解像度変更 / スケーリング変更) を監視して再配置する。
- 内蔵ディスプレイが閉じている (クラムシェル) ときは、フォールバックの浮遊バーに切り替える。
- どのディスプレイに出すかは設定 (既定: 内蔵 → 無ければメインディスプレイ)。
- **`display = "all"` は「全部に同じものを出す」ではありません。** サーフェスは常に **1 つ**で、
  `"all"` は**ポインタが今いるディスプレイに引っ越す**という意味です。全画面に複製すると、
  ホバーの持ち主が曖昧になり (どの画面のトレイが開いているのか)、ドラッグ中はさらに悪化します。
  引っ越しはドラッグ中には行いません — 掴んでいる最中に的が別の画面へ移ると、落とし先を見失うためです。

| 設定値 | 出る場所 | ホバー / ドラッグの受け手 |
|--------|---------|------------------------|
| `"builtin"` (既定) | 内蔵ディスプレイ。無ければメイン | そのディスプレイの上端だけ |
| `"main"` | メインディスプレイ | 同上 |
| `"all"` | ポインタがいるディスプレイ (1 つだけ、追従) | 追従先の上端だけ。ドラッグ中は追従を止める |

### 5.3 crate 配置

```text
crates/nohrs-notch/          # 新規 (D6)
├── src/nohrs_notch.rs       # サーフェスのライフサイクル、状態機械
├── src/window.rs            # ウィンドウ生成・幾何・ディスプレイ追従
├── src/shelf.rs             # シェルフのモデル (ビューは nohrs-ui)
└── src/activity.rs          # ライブアクティビティの購読
```

依存は `nohrs-ui` / `nohrs-services` / `nohrs-store` / `nohrs-platform` / `nohrs-core` の下向きのみ。
**`nohrs-launcher` と `nohrs-pages` は参照しません** ([`architecture.md`](./architecture.md) §2 の依存ルール)。
共有するのはコマンドレジストリ (`services::command`) と UI コンポーネント (`nohrs-ui`) だけです。

### 5.4 ライブアクティビティの購読

進捗は「ファイル操作サービスが `Progress` イベントを流し、notch が購読する」形にします。
explorer も同じイベントを購読して自分のステータスバーを更新するので、**進捗の実装は 1 つ**で済みます。

```text
services::fs::ops  ──(async-channel / postage broadcast)──┬──▶ pages::explorer  (ステータスバー)
                                                          └──▶ notch::activity  (ライブアクティビティ)
```

## 6. 非機能要件

| 観点 | 予算 |
|------|------|
| Idle (アクティビティ無し) の CPU | **0%** (タイマーを回さない。イベント駆動のみ) |
| ホバー成立 → トレイ描画 | < 50ms (滞留 250ms はこれに含めない) |
| ドラッグ検知 → Tray | 事前武装できる環境は < 150ms、Wayland は notch 帯に入ってから < 80ms ([§3.3](#33-ドラッグ時のドロップ先ファンアウト-p4)) |
| ドラッグ推定のポーリング (macOS) | 左ボタンが押されている間だけ 30Hz。押されていない間は **0** |
| 追加 RSS | < 25MB (シェルフのサムネイル込み) |
| ディスプレイ構成変更への追従 | < 1s |
| 画面収録権限 | **不要**。必要になる機能は作らない |
| フルスクリーン動画の上に出る | 出せること。ただし**動画再生中は Idle を抑制**する設定を持つ |

## 7. 設定 (`config.toml` 追加分)

```toml
[notch]
enabled = true
display = "builtin"        # "builtin" | "main" | "all"
fallback_bar = true        # notch が無い環境で浮遊バーを出すか
idle_indicator = true      # Idle (pill) を出すか
open_on_drag = true        # ドラッグが上端に来たら開くか (先読みは [notch.drag] の prearm)
hotkey = "Cmd+Shift+B"

[notch.hover]
# ホバーの誤爆対策 (§2.1)。ここを緩めるとメニューバー操作でトレイが降ってくる。
enabled        = true      # false にするとホバーでは開かず、クリックとホットキーだけになる
dwell_ms       = 250       # notch 帯にこれだけ留まって初めて開く。横断では開かない
from_below     = true      # 画面内側から上端へ向かう動きだけを入り口にする
drag_dwell_ms  = 80        # ドラッグ中は緩める (方向も問わない)

[notch.drag]
# ドロップ先ファンアウト (§3.3)。幾何は事前武装の可否で変わりません。
prearm            = true   # ポインタが上端に来る前に的の枠を描き始める。Wayland では効きません
prearm_timeout_ms = 300    # マウスダウンからこの時間ドラッグが始まらなければ推定をやめる (macOS)
max_targets       = 5      # 増やすと狙えなくなります

[notch.tray]
# ホバー / ドラッグで開くトレイ (シェルフ)。ここにはタブを出しません (§3.6)。
recent_clip    = true      # 直近のコピーを 1 行だけ出す
activity_strip = true      # 進行中・要確認の帯
widgets        = false     # plugin 提供のウィジェット (§3.9)。P5

[notch.clipboard]
# キーで開くクリップ履歴パネル (§3.6)。高さは固定で、一覧が送られます。
enabled     = true
leader_key  = "v"          # リーダーの後の 1 打鍵。グローバル既定は置きません (§4)
wrap        = true         # 先頭で ↑ は末尾へ、末尾で ↓ は先頭へ
tabs        = ["clipboard", "shelf", "snippets", "emoji"]
split_ratio = 0.4          # 左の一覧の**初期**比率。動かした値は redb (`notch.clipboard.split_ratio`) に入ります

# 行数は 5 で固定です。設定にしません — パネルは 760 x 440 固定 (§3.6) なので、
# 6 行以上は入らず、入れようとすると高さが動いて固定の前提が崩れます。5 件を超える分は送られます。

[notch.privacy]
# 既定は「存在」だけを出し、「中身」はトレイが出てから (§3.8)。
presentation_mode = false  # 手動。オンの間はホバーしても中身を出さない
hide_when_shared  = true   # 画面共有・録画・ミラーリングを検出したら伏せる (R15)
suppress_in_focus = true   # OS の集中モード中は pill を抑制する

[notch.watch]
# 見張り (§3.5)。ユーザーのフォルダを覗く 2 つは既定オフ。
downloads       = false    # 新着ダウンロードを一定時間だけ取り出せる状態に置く
downloads_ttl_minutes = 10
screenshots     = false    # 撮った直後のスクリーンショットを出す
volumes         = true     # マウント / 取り外し (取り外しは進行中の操作があるときだけ警告)
low_disk        = true     # コピー先の空きが足りないときだけ

[notch.activity]
undo_grace_seconds = 10    # 破壊的操作の取り消し猶予 (§3.4)。0 で無効

[notch.shelf]
persist = true             # 再起動を跨いで復元するか
max_items = 100
```

## 8. フェーズ割当

| Phase | 範囲 |
|-------|------|
| **P4** | サーフェス基盤 (状態機械・ウィンドウ・幾何・フォールバック) / シェルフ (§3.2) と `noh shelf` CLI / ドロップ先ファンアウト (§3.3) / ライブアクティビティ + 取り消し猶予 + 失敗の回収 (§3.4) / **クリップ履歴パネル 760 × 440 — 検索バー・タブ・ローリング一覧・プレビュー (§3.6)** / アービトレーション (§3.7) / プライバシー既定 (§3.8) / 設定 |
| **P5** | 見張り (§3.5) / plugin の寄与 3 種と WIT `notch` interface、plugin が投げるアクティビティ (§3.9) / テーマ連携 |
| **P6** | 性能ゲート (Idle CPU 0%) の CI 計測 / Linux の対応状況マトリクス確定 |

**P4 に §3.7 と §3.8 を入れてあるのは後回しにできないため**です。アービトレーションは
「2 つ目のアクティビティが来た日」に必要になり、後から入れると表示の作りを作り直します。
プライバシーの既定 (中身を出さない) は、後から変えると**それまでのユーザーが既に画面共有で漏らした後**です。

| R19 | `wlr-layer-shell` のサーフェスに、コンポジタが DnD (`wl_data_device.enter`) を配送するか。しないなら Linux のファンアウトは無くなり、シェルフは launcher / explorer から使う形に倒す (R8 と同じ倒し方) |

| R22 | **`Expanded` とクリップ履歴パネルの最大到達サイズ**をどう決めるか。ウィンドウはこの大きさで固定するので、シェルフの `max_items` = 100 を全部見せる高さにすると画面をほぼ覆います。`Expanded` 側にも上限が要る (§5.1) |
| R25 | **`public.file-url` の一時ファイルの持ち主と期限を、プロセスが落ちた後からでも判断できる形でどう持つか** (§3.2 の A〜G)。起動単位で一意な識別子を 3 プラットフォームで取れるか (Linux `/proc/sys/kernel/random/boot_id`、macOS `kern.boottime`、Windows は起動時刻)。取れない環境で E (到達できないファイルを残さない) をどう満たすか。ここは**同じ段落に機構を書き足す形で 9 回直し、そのたびに前の修正が次の穴を作りました** — 実機で確かめてから決めます |
