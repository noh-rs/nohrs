# 0009 — インデックスの書き手は常駐プロセスに任せ、専用デーモンは作らない

> Status: Accepted
> Date: 2026-09-16

## Context

tantivy の `IndexWriter` はインデックスディレクトリに**排他ロック**を取り、プロセスを跨いで同時に 1 つしか
存在できない。`IndexManager::new()` は起動時に無条件で writer を開いていたため、GUI が立ち上がっている間は
**他のどのプロセスもインデックスを更新できなかった**。CLI (`noh search` / `noh index`) を足すにあたり、これが
最初に突き当たった制約である ([`docs/cli.md`](../cli.md) §7、[`docs/search.md`](../search.md) §6)。

「書き手を専用デーモン (`nohrs-indexd` 等) に集約し、GUI も CLI も reader として振る舞う」案を検討した。
単一 writer が構造的に保証され、UI が開いていなくても増分更新が進み、将来の重い書き込み (embedding 生成) を
隔離できる。

一方で、常駐デーモンには次のコストがある:

- **プロダクトの主張との衝突**: README は "Search without Spotlight — no dependency on the OS search daemon" を
  掲げている。自前の常駐デーモンを足すのは、その看板と噛み合わない。
- **常駐物が嫌われる理由を自分で引き受ける**: ログイン時からの常駐、見えない CPU / バッテリー消費、止め方が
  分からない、launchd / systemd への登録、本体とのバージョン不整合。
- **払う時期が早い**: デーモンの旨みが要るのは「UI を開いていない間も増分更新したい」「embedding 生成を
  隔離したい」段階、すなわち V3 / ベクトル検索 ([`docs/search.md`](../search.md) §2) 以降である。
- **ランチャーが既に常駐する**: グローバルホットキーのランチャーがある以上、書き手を担える常駐プロセスは
  もともと存在する。別プロセスを立てるのは役割の重複になる。

## Decision

**専用デーモンは作らない。writer を遅延取得にし、読み手は全員ロックなしで読む。**

| 役割 | 実装 |
|------|------|
| 読み | `IndexReader` — `Index::open_in_dir` + reader のみ。ロックを取らないので何プロセスからでも同時に読める |
| 書き | `IndexManager` — **最初の書き込み時に** writer を取得し、以後保持。取得できなければ「他のプロセスが書いている」と報告する |
| 書き手になるのは | そのとき writer を取れたプロセス。通常は常駐している GUI / ランチャー。ヘッドレスでは `noh index build` |

インデックスを作らないまま読むことは**しない**: `IndexReader::open` は空のインデックスを作成せずに `None` を
返す。空のインデックスは「壊れていないが何も答えない」状態で、以後の検索がすべて 0 件になるため。

バックグラウンド更新が要るユーザーは `noh index build` を cron / systemd timer に載せられる。nohrs の側から
勝手に常駐はしない。

## Consequences

### Positive

- CLI と GUI が同時にインデックスを読める。`noh search` はアプリが起動していても動く
- 常駐プロセス・IPC プロトコル・自動起動・パッケージングを一切増やさない
- 索引が古い / 無いことは黙って 0 件にならず、`noh search` の stderr と `noh index status` で可視化される
- 将来デーモンに移す場合も、変わるのは writer 役の置き場所だけで、読み手の API (`IndexReader`) は変わらない

### Negative

- GUI もランチャーも起動していない間は増分更新が進まない (ユーザーが timer を仕掛ける必要がある)
- 「誰が writer を持っているか」はロックの取得可否でしか分からず、保持者の名前は出せない
- `noh index build` はアプリ起動中だと失敗する (メッセージで理由は示す)

## Alternatives Considered

| 案 | 棄却理由 |
|----|---------|
| 常駐デーモン (`nohrs-indexd`) を今導入 | 旨みが要るのは V3 / ベクトル検索以降。今払うコスト (ライフサイクル、IPC、パッケージング、常駐物への忌避) に対して早すぎる。README の "no search daemon" とも衝突 |
| アイドルで自己終了する書き込みヘルパー | 常駐型よりは穏当だが、結局「writer 権を持つ者が書く」に自動起動が付いただけ。自動起動が要る段階になってから足せる |
| GUI が起動時に writer を取り続ける (従来) | CLI からインデックスを一切触れない。二重起動も不可 |
| SQLite FTS5 に寄せて複数プロセス書き込みを可能にする | [ADR 0001](./0001-sqlite-tantivy-hybrid-search.md) の V2 そのもので、検索エンジンの載せ替え。writer ロック問題の解消とは別の PR で扱うべき |

将来デーモンを導入する場合の形も、判断の前提として書き残しておく: socket に流すのは**書き込み要求と状態
問い合わせだけ**とし、検索クエリは流さない。読者は tantivy を直接読むので、デーモンが落ちても検索は動き続け、
IPC がホットパスに入らない。
