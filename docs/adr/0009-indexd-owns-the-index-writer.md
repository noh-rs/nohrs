# 0009 — インデックスの watcher と writer を `nohrs-indexd` に集約し、寿命を nohrs に一致させる

> Status: Accepted
> Date: 2026-09-17

## Context

tantivy の `IndexWriter` はインデックスディレクトリに**排他ロック**を取り、プロセスを跨いで同時に 1 つしか
存在できない。`IndexManager::new()` は起動時に無条件で writer を開いていたため、GUI が立ち上がっている間は
**他のどのプロセスもインデックスを更新できなかった** (`noh index build` も、2 つ目のウィンドウも)。

これを「writer は最初の書き込み時に取る」に変え、読み手は全員ロック不要の `IndexReader` にした。これで
CLI からもインデックスを触れるようになったが、**書き手が「そのとき writer を取れたプロセス」のままである**
という問題が残る。判断を要したのは次の点である。

- **ランチャーの検索がインデックスを使う。** ランチャーは他アプリの前面からグローバルホットキーで呼ばれる
  ([`launcher.md`](../launcher.md) §2)。索引の鮮度がランチャーの UX 契約の一部になるため、
  「nohrs のウィンドウを開いていた人だけ結果が正しい」は成立しない。
- **watcher と writer を別プロセスに分けると取りこぼしが黙って起きる。** watcher の出力は書き込み要求そのもの
  で、消費側が落ちている間のイベントは誰にも届かず索引が静かにずれる。同じプロセスが持てば
  「indexd が生きている ⟺ 索引が追従している」という**単一の検査可能な条件**になる。
- **ランチャーのプロセスは索引の置き場所として不適。** ホットキー→ウィンドウ <100ms、キー入力→リスト更新
  <50ms ([`launcher.md`](../launcher.md) §12) の対話プロセスであり、索引はスループット側の仕事である。
  同居させると、tantivy の writer (50MB ヒープ + マージスレッド) と将来の embedding モデル (数百 MB〜GB) が
  ホットキーを握るプロセスのアロケータとスレッドプールを奪い合い、索引側の OOM やパニックが**ユーザーの
  ホットキーごと落とす**。OS から見たプロセス分類も前面アプリのままなので、[`search.md`](../search.md) §7.1 の
  「UTILITY/BACKGROUND で回す」も効きにくい。なお**ランチャーのホットパスは tantivy を引いていない**
  (名前索引 `search::file_index` を引く) ので、同居させる利点は元から無い。
- **単一 writer の競合は今後増える。** 現状の競合相手は GUI・2 つ目のウィンドウ・`noh index build` の 3 者。
  P4 でプラグインが索引に書けるようになり、ベクトル索引が来ると更に増える。「取れた者が書く」はレースであり、
  ユーザーに見える失敗になる。

一方で、**常駐デーモンは嫌われる**。ログイン時からの常駐、見えない CPU / バッテリー消費、止め方が分からない、
launchd / systemd への登録、本体とのバージョン不整合。README は "Search without Spotlight — **no dependency
on the OS search daemon**" を掲げており、ログイン常駐物を足すのは看板と噛み合わない。

## Decision

**`nohrs-indexd` に watcher と writer を集約する。ただし常駐させず、寿命を nohrs のそれに一致させる。**

| 役割 | 置き場所 |
|------|---------|
| **watcher (変更検出)** | indexd |
| **writer (書き込み)** | indexd |
| **将来の embedding 生成** | indexd |
| **読み** | 各プロセスが `IndexReader` で**直接** tantivy を読む |
| **追いつき (nohrs 終了中の変更)** | indexd 起動時の増分パス |

- **起動**: 最初に必要としたプロセス (ランチャー / アプリ / `noh index build`) が socket に繋ぎ、繋がらなければ
  spawn する。ログイン項目にも launchd / systemd にも登録しない。
- **終了**: 最後のクライアントが去り、猶予時間が過ぎたら自分で exit する。
- ランチャーはグローバルホットキーのために**もともと常駐**なので、indexd を足しても**ユーザーから見た常駐物は
  「nohrs が起動しているかどうか」の 1 つのまま**である。quit すれば両方消える。そして nohrs を終了している間は
  ランチャーも呼べないため、「ランチャーが古い索引で答える窓」は原理的に存在しない。
- **読みは socket を通さない。** これが設計の要で、indexd は**任意のインフラであって依存ではない**。落ちても・
  古くても・居なくても検索は動く (鮮度が止まるだけ)。段階導入とクラッシュ耐性が同時に手に入る。
- socket が運ぶのは**書き込み要求・状態問い合わせ・イベント通知**だけ。イベント (commit / 進捗) は、読み手が
  `IndexReader::reload` を呼ぶ合図と UI の進捗表示に使う。各プロセスが tantivy の commit 監視スレッドを持たずに
  済むという副次効果もある。

「最後のクライアントが去ったら終了」の**参照カウントはカーネルが持つ**。`Drop` はプロセス境界を越えず、
SIGKILL でも走らないため、Rust 側の後始末には頼れない。unix socket の接続はプロセスが**どんな死に方をしても**
カーネルが閉じ、サーバ側に EOF として届く。したがって「生きているクライアント数 = 開いている接続数」であり、
これはクラッシュに対して正しい。Rust が担うのはその上の**RAII 表現** — クライアントはハンドルを持ち、
落とせば接続が閉じる。**ランタイムが OS 側にある RAII** と考えるのが正確である。

二重起動の競合は、indexd が生存中ずっと保持する `flock` で解く。クライアントは接続に失敗したらロックを試し、
取れなければ「誰かが起動中」なので接続をリトライし、取れれば spawn する。バージョン不整合は接続時の
ハンドシェイクで検出し、**短命だからこそ**古い方を終了させて自分の版を起動できる。

## Consequences

### Positive

- 索引の鮮度がランチャーの起動状態と一致し、「開いていた人だけ正しい」が無くなる
- ホットキーを握るプロセスから索引の CPU・メモリ・クラッシュが隔離される。将来の embedding 生成の置き場所も決まる
- 単一 writer がレースではなくキューになり、「アプリが writer を握っていて失敗」がユーザーから見えなくなる
- 変更ストリームの消費者を writer とランチャーの名前索引の 2 つにできる ([`launcher.md`](../launcher.md) §291 の宿題)
- 常駐物を増やさない (ログイン項目なし・OS への登録なし)。README の主張とも矛盾しない
- indexd が落ちても検索は動き続ける

### Negative

- 新しいバイナリ・IPC プロトコル・spawn とバージョン整合の面倒が増える
- nohrs を終了している間は索引が追従しない (欲しい人は `noh index build` を timer に載せる、または opt-in の常駐設定)
- Windows は unix socket 前提のこの経路を使えないため、当面 in-process フォールバックで動く
- 「誰が writer を持っているか」はロックの取得可否でしか分からず、保持者を名指しはできない

## Alternatives Considered

| 案 | 棄却理由 |
|----|---------|
| ランチャーの常駐プロセスに載せる (「どうせ常駐している」) | 常駐かどうかではなく**レイテンシ予算と運命の共有**が問題。ランチャーは 50ms/100ms の対話プロセスで、しかも tantivy を引いていない。索引側の事故がホットキーごと落とす |
| watcher は UI、writer は indexd | indexd が落ちている間のイベントが失われ、索引が黙ってずれる。鮮度が検査可能な条件にならない |
| ログイン時から常駐するデーモン | 常駐物が嫌われる理由をすべて引き受ける。README の "no search daemon" とも衝突。ランチャーが既に常駐なので、寿命を一致させれば足りる |
| writer を取れた者が書く (この ADR 以前の判断) | 書き手が居ない時間が生まれ、鮮度がランチャーの契約を満たせない。競合も残る |
| SQLite FTS5 に寄せて複数プロセス書き込みを可能にする | [ADR 0001](./0001-sqlite-tantivy-hybrid-search.md) の V2 そのもので、検索エンジンの載せ替え。watcher の所在という本件とは別の問題 |
