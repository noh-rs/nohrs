writer は一つしか許さないが、reader は何プロセスからでも同時に読めるストアがある。[tantivy](https://github.com/quickwit-oss/tantivy) のインデックスがそうであり、LMDB の書き込みトランザクションもそうである。単一 writer ロックで守られたストアは、いずれも同じ性質を持つ。

この制約はストアごとにかかる。一つのインデックスを開くプロセスがマシン上にいくつあろうと、writer になれるのはそのうち一つだけである。どれが writer になるかは、ディスク上のファイルに対して取られるロックで決まる。プロセスをまたいで見えるものが、それ以外にない。

writer をどれか一つのプロセスの中に置くと、そのプロセスが動作している限り、そのプロセスがストアを独占する。他のプロセスは書き込めない。アプリの二つ目のインスタンスも、書き込みを行うコマンドラインツールも拒否される。これを避けるには、writer に専用のプロセスを与える以外にない。

ではそのプロセスは<strong>いつ終了すればよいのか</strong>。

## 必要とされている間だけ存在させる

writer は、必要とされている間だけ存在すべきである。ログイン時に自動起動すべきではないし、launchd や systemd に登録すべきでもない。登録されて常駐するプロセスは、停止させたいときに人手で探し出して止める必要がある。

これは参照カウントである。writer を必要としている主体一つにつきカウントを一つ持ち、ゼロになった時点でプロセスを終了する。同一アドレス空間の中でなら `Arc` で済み、Rust では三行で書ける。問題は、数えるべき対象が別のプロセスに存在することである。

## デストラクタが届かない範囲

別のプロセスを数えるとなると `Drop` は使えない。デストラクタ、`defer`、`finally` といった言語レベルの後始末機構も、同じ理由で使えない。理由は二つある。

1. <strong>`Drop` は `SIGKILL` では実行されない。</strong>OOM killer による終了でも、segfault でも、電源断でも実行されない。クライアントが正常に終了したときにしか正しくないカウントは、それが最も必要な場面で狂う。writer を永久に走らせ続けるのは、後始末のコードが一行も実行されなかった場合だからである。
2. <strong>`Drop` はアドレス空間を越えない。</strong>クライアント側のデストラクタから writer 側のカウンタを減らすことはできない。クライアントが終了時に何を実行しようと、writer がそれを知るには、プロセス境界を越える仕組みが別に必要である。

容易に思いつく代替案は、いずれも成立しない。

- <strong>ハートビート</strong>はプロセス境界を越えられるが、確実な事実をタイムアウト付きの推測に変える。終了したことが判明するのはタイムアウトが経過した後であり、単に処理が重いだけのクライアントは終了したものと見なされる。
- <strong>クライアントの pid を監視する方法</strong>は pid の再利用と競合する。pid を確認してから判断を下すまでの間に、その番号が別のプロセスのものになっている可能性がある。
- <strong>`PR_SET_PDEATHSIG`</strong> は<em>親</em>が終了したときに子へシグナルを送る機構であり、ここで必要なものとは向きが逆である。writer は自分を起動したプロセスより長く存続しなければならない。起動元が一秒後に終了する単発のコマンドであっても、writer は次の呼び出しのために残る必要がある。

## カーネルがすでに数えている

カーネルはこのカウントをすでに保持している。しかも、必要とされる意味のまま保持している。

<strong>unix socket の接続は、カーネルが参照カウントしている。</strong>カーネルが数えているのは fd の本数である。プロセスが終了すれば、いかなる終わり方であっても、ユーザーコードが一行も実行されなくても、その fd はカーネルが閉じる。片側の最後の fd が消えた時点で、反対側は end-of-stream を読む。

この数は、生存しているクライアントの数とは一致しない。一つのプロセスが接続を二本開けば二と数えられ、子が引き継いだ fd は、それを開いたプロセスが終了した後も接続を保つ。writer を起動したままにしておく理由は、誰かが接続を保持していることであるから、必要となるのはこの数である。そしてこの数は `kill -9` に対しても正しい。維持を求められているユーザー空間のコードが、どこにも存在しないためである。

同じことは socket 以外にも当てはまる。<strong>あるプロセスの生存を別のプロセスが知らなければならないときは、カーネルが維持しているものを使う。</strong>開いた接続、アドバイザリロック、読み側が EOF を返すパイプ。言語側の型は、その上に被せる RAII のラッパーで足りる。プロセスが終了時に忘れず実行しなければならない処理は、いつか実行されない。

考え方は `Arc` のままで、カウントの実体だけをカーネルに預ける。実装は次のようになる。

## lease の形

writer 側の lease は通常の RAII 型である。設計上重要なのは一点だけで、<strong>接続を処理する関数がこれを値で受け取る</strong>ことである。

```rust
/// 接続が終わるまで、クライアント一つを処理する。
///
/// `lease` は値で受け取り、どこにも渡さない。この関数が返ること自体が解放である。
/// 接続を終わらせるのは多くの場合クライアント側の socket が閉じることであり、
/// クライアントがどのような終わり方をしても、閉じるのはカーネルである。
/// こちら側から終わらせる場合もある。`Stop` を受けたときと、
/// 読まれなくなった相手への書き込みが失敗したときである。
fn serve_client(&self, stream: UnixStream, lease: Lease) -> Result<()> {
    let mut reader = BufReader::new(stream);
    while let Some(request) = read_frame::<Request>(&mut reader)? {
        // ...
    }
    Ok(()) // ここで lease が落ちる
}
```

lease を持たずにクライアントを処理する方法はなく、処理を終えた後も持ち続ける方法もない。解放を忘れることは起こらない。関数から返ること自体が解放だからである。

## 参照カウントを `Arc` にしない理由

実際には猶予時間が必要である。シェルスクリプトの中で二つのコマンドが一秒の間隔で実行されたときに、writer の起動コストを二度払う理由はない。そこで writer は、最後のクライアントが去ってから一定時間待機したうえで終了する。ここでは 90 秒としている。

これにより「最後の drop で終了する」という形は崩れる。`Arc` はカウントがゼロになったことを伝えて消えるだけで、それをきっかけに動き出したものを後から取り消す手段は残らない。猶予時間中に到来したクライアントはカウントダウンを止めなければならないが、止めるための手がかりが残っていない。

そこで、カウントと、それがゼロになった時刻とを明示的に保持する。

```rust
struct State {
    live: usize,
    /// 最後にカウントがゼロになった時刻。誰かが lease を持っている間は `None`。
    /// 保留中のシャットダウンをクライアントが取り消せるのは、これがあるためである。
    idle_since: Option<Instant>,
    /// `release` が立てるフラグ。カウントがいくつであっても待機を打ち切る。
    /// `Stop` がこれを使う。猶予時間を待たない唯一の出口である。
    released: bool,
}
```

待機には条件変数を使うため、処理のない writer を保持するコストはない。

```rust
pub fn wait_until_idle(&self) {
    let mut state = self.lock();
    loop {
        if state.released {
            return;
        }
        match state.idle_since {
            // 誰かが接続している。状況が変わるまで行うことはない。
            None => state = self.wait(state),
            Some(since) => match self.grace.checked_sub(since.elapsed()) {
                None => return,
                Some(remaining) => state = self.wait_for(state, remaining),
            },
        }
    }
}
```

これを独立した型として切り出しておくと、<strong>socket を一切使わずに検証できる</strong>。lease を取り、手放し、待機がいつ返るかを確かめればよい。

## どちらが writer になるかを決める

writer の生存期間のもう一方の端、すなわち起動の側も同じ形をしている。writer を必要とするプロセスが同時に二つあれば、両方が起動を試み、敗れた側は引き下がらなければならない。

この勝敗を socket ファイルの有無で決めることはできない。socket ファイルは、それを作成したプロセスより長く残る。ファイルが存在することは、そこで誰かが待ち受けていることを意味しない。pid ファイルはさらに問題が多い。pid の再利用が再び関わってくるためであり、そこに書かれた番号は、読んだ時点では別のプロセスのものになっている可能性がある。

代わりに、writer の生存期間を通じて保持する<strong>アドバイザリロック (`flock`)</strong> で決める。カーネルがこのロックを解放するのは、それを参照する最後の fd が閉じられたときである。ここでも数えているのは fd であるため、子が引き継いだ複製が残っていれば、ロックを取得したプロセスが去った後もロックは保たれる。ロックを取得して誰にも渡さないプロセスにとっては、ロックが解放される時点はそのプロセスが終了した時点であり、終了の仕方は問われない。socket とまったく同じ規則である。この設計の両端は、一つの対象を参照する fd の数という同じカウントに乗っており、数えているのも同じカーネルだからである。

アドバイザリロックは、ロックを取得しに行ったプロセスどうしの間でしか意味を持たない。ここではそれで十分である。決めたいのはどちらが writer になるかであり、候補は両方ともロックを取得しに来ている。pid ファイルは読むたびに疑う必要があるが、ロックは古くならない。

writer になることも、writer をやめることも、同じ理由でカーネルに委ねている。

## writer を経由しない reader

単一 writer の設計を成り立たせているのは、一つの不変条件である。<strong>reader は writer を経由しない。</strong>

読み取りにロックは要らないため、reader はストアを直接開く。同時に何プロセスから開いてもよい。socket が運ぶのは書き込み要求、状態の問い合わせ、commit の通知だけであり、クエリが流れることはない。

これにより writer は<em>あってもなくてもよいインフラ</em>となる。writer が停止していても、応答しなくなっていても、バージョンが一つ古くても、読み取りは答えを返す。本来よりいくらか古いストアから返すだけである。存在すら知らないバックグラウンドプロセスの不調が原因でエラーになる、という失敗はそもそも起こらない。同じ理由により、writer プロセスは読み取り経路を一切変更せずに、段階的に導入することも、後から取り外すこともできる。

## 予告のない終了を検証する

要となるテストはプロセス内では記述できない。確かめたいのは、終了時に一行もコードが実行されなかった場合の挙動である。そこで、接続したまま待機するだけの小さなヘルパーバイナリを用意し、テストはこれを kill する。

```rust
let mut held = Command::new(env!("CARGO_BIN_EXE_holds_a_connection"))
    .arg(&fixture.endpoint.socket)
    .spawn()
    .unwrap();
until("the killable client to be counted", || {
    probe.status().unwrap().clients == Some(2)
});

// ここから先、writer を支えているのは kill される側のみである。
drop(probe);
std::thread::sleep(GRACE * 2);
assert!(!gone(&fixture.endpoint.socket), "クライアントが居るのに writer が止まった");

held.kill().unwrap();
until("the writer to stop", || gone(&fixture.endpoint.socket));
```

重要なのは最初の待機である。これがないと、ヘルパーが接続を終える前に probe を落とすことがある。そうなると writer は数えるべきクライアントを失い、まだ存在しているはずだと検証しようとしているテストの前でカウントダウンを始める。この待機が保証するのはカーネルがヘルパーを数え終えていることだけであるが、それによって probe を落とした後は、writer を支えているのがヘルパーだけになる。以降の記述はすべてこの前提の上に成り立っている。

## 結論

プロセス自身の寿命は、ユーザーコードで維持できる参照カウントではない。問題となるのは、ユーザーコードが実行されない瞬間と、デストラクタが越えられない境界である。誰が writer になるか、writer がいつ終了するか。その両方はカーネルに委ねるべきである。カーネルは自身の都合で、すでにそのカウントを保持している。
