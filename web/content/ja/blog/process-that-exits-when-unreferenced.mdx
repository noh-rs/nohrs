writer は一つしか許さないが、reader は何プロセスからでも同時に読めるストアがある。[tantivy](https://github.com/quickwit-oss/tantivy) のインデックスがそうであり、LMDB の書き込みトランザクションもそうである。単一 writer ロックで守られたストアは、どれも同じ性質を持つ。

この制約がかかるのはプロセス単位ではなくストア単位である。一つのインデックスを開くプロセスがマシン上にいくつあろうと、writer になれるのはそのうち一つだけである。どれが writer になるかを決めるのは、プロセスの内部にある何かではなく、ディスク上のファイルに対して取られるロックである。

writer をどれか一つのプロセスの中に置くと、そのプロセスが動いている限り、そのプロセスがストアを独占する。他のプロセスは書き込めない。アプリの二つ目のインスタンスも、書き込みを行うコマンドラインツールも拒否される。これを避けるには、writer に専用のプロセスを与えるしかない。

ではそのプロセスは<strong>いつ終了すればよいのか</strong>。これがこの記事の主題である。

## 必要とされている間だけ存在させる

writer は、必要とされている間だけ存在すべきである。ログイン時に自動起動すべきではないし、launchd や systemd に登録すべきでもない。登録されて常駐するプロセスは、止めたくなったときに人間が探し出して止めてやらねばならないからである。

これはつまり参照カウントである。writer を必要としている主体一つにつきカウントを一つ持ち、ゼロになった時点でプロセスを終了する。同じアドレス空間の中でなら `Arc` で済む話で、Rust なら三行で書ける。問題は、ここで数えたい相手が別のプロセスにいることである。

## デストラクタでは届かない

別のプロセスを数えるとなると `Drop` は使えない。デストラクタ、`defer`、`finally` といった言語レベルの後始末機構も、同じ理由で使えない。理由は二つある。

1. <strong>`Drop` は `SIGKILL` では実行されない。</strong>OOM killer に殺されたときも、segfault のときも、電源が落ちたときも実行されない。クライアントが行儀よく終了したときにしか正しくないカウントは、それが最も必要な場面で狂う。writer を永久に走らせ続けてしまうのは、まさに後始末のコードが一行も走らなかったときだからである。
2. <strong>`Drop` はアドレス空間を越えない。</strong>クライアント側のデストラクタから writer 側のカウンタを減らすことはできない。クライアントが終了時に何をしようと、writer がそれを知るには、プロセス境界を越える仕組みが別に要る。

すぐ思いつく代替案は、どれもうまくいかない。

- <strong>ハートビート</strong>はプロセス境界を越えられるが、確実な事実をタイムアウト付きの推測に変える。死んだことが分かるのはタイムアウトが過ぎた後であり、単に忙しいだけのクライアントは死んだものと見なされる。
- <strong>クライアントの pid を監視する方法</strong>は pid の再利用と競合する。pid を確認してから判断を下すまでの間に、その番号が別のプロセスのものになっているかもしれない。
- <strong>`PR_SET_PDEATHSIG`</strong> は<em>親</em>が死んだときに子へシグナルを送る機構で、ここで必要なものとは向きが逆である。writer は自分を起動したプロセスより長く生きなければならない。起動元が一秒後に終了する単発のコマンドであっても、writer は次の呼び出しのために残る必要がある。

## カーネルがすでに数えている

このカウントは、カーネルがすでに持っている。しかもちょうど必要な意味で持っている。

<strong>unix socket の接続は、カーネルが参照カウントしている。</strong>数えているのはプロセスではなく fd である。プロセスが終了すれば、どんな終わり方であっても、ユーザーコードが一行も走らなくても、その fd はカーネルが閉じる。片側の最後の fd が消えた時点で、反対側は end-of-stream を読む。

つまりカーネルが数えているのは「生きているクライアントの数」ではなく「保持されている接続の数」である。一つのプロセスが接続を二本開けば二と数えられ、子が引き継いだ fd は、それを開いたプロセスが終了した後も接続を保つ。必要なのは後者である。writer が起動されたままでいる理由は、誰かが接続を保持していることだからである。この数は `kill -9` に対しても正しい。維持を求められているユーザー空間のコードが、どこにもないからである。

同じことは socket 以外にも言える。この記事の要点はここにある。<strong>あるプロセスの生存を別のプロセスが知らなければならないときは、カーネルが維持しているものを使う。</strong>開いた接続、アドバイザリロック、読み側が EOF を返すパイプ。言語側の型は、その上に被せる RAII のラッパーでしかない。プロセスが終了時に忘れず実行しなければならない処理は、いつか実行されないからである。

考え方は `Arc` のままで、カウントの実体だけをカーネルに預ける。以下がその実装である。

## lease の形

writer 側の lease はごく普通の RAII 型である。設計上重要なのは一点だけで、<strong>接続を処理する関数がこれを値で受け取る</strong>ことである。

```rust
/// 接続が終わるまで、クライアント一つを処理する。
///
/// `lease` は値で受け取り、どこにも渡さない。この関数が返ること自体が解放になる。
/// 接続を終わらせるのはたいていクライアント側の socket が閉じることで、
/// クライアントがどんな終わり方をしても、閉じるのはカーネルである。
/// こちら側から終わらせる場合もある。`Stop` を受けたときと、
/// 読まれなくなった相手への書き込みが失敗したときである。
fn serve_client(&self, stream: UnixStream, lease: Lease) -> Result<()> {
    let mut reader = BufReader::new(stream);
    while let Some(request) = read_frame::<Request>(&mut reader)? {
        // ...
    }
    Ok(()) // ここで lease が落ちる
}
```

lease を持たずにクライアントを処理する方法はないし、処理を終えた後も持ち続ける方法もない。解放を忘れることは起こらない。解放は手順ではなく、関数から返ること自体だからである。

## 参照カウントを `Arc` にしない理由

実際には猶予時間が要る。シェルスクリプトの中で二つのコマンドが一秒違いで走ったときに、writer の起動コストを二度払う必要はない。そこで writer は、最後のクライアントが去ってから一定時間待ってから終了する。ここでは 90 秒にしている。

これで「最後の drop で終了する」という形は崩れる。`Arc` はカウントがゼロになったことを伝えて消えるだけで、それをきっかけに動き出したものを後から取り消す手段は残らない。猶予時間の途中でやってきたクライアントはカウントダウンを止めなければならないが、止めるための手がかりがない。

そこで、カウントと、それがゼロになった時刻とを自分で持つ。

```rust
struct State {
    live: usize,
    /// 最後にカウントがゼロになった時刻。誰かが lease を持っている間は `None`。
    /// 保留中のシャットダウンをクライアントが取り消せるのは、これがあるからである。
    idle_since: Option<Instant>,
    /// `release` が立てるフラグ。カウントがいくつであっても待機を打ち切る。
    /// `Stop` がこれを使う。猶予時間を待たない唯一の出口である。
    released: bool,
}
```

待機はポーリングではなく条件変数で行うので、何もしていない writer を残しておくコストはない。

```rust
pub fn wait_until_idle(&self) {
    let mut state = self.lock();
    loop {
        if state.released {
            return;
        }
        match state.idle_since {
            // 誰かが接続している。状況が変わるまで行うことはない。
            None => state = self.wait(state),
            Some(since) => match self.grace.checked_sub(since.elapsed()) {
                None => return,
                Some(remaining) => state = self.wait_for(state, remaining),
            },
        }
    }
}
```

これを独立した型として切り出しておくと、<strong>socket を一切使わずにテストできる</strong>。lease を取り、手放し、待機がいつ返るかを確かめればよい。

## どちらが writer になるかを決める

writer の一生のもう一方の端、つまり起動する側も同じ形をしている。writer を必要とするプロセスが同時に二つあれば、両方が起動を試み、負けた方は引き下がらなければならない。

この勝敗を socket ファイルの有無で決めることはできない。socket ファイルは、それを作ったプロセスより長く残るからである。ファイルがあることは、そこで誰かが待ち受けていることを意味しない。pid ファイルはもっと悪い。pid の再利用がまた問題になるからで、そこに書かれた番号は、読んだ時点では別のプロセスのものになっているかもしれない。

代わりに、writer が生きている間ずっと保持する<strong>アドバイザリロック (`flock`)</strong> で決める。カーネルがこのロックを解放するのは、それを参照する最後の fd が閉じられたときである。ここでも数えているのはファイルではなく fd なので、子が引き継いだ複製が残っていれば、ロックを取ったプロセスが去った後もロックは保たれる。ロックを取って誰にも渡さないプロセスにとっては、ロックが解放される瞬間は自分が死んだ瞬間であり、どう死んだかは問われない。socket とまったく同じ規則である。偶然ではなく、この設計の両端が同じカウント、つまり一つの対象を参照する fd の数に乗っているからで、数えているのも同じカーネルである。

アドバイザリロックは、ロックを取りに行ったプロセスどうしの間でしか意味を持たない。ここではそれで十分である。決めたいのはどちらが writer になるかであり、候補は両方ともロックを取りに来ているからである。pid ファイルは読むたびに疑う必要があるが、ロックは古くならない。

writer になることと、writer をやめること。writer の一生の両端は、どちらも同じ理由でカーネルに任せている。

## writer を経由しない reader

単一 writer の設計を成り立たせているのは、一つの不変条件である。これは最適化ではなく設計上の選択である。<strong>reader は writer を経由しない。</strong>

読み取りにロックは要らないので、reader はストアを直接開く。何プロセスから同時に開いても構わない。socket が運ぶのは書き込み要求、状態の問い合わせ、commit の通知だけで、クエリが流れることはない。

これによって writer は<em>依存先ではなく、あってもなくてもよいインフラ</em>になる。writer が止まっていても、固まっていても、バージョンが一つ古くても、読み取りは答えを返す。本来よりいくらか古いストアから返すだけである。存在すら知らないバックグラウンドプロセスの不調が原因でエラーになる、という失敗はそもそも起こらない。同じ理由で、writer プロセスは読み取り経路に一切手を触れずに、段階的に導入することも、後から取り外すこともできる。

## 予告なく死んだ場合をテストする

肝心のテストはプロセスの中では書けない。確かめたいのは、終了時に一行もコードが走らなかった場合の挙動だからである。そこで、接続して眠るだけの小さなヘルパーバイナリを用意し、テストはこれを kill する。

```rust
let mut held = Command::new(env!("CARGO_BIN_EXE_holds_a_connection"))
    .arg(&fixture.endpoint.socket)
    .spawn()
    .unwrap();
until("the killable client to be counted", || {
    probe.status().unwrap().clients == Some(2)
});

// ここから先、writer を支えているのは kill される側のみである。
drop(probe);
std::thread::sleep(GRACE * 2);
assert!(!gone(&fixture.endpoint.socket), "クライアントが居るのに writer が止まった");

held.kill().unwrap();
until("the writer to stop", || gone(&fixture.endpoint.socket));
```

重要なのは最初の待機である。これがないと、ヘルパーが接続を終える前に probe を落とすことがある。そうなると writer は数えるべきクライアントを失い、まだ生きているはずだと確かめようとしているテストのそばからカウントダウンを始める。この待機が保証するのはカーネルがヘルパーを数え終えていることだけだが、それによって probe を落とした後は、writer を支えているのがヘルパーだけになる。この後の行はすべてその前提の上に書かれている。

## 結論

プロセス自身の寿命は、ユーザーコードで維持できる参照カウントではない。問題になる瞬間はユーザーコードが走らない瞬間であり、問題になる境界はデストラクタが越えられない境界である。誰が writer になるか、writer がいつ終了するか。その両方はカーネルに任せるのがよい。カーネルは自分の都合で、すでにそのカウントを取っている。
