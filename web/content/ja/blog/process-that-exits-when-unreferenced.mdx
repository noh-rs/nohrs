一つの [tantivy](https://github.com/quickwit-oss/tantivy) インデックスに対して、writer は同時に一つしか存在できない。二つ目の `IndexWriter` を作ろうとすると、tantivy 自身がインデックスのディレクトリに置く `.tantivy-writer.lock` がこれを拒否する。これはファイルロックであるから、制約はプロセスの内側で閉じていない。同じインデックスを開くプロセスがマシン上にいくつあろうと、writer になれるのはそのうち一つだけである。

reader の側に制限はない。読み取りはロックを取らないため、何プロセスから同時に開いてもよい。単一 writer・複数 reader というこの形は tantivy に限らない。LMDB の書き込みトランザクションをはじめ、単一 writer ロックで守られたストアはいずれも同じ性質を持つ。

したがって設計上の問題は、writer をどのプロセスに置くかということになる。nohrs には検索に入る経路が三つある。explorer の検索バー、グローバルホットキーで開くランチャー、ターミナルから打つ `noh search` である。三つとも同じインデックスを読み、三つとも最新であることを前提にしている。

そしてこの三つは寿命を共有しない。ランチャーは他のアプリが前面にいても呼び出せ、explorer のウィンドウを一枚も開かずランチャーだけを常駐させる起動の仕方もある。`noh search` はアプリのプロセスの外にいて、打たれた瞬間にだけ動く。

writer を GUI アプリの中に置くと、この食い違いがそのまま検索結果に出る。アプリが動いている間はアプリがインデックスを占有するので、`noh index build` は書き込めず、二つ目のインスタンスも起動できない。アプリを終了すれば書けるようになるが、今度はアプリが動いていない間はインデックスが一切更新されない。ターミナルで `noh search` を打つのは、たいていアプリを開いていないときである。ランチャーの側にも同じ問題がある。ホットキーがいつ押されるか分からない以上、返す結果の鮮度が、そのときウィンドウを開いていたかどうかに左右されてはならない。

そこで、writer だけを持つプロセスを別に立てる。nohrs ではこれが `nohrs-indexd` である。インストールもサービス登録もせず、writer を必要とした最初のプロセスがその場で起動する。

残るのは、そのプロセスをいつ終了させるかという問題である。ログイン時に起動して常駐させるなら考えることはないが、それは避けたい。登録されて常駐するプロセスは、必要でなくなっても自分では消えず、止めるには人手が要る。

## 終了条件は参照カウントになる

writer を必要としているクライアントを数え、ゼロになった時点で終了する。同一プロセスの中でなら `Arc` がこれをやる。問題は、数えるべきクライアントが別のプロセスにいることである。

`Drop` はこれに使えない。理由は二つあり、どちらも決定的である。

1. <strong>`Drop` は `SIGKILL` では実行されない。</strong>OOM killer による終了でも、segfault でも、電源断でも実行されない。クライアントが正常に終了したときにしか正しくないカウントは、それが最も必要な場面で狂う。writer が誰にも必要とされないまま走り続ける事態は、まさに後始末のコードが実行されなかったときに起こるからである。
2. <strong>`Drop` はアドレス空間を越えない。</strong>クライアント側のデストラクタから、別プロセスにあるカウンタを減らすことはできない。クライアントが終了時に何を実行しようと、writer 側がそれを知るには、プロセス境界を越える経路が別に必要である。

境界を越える経路として容易に思いつくものは、いずれも別の問題を持ち込む。

- <strong>ハートビート</strong>は、確実な事実をタイムアウト付きの推測に変える。クライアントが消えたことが判明するのはタイムアウトが経過した後であり、その間 writer は不要なまま走り続ける。逆にタイムアウトを短くすれば、処理が重いだけのクライアントが消えたものと判定される。
- <strong>クライアントの pid の監視</strong>は pid の再利用と競合する。pid を確認してから判断を下すまでの間に、その番号が別のプロセスのものになっている可能性がある。
- <strong>`PR_SET_PDEATHSIG`</strong> は<em>親</em>が終了したときに子へシグナルを送る機構であり、ここで必要なものとは向きが逆である。writer は自分を起動したプロセスより長く存続しなければならない。起動元が一秒後に終了する単発のコマンドであっても、writer は次の呼び出しのために残る必要がある。

## fd が指しているもの

ここから先はカーネルの持ち物の話になるので、先に前提を整理する。以降の設計は全体がファイルディスクリプタ (fd) の構造の上に乗っている。

fd はプロセスごとの小さな整数である。プロセスが `open` や `socket` を呼ぶと、カーネルはそのプロセスの fd テーブルで空いている枠のうち最も番号の小さいものを使い、その番号を返す。0、1、2 は標準入力・標準出力・標準エラー出力が占めているので、起動直後のプロセスが最初にファイルを開けば 3 が返る。

番号そのものは目印にすぎない。ファイルの現在位置、開いたときのフラグ、そして対象 (inode、socket、パイプ) への参照を持っているのは、枠が指す先にある<strong>オープンファイル記述 (open file description)</strong> の方である。整理すると三段になる。

```
fd テーブル (プロセスごと)    オープンファイル記述 (カーネル全体)    対象
  3 ───────────────────────▶  位置 0 / 読み取り ─────────────────▶ inode 12345
  4 ───────────────────────▶  位置 0 / 読み取り ─────────────────▶ inode 12345
```

同じファイルを二度 `open` すると、この図のように fd も記述も別々になる。位置は記述ごとに一つあるので、片方から読んでももう片方の位置は動かない。

```rust
// 同じファイルを二度開く。`open` が二回呼ばれるので、記述も二つできる。
// 行末の `?` は、失敗したらその場で呼び出し元に返す、という意味である。
let mut first = File::open("index.json")?;
let mut second = File::open("index.json")?;

// 10 バイト分の入れ物を用意し、`first` から先頭 10 バイトを読む。
// `first` の記述の位置が 0 から 10 に進む。
let mut buffer = [0u8; 10];
first.read_exact(&mut buffer)?;

// `second` の記述の位置は 0 のままである。したがってこれも、
// 同じ先頭 10 バイトを読む。
second.read_exact(&mut buffer)?;
```

`dup` で複製した fd と、`fork` した子が引き継いだ fd は、これと違って<strong>同じオープンファイル記述を指す</strong>。Rust の標準ライブラリで `dup` を呼ぶのは `try_clone` である。

```rust
let mut first = File::open("index.json")?;

// `try_clone` は `dup` を呼ぶ。fd は二本になるが、記述は一つのままである。
let mut second = first.try_clone()?;

let mut buffer = [0u8; 10];
first.read_exact(&mut buffer)?;

// 位置は一つしかなく、それがもう 10 に進んでいる。
// したがってこれは 11 バイト目から読む。
second.read_exact(&mut buffer)?;
```

nohrs の daemon もこれを使っている。一つの接続に対して読む側のスレッドと書く側のスレッドを立てるため、socket の fd を複製する。

```rust
// `stream` は接続一つ。`writing_end` は、同じ接続を指す二本目の fd である。
let writing_end = stream.try_clone()?;
```

`try_clone` が作るのは、同じ記述を指す二本目の fd である。接続はこれによって増えない。二本の fd は同じ一つの接続の、同じ相手に向いている。

そしてカーネルは、一つのオープンファイル記述を指す fd が何本あるかを数えている。最後の一本が閉じられた時点で、その記述は破棄される。上の daemon で `stream` だけを閉じても接続は生きたままであり、`writing_end` も閉じられて初めて切れる。

プロセスが終了すると、そのプロセスの fd テーブルにある枠はカーネルがすべて閉じる。`exit` を呼んだ場合も、panic で落ちた場合も、`SIGKILL` で殺された場合も同じである。ユーザーコードが一行も走らなくても閉じられるのは、閉じているのがカーネルだからである。

## unix socket が運ぶもの

daemon とクライアントは別々のプロセスである。変数を直接見せ合うことはできないので、両者がやり取りするには、カーネルが用意している経路を通すことになる。nohrs が使っているのは unix socket である。

unix socket は、同じマシンの上のプロセス二つをつなぐ双方向のバイトの通り道である。TCP の socket とほぼ同じ呼び出しで扱えるが、ネットワークを一切通らない。IP アドレスとポート番号の代わりに、待ち合わせ場所をファイルシステム上のパスで指定する。nohrs が使うのは次のパスである。

```
/run/user/1000/nohrs/indexd.sock
```

このパスを `ls -l` で見ると、行の先頭が `s` になっている。通常のファイルなら `-`、ディレクトリなら `d` が出る位置であり、`s` が socket を表す。

```
srwxr-xr-x 1 shuya shuya 0 Sep 17 11:04 /run/user/1000/nohrs/indexd.sock
```

サイズは常に 0 である。このファイルに中身が書き込まれることはなく、やり取りされるバイトがディスクに触れることもない。このパスが果たしているのは、どこで待ち合わせるかを両者に伝える役割だけである。

### 待ち受ける側と、繋ぎに行く側

daemon 側が使う呼び出しは三つある。

1. <strong>`bind`</strong> — 上のパスを自分の socket に結び付ける。これでファイルシステムにそのパスが現れ、クライアントから見つけられる状態になる。
2. <strong>`listen`</strong> — 接続を受け付ける、とカーネルに伝える。到着した接続は、カーネルが待ち行列に積んでおいてくれる。
3. <strong>`accept`</strong> — 待ち行列から接続を一つ取り出す。何も積まれていなければ、到着するまでここで止まる。

クライアント側は `connect` を一度呼ぶだけで、その引数が `bind` された同じパスである。

Rust の標準ライブラリでは、`bind` と `listen` がまとめて `UnixListener::bind` になっている。

```rust
// パスに結び付け、待ち受けを始める。
let listener = UnixListener::bind("/run/user/1000/nohrs/indexd.sock")?;

// `incoming()` は `accept` を繰り返し呼ぶ。接続が来るまでループは
// ここで止まり、一つ来るたびに一周する。
for connection in listener.incoming() {
    // `connection` が、クライアント一人分の接続である。
    // (`accept` は失敗しうるので、実際には `Result` に包まれて返る。)
}
```

ここで重要なのは、<strong>`accept` が返すのは新しい fd である</strong>という点である。`listener` が持っている fd は待ち受け専用で、これを相手にして読み書きはできない。読み書きできる fd は、接続が一つ成立するたびに一本ずつ増える。

クライアントが三つ繋がっている daemon は、次の四本の fd を持っていることになる。

```
待ち受け用の fd 3 ──▶ /run/user/1000/nohrs/indexd.sock
接続用の fd     4 ──▶ クライアント A
接続用の fd     5 ──▶ クライアント B
接続用の fd     6 ──▶ クライアント C
```

クライアントを一人ずつ数えられるのは、この形のおかげである。比較のために、同じパスに名前付きパイプ (FIFO) を置いた場合を考える。FIFO はバイトの通り道を一本だけ作るもので、これを開いたプロセスが何人いようと、書き込まれたバイトは全部が同じ一本に流れ込む。読む側からは、どのプロセスから来たバイトなのかも、いま何人が開いているのかも分からない。socket は接続ごとに fd を分けるので、その本数がそのままクライアントの数になる。

### 接続の上を流れるもの

nohrs がこの通り道に流しているのは、改行で区切った JSON である。クライアントは接続すると最初にプロトコルの版を名乗り、daemon がそれに答える。

```
→ {"request":"hello","version":1}
← {"response":"welcome","version":1,"pid":4121}
→ {"request":"refresh","full":false}
```

一行が一つのメッセージであり、長さを示す前置きを持たない。区切りが改行だけなので、`nc -U /run/user/1000/nohrs/indexd.sock` で繋げば、流れているものをそのまま目で読める。

### socket ファイルは生死を表さない

socket ファイルには、後の設計に関わる性質が一つある。<strong>それを作ったプロセスが終了しても、パスは消えずに残る</strong>。`kill -9` された daemon の socket ファイルは、誰も待ち受けていない状態のままファイルシステムに残り続ける。このファイルがあることは、そこに daemon がいることを意味しない。

### 相手が消えたことをどう知るか

ある接続について、片側のプロセスが持っていた fd がすべて閉じられたとする。このとき、反対側でその接続から `read` を呼ぶと、<strong>0 バイトを読んで成功する</strong>。

これが end-of-stream である。失敗ではないので、エラーを調べても何も出てこない。0 バイトという返り値そのものが、この接続にはもうデータが来ない、という通知になっている。

daemon がクライアントの消滅を知るのは、これによってである。そして、クライアントが `close` を呼んで終了した場合も、`main` から戻った場合も、`SIGKILL` で殺された場合も、fd を閉じるのはカーネルなのだから、daemon 側が受け取るものは同じ 0 バイトである。クライアントがどう終わったかを daemon は区別できず、区別する必要もない。

## カーネルは接続をすでに数えている

クライアント一人を一つの接続として扱えば、必要だったカウントはそのままカーネルの数える fd の本数になる。daemon の accept ループはこうなっている。

```rust
for connection in listener.incoming() {
    let stream = connection?;

    // lease を一つ取る。daemon が数えているクライアントが一人増える。
    let lease = daemon.leases.take();

    // `daemon` への参照を一つ増やす。下のスレッドへ渡す分である。
    let daemon = Arc::clone(&daemon);

    // 接続ごとにスレッドを一つ立てる。読み待ちで止まっているだけの
    // スレッドが専有するのは、スタック一本分である。
    std::thread::spawn(move || {
        if let Err(error) = daemon.serve_client(stream, lease) {
            tracing::debug!("client gone: {error:#}");
        }
    });
}
```

`std::thread::spawn` に渡している `move || { ... }` は、引数を取らない無名の関数である。頭に付いた `move` が、この無名関数が `stream` と `lease` を<strong>所有権ごと受け取る</strong>という指定にあたる。この二つはループ側の持ち物ではなくなり、新しいスレッドのものになる。

受け取った先が `serve_client` である。ここが設計の要点なので、周辺を削って形だけを見る。

```rust
// `lease: Lease` を値で受け取っている。lease はこの関数のものになり、
// 呼び出し元の手元には残らない。
fn serve_client(&self, stream: UnixStream, lease: Lease) -> Result<()> {
    let mut reader = BufReader::new(stream);

    // `read_frame` は一行読んで、メッセージを一つ返す。
    // 相手側の fd がすべて閉じられて読むものがなくなると `None` を返す。
    // `while let Some(...)` は、`Some` が返る間だけ回るループなので、
    // そこでこのループが終わる。
    while let Some(request) = read_frame(&mut reader)? {
        // ... 要求に答え、返事を書き戻す ...
    }

    Ok(())
    // 関数から返ると `lease` は有効な範囲から外れ、`Drop` が走って
    // カウントが一つ減る。
}
```

クライアントが `kill -9` で殺されたとき、実際に起きることを順に書くとこうなる。

1. カーネルがそのプロセスの fd を閉じる。クライアント側のコードは一行も実行されていない。
2. その接続を参照する fd が他に残っていなければ、これでクライアント側の最後の fd が閉じられる。子が引き継いだ fd が残っていれば、そちらが閉じるまで接続は開いたままである。daemon が数えているのは保持されている接続なので、これは意図した挙動である。
3. クライアント側の最後の fd が閉じられた時点で、daemon 側のスレッドが `read_frame` で読んでいた先が end-of-stream になる。読みかけのものが何もなければ `None` が返る。一行の途中で切れていれば、読めた分は壊れた JSON なので、`read_frame` はエラーを返す。
4. どちらであっても `while` のループは終わり、`serve_client` が返る。実際の `serve_client` は、読み取りの結果がエラーであっても、それをそのまま投げ返す前に後始末を済ませる。したがってエラーで終わった接続も、通る経路は同じである。
5. 引数として持っていた `lease` が有効な範囲から外れ、`Drop` が走ってカウントが一つ減る。

カウントを維持するために、クライアント側で実行されなければならない処理は存在しない。これが、終了の仕方を問わないという性質の出どころである。

ここで Rust が担っているのは形の部分だけである。lease を値で受け取っているため、lease を持たずにクライアントを処理する方法はなく、処理を終えた後も持ち続ける方法もない。解放は関数から返ること自体であり、忘れる余地がない。

一般化すると、<strong>あるプロセスの生存を別のプロセスが知る必要があるときは、カーネルが維持しているものを使う</strong>ということになる。開いた接続、アドバイザリロック、読み側が EOF を返すパイプがこれにあたる。プロセスが終了時に忘れず実行しなければならない処理は、いつか実行されない。

## 猶予時間と、その取り消し

カウントがゼロになった瞬間に終了させると、実用上の無駄が出る。シェルスクリプトの中で二つのコマンドが一秒の間隔で実行されれば、daemon の起動とインデックスを開く処理を二度払うことになる。そこで、最後のクライアントが去ってから一定時間待ち、その間に誰も来なければ終了する。nohrs では 90 秒としている。

この猶予時間のために、カウントは `Arc` では済まなくなる。必要な情報が二つあるからである。<strong>カウントがゼロになった時刻</strong>と、<strong>カウントダウンを取り消す手段</strong>である。`Arc` はゼロになった時点で一度だけデストラクタを走らせて消えるので、そこから先に何も残さない。猶予時間中に新しいクライアントが来ても、進行中のカウントダウンに手を伸ばす経路がない。

そこで、この二つを明示的に保持する。

```rust
struct State {
    /// いま lease を持っているクライアントの数。
    live: usize,
    /// 最後に `live` がゼロになった時刻。誰かが持っている間は `None`。
    /// `Option` なので、「まだゼロになっていない」と「いつゼロになったか」を
    /// 一つの値で表せる。
    idle_since: Option<Instant>,
    /// `release` が立てるフラグ。`live` がいくつであっても待機を打ち切る。
    released: bool,
}
```

待機側はこの状態を読んで分岐する。使っているのは条件変数である。これは、状態が変わるまでこのスレッドを寝かせておいてくれ、とカーネルに頼む仕組みで、一定時間ごとに状態を見に行くポーリングと違い、寝ている間は CPU を使わない。他のスレッドが状態を書き換えて起こすまで、待っているスレッドは一切走らない。何もしていない daemon を置いておくコストがないのは、これによる。

```rust
pub fn wait_until_idle(&self) {
    // `state` は、`Mutex` の中身を触っている間だけ有効な借用である。
    let mut state = self.lock();

    loop {
        // `Request::Stop` が来ていた。カウントに関わらず、ここで終わる。
        if state.released {
            return;
        }

        match state.idle_since {
            // 誰か繋がっている。状態が変わって起こされるまで待つ。
            None => state = self.wait(state),

            // 誰も繋がっていない。ゼロになった時刻からの経過時間を
            // 猶予時間から引く。
            Some(since) => match self.grace.checked_sub(since.elapsed()) {
                // 引くと負になった。つまり猶予時間は尽きている。終了する。
                None => return,

                // 残りがある。その分だけ待つ。途中で誰か来れば起こされ、
                // そのときには `idle_since` が `None` に戻っているので、
                // ループの先頭からやり直しになる。
                Some(remaining) => state = self.wait_for(state, remaining),
            },
        }
    }
}
```

`state = self.wait(state)` が代入の形になっているのは、待つ間は `Mutex` を手放さなければならないからである。中身を握ったまま眠れば、状態を書き換えて起こす側が握れず、誰も動けなくなる。`wait` は受け取った借用をいったん手放して眠り、起こされたところで握り直して返す。だから渡して受け取り直す形になる。

カウントを上げ下げする側は、状態を書き換えてから条件変数を叩く。`take` は `live` を増やして `idle_since` を `None` に戻し、`Lease` の `Drop` は `live` を減らし、ゼロになったときだけ `idle_since` に現在時刻を入れる。

猶予時間中に到来したクライアントがカウントダウンを取り消す処理は、これだけで済んでいる。そのクライアントは通常どおり `take` を呼び、`idle_since` が `None` に戻り、条件変数で起こされた待機側が無期限の待機に戻る。取り消しのための経路は存在しない。カウントが上がったことの帰結として起きる。

状態の初期値も同じ枠組みで決まる。`Leases::new` は `live` をゼロに、`idle_since` を<strong>現在時刻</strong>にして始める。つまり daemon は起動した瞬間から猶予時間のカウントダウンに入っている。こうしておかないと、起動したものの誰一人接続してこなかった daemon が、カウントがゼロのまま無期限に居座ることになる。

`released` は `Request::Stop` のためにある。`noh index stop` は、他のクライアントがまだ繋がっていても、猶予時間の残りを待たずに daemon を終了させる。これはカウントの問題ではないので、カウントとは独立したフラグで待機を打ち切る。

## どちらのプロセスが daemon になるか

writer を必要とするプロセスが同時に二つあれば、両方が daemon を起動しようとする。どちらか一方だけが daemon にならなければならない。

この判定を socket ファイルの有無で行うことはできない。socket ファイルは、それを作成したプロセスが死んでも残る。ファイルが存在することは、そこで誰かが待ち受けていることを意味しない。pid ファイルはさらに悪く、pid の再利用を持ち込む。

判定には `flock` を使う。これは、ファイルを一つ決めておき、それに対するロックを取れた者を勝ちとする仕組みである。付いている性質が二つある。

- <strong>アドバイザリ (advisory)</strong> である。ロックを取りに来たプロセス同士だけを拘束し、ファイルへの読み書きそのものはカーネルが止めない。ロックを見ずに書きに来たプロセスは素通りする。ここではロックを取りに来るのが daemon になろうとするプロセスだけなので、これで足りる。
- <strong>非ブロッキング</strong>で試せる。すでに誰かが持っていた場合に、空くまで待たずその場で返れ、という指定ができる。

```rust
pub fn take(path: &Path) -> Result<Option<Self>> {
    // ロックを掛ける相手として存在するだけのファイル。中身は読み書きしない。
    let file = File::options()
        .create(true).read(true).write(true).truncate(false)
        .open(path)?;

    match flock(&file, FlockOperation::NonBlockingLockExclusive) {
        // 取れた。このプロセスが daemon になる。
        Ok(()) => Ok(Some(Self { _file: file })),

        // 生きている daemon がすでに持っている。呼び出し元はそちらに
        // 話しかけに行くので、これは失敗として扱わない。
        Err(Errno::WOULDBLOCK) => Ok(None),

        // それ以外は本当の失敗である。
        Err(error) => Err(error.into()),
    }
}
```

返り値が `Result<Option<Self>>` という二重の入れ子になっているのは、結果が三通りあるからである。ロックが取れた、生きている daemon が持っていた、呼び出し自体が失敗した、の三つで、上の `match` の三つの腕がそれぞれに対応する。二つ目を失敗として返さないのは、それが想定どおりの結果だからである。

返している `Self { _file: file }` が、開いたファイルをそのまま抱えていることにも意味がある。ロックはこのファイルに結び付いているので、ファイルを閉じればロックも外れる。ロックを持ち続けるには、ファイルを開いたままにしておくよりほかにない。名前が `_file` なのは、この値を後で読むことがなく、ただ持っていること自体が仕事だからである。

このロックの解放を決めるのはカーネルである。`flock` のロックはプロセスに属していない。属しているのは、先に見たオープンファイル記述の方である。したがって解放されるのは、その記述を参照する最後の fd が閉じられた時点になる。プロセスが終了すれば fd は閉じられるので、終了の仕方によらずロックは解放される。socket の接続と同じ規則であり、どちらも一つの対象を参照する fd の本数を数えている。

ロックの持ち主がオープンファイル記述であることには、もう一つ帰結がある。`dup` や `fork` で複製された fd は同じ記述を指すので、ロックを共有する。一方、同じファイルを改めて `open` すれば別の記述になるので、同じプロセスであってもロックは取れない。二重起動の判定を同一プロセス内で試しても正しく弾かれるのは、このためである。

daemon 側の起動手順は、この判定を軸に組み立てられる。

1. ロックを取る。取れなければ、すでに daemon が動いているか、クライアントが起動処理の途中でロックを握っている。どちらであっても自分は daemon にならず、何もせずに終了する。
2. ロックが取れたということは、この手順に従う daemon が listen していないということである。ロックはアドバイザリなので、保証が及ぶのはロックを取りに行くプロセスの範囲までであり、socket を bind するのがこの手順を通る `serve` だけであることによって成り立っている。したがって socket ファイルが残っていれば、それは死んだ daemon が残したものである。bind に失敗するので、先に消す。
3. bind して accept ループに入る。ロックはプロセスが終了するまで持ち続ける。

クライアント側も同じロックを使うが、目的が違う。

1. まず接続を試みる。成功すればそれで終わりである。
2. 失敗したらロックを試す。取れなければ、別のクライアントが daemon を起動しようとしているか、接続に失敗した後で daemon が起動している。自分では何も起動せず、接続の再試行に移る。
3. 取れたら、そのロックを手放してから daemon を起動する。ロックを一生持つのは子プロセスの側だからである。
4. 5 秒を上限に、間隔を広げながら接続を再試行する。

2 の判定がないと、同時に到着した n 個のクライアントがそれぞれ daemon を起動し、そのうち一つを除く全部が 1 でロックを取れずに即座に終了することになる。結果は正しいが、fork の分だけ無駄である。

この判定は無駄を減らすものであって、なくすものではない。3 でクライアントがロックを手放してから子プロセスがそれを取るまでの短い間、ロックは誰も持っていない。その隙に別のクライアントが 2 を通過すれば、daemon は二つ起動される。それでも daemon になれるのは 1 でロックを取れた側だけであり、もう一方はそこで終了する。ロックが保証しているのは、writer を持つプロセスが同時に二つ存在しないことであって、余分なプロセスが一度も起動されないことではない。

## reader は daemon を経由しない

socket が運ぶのは、書き込み要求、状態の問い合わせ、commit の通知だけである。検索クエリは一度も流れない。reader はインデックスを直接開く。読み取りにロックが要らない以上、daemon を経由させる理由がないからである。

この一点が、daemon の位置づけを決めている。daemon が停止していても、応答しなくなっていても、バージョンが一つ古くても、検索は答えを返す。本来よりいくらか古いインデックスから返すだけである。存在すら知らないバックグラウンドプロセスの不調が原因で検索がエラーになる、という失敗は起こらない。同じ理由により、writer プロセスは読み取り経路を一切変更せずに導入でき、必要なら取り外せる。

## 予告のない終了を検証する

要となるテストはプロセス内では記述できない。確かめたいのは、クライアントが終了時に一行もコードを実行しなかった場合の挙動だからである。そこで、接続したまま待機するだけのヘルパーバイナリを用意し、テストはこれを `kill` する。

```rust
// `env!("CARGO_BIN_EXE_...")` は、cargo がテスト用に用意したヘルパー
// バイナリのパスに、コンパイル時に置き換わる。`.unwrap()` は、失敗して
// いたらそこでテストを落とす、という意味である。
let mut held = Command::new(env!("CARGO_BIN_EXE_holds_a_connection"))
    .arg(&fixture.endpoint.socket)
    .spawn()
    .unwrap();

// `until` は、渡した条件が真になるまで短い間隔で確かめ続ける補助関数。
// `|| { ... }` はその条件を書いた無名関数で、`until` がこれを繰り返し呼ぶ。
// ここで待っているのは、daemon の数えるクライアントが 2 になることである。
// 2 は、状態を問い合わせている probe 自身の接続と、ヘルパーの接続である。
until("the killable client to be counted", || {
    probe.status().unwrap().clients == Some(2)
});

// probe を落とす。ここから先、daemon を支えているのはヘルパーだけになる。
drop(probe);

// 猶予時間の二倍待っても、daemon は生きていなければならない。
std::thread::sleep(GRACE * 2);
assert!(!gone(&fixture.endpoint.socket), "クライアントが居るのに daemon が止まった");

// ヘルパーを `SIGKILL` で殺す。ヘルパー側の後始末のコードは一行も走らない。
held.kill().unwrap();

// それでも daemon は、自分から終了しなければならない。
until("the writer to stop", || gone(&fixture.endpoint.socket));
```

最初の待機が重要である。`clients` が 2 になるのを待っているのは、状態を問い合わせている probe 自身の接続とヘルパーの接続で 2 だからであり、ここを通過した時点で<strong>カーネルがヘルパーを数え終えている</strong>ことが確定する。

この待機がないと、ヘルパーが接続する前に probe を落としてしまう場合がある。そうなると daemon のクライアントは一つもなくなり、daemon はカウントダウンを始める。その後の `sleep` と assert は、daemon がまだ生きていることをヘルパーの存在によって確かめるつもりで書かれているので、実際には何も確かめないまま通過しうる。最初の待機は、以降の記述が乗っている前提そのものである。

## 結論

プロセス自身の寿命は、ユーザーコードで維持できる参照カウントではない。問題となるのは、ユーザーコードが実行されない瞬間と、デストラクタが越えられない境界である。どちらが writer になるか、writer がいつ終了するかは、カーネルがすでに数えているものに委ねられる。Rust が受け持つのは、その上に RAII の形を与えることである。
