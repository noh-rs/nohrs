writer は一つしか許さないが、reader は何プロセスからでも同時に読めるストアがある。[tantivy](https://github.com/quickwit-oss/tantivy) のインデックスがそうであり、LMDB の書き込みトランザクションもそうである。単一 writer ロックで守られたストアは、どれも同じ性質を持つ。

この制約はプロセス単位ではなくストア単位で効く。一つのインデックスを開くプロセスがマシン上にいくつあろうと、writer になれるのはそのうち一つだけである。どれが writer になるかを決めるのは、プロセスの内部にある何かではなく、ディスク上のファイルに対して取られるロックである。

writer をどれか一つのプロセスの中に置けば、そのプロセスが動いている限りストアはその専有物になる。他のプロセスは書き込めない。アプリの二つ目のインスタンスも、書き込みを行うコマンドラインツールも、いずれも拒否される。逃れる道は、writer に専用のプロセスを与えることである。

そこで問いが生じる。<strong>そのプロセスはいつ終了するのか。</strong>

## 要件を参照カウントとして述べる

writer は、必要とされている間だけ存在すべきである。ログイン時に自動起動すべきではないし、launchd や systemd に登録すべきでもない。登録されて常駐するプロセスは、止めたくなったときに人間が探し出して止めてやらねばならないからである。

これは参照カウントそのものである。writer を必要としている主体一つにつきカウントを一つ持ち、ゼロになった時点でプロセスを終了する。同一アドレス空間の中でなら `Arc` で済む話で、Rust なら三行で書ける。

プロセスを跨ぐと、そうはいかない。

## デストラクタが届かない範囲

`Drop` には——デストラクタ、`defer`、`finally` など、言語レベルの後始末機構すべてに共通して——二つの制約がある。この二つが結論を決めてしまう。

1. <strong>`Drop` は `SIGKILL` では実行されない。</strong>OOM killer に殺されたときも、segfault のときも、電源が落ちたときも実行されない。クライアントが行儀よく終了したときにしか正しくないカウントは、<strong>それが最も必要な場面でこそ狂う</strong>。writer を永久に走らせ続けてしまうのは、まさに後始末のコードが一行も走らなかったときだからである。
2. <strong>`Drop` はアドレス空間を越えない。</strong>クライアント側のデストラクタから writer 側のカウンタを減らすことはできない。クライアントが終了時に何をしようと、writer がそれを知るには、プロセス境界を越える何らかの仕組みが要る。

すぐ思いつく代替案は、どれもどこかで破綻する。

- <strong>ハートビート</strong>はプロセス境界を越えられるが、確実な事実をタイムアウト付きの推測に変えてしまう。死んだことが分かるのはタイムアウトが経過した後であり、単に忙しいだけのクライアントは死んだものと見なされる。
- <strong>クライアントの pid を監視する方法</strong>は pid の再利用と競合する。pid を確認してから判断を下すまでの間に、その番号が別のプロセスのものになっているかもしれない。
- <strong>`PR_SET_PDEATHSIG`</strong> は<em>親</em>が死んだときに子へシグナルを送る機構で、ここで欲しいものとは向きが逆である。writer は自分を起動したプロセスより長く生きなければならない。起動元が一秒後に終了する単発のコマンドであっても、writer は次の呼び出しのために残る必要がある。

## カーネルがすでに数えているもの

カーネルはすでにこのカウントを持っている。しかも、ここで欲しいのとまったく同じ意味で。

<strong>unix socket の接続は、カーネルが参照カウントしている。</strong>数えているのはプロセスではなく fd である。プロセスが終了すれば——どんな終わり方であれ、ユーザーコードが一行も走らない場合を含めて——その fd はカーネルが閉じ、片側の最後の fd が消えた時点で反対側は end-of-stream を読む。

したがってカーネルが数えているのは「生きているクライアントの数」ではなく「保持されている接続の数」である。一つのプロセスが接続を二本開けば二と数えられ、子が引き継いだ fd は、それを開いたプロセスが終了した後も接続を保つ。そして欲しいのは後者である。writer が起動されたままでいる理由は、誰かが接続を保持していることだからである。この数は `kill -9` に対しても正しい。<strong>その維持を求められているユーザー空間のコードが、どこにもない</strong>からである。

これは socket に限った話ではない。本記事の要点はここにある。<strong>あるプロセスの生存を別のプロセスが知らねばならないときは、カーネルが維持しているものを使う</strong>——開いた接続、アドバイザリロック、読み側が EOF を返すパイプ。言語側の型は、その上に被せる RAII の皮でしかない。プロセスが終了時に忘れず実行しなければならない処理は、いつか実行されないからである。

モデルは `Arc`、実体はカーネル、そして Rust がその両方に形を与える。

## lease の形

writer 側の lease はごく普通の RAII 型である。設計として効いているのは一点だけで、<strong>接続を処理する関数がこれを値で受け取る</strong>ことである。

```rust
/// 接続が終わるまで、クライアント一つを処理する。
///
/// `lease` は値で受け取り、どこにも渡さない。この関数が返ること自体が解放である。
/// 接続を終わらせるのはたいていクライアント側の socket が閉じることで、
/// クライアントがどんな終わり方をしても、閉じるのはカーネルである。
/// こちら側から終わらせる場合もある。`Stop` を受けたときと、
/// 読まれなくなった相手への書き込みが失敗したときである。
fn serve_client(&self, stream: UnixStream, lease: Lease) -> Result<()> {
    let mut reader = BufReader::new(stream);
    while let Some(request) = read_frame::<Request>(&mut reader)? {
        // ...
    }
    Ok(()) // ここで lease が落ちる
}
```

lease を持たずにクライアントを処理する方法はないし、処理を終えた後も持ち続ける方法もない。解放は忘れうる手順ではない。そもそも手順ではないからである。

## 参照カウントを `Arc` としない理由

実際には猶予時間が要る。シェルスクリプトの中で二つのコマンドが一秒違いで走ったときに、writer の起動コストを二度払う必要はない。そこで writer は、最後のクライアントが去ってから一定時間待ってから終了する。ここでは 90 秒にしている。

これで「最後の drop で終了する」という形は崩れる。`Arc` は<strong>カウントがゼロになったことを伝えて消えるだけで、それをきっかけに動き出したものを取り消す手段は残らない</strong>。猶予時間中にやってきたクライアントはカウントダウンを止めなければならないが、止めるための取っかかりがない。

そこで、カウントと、それがゼロになった時刻とを明示的に持つ。

```rust
struct State {
    live: usize,
    /// 最後にカウントがゼロになった時刻。誰かが lease を持っている間は `None`。
    /// 保留中のシャットダウンをクライアントが取り消せるのは、これがあるためである。
    idle_since: Option<Instant>,
    /// `release` が立てるフラグ。カウントの値によらず待機を打ち切る。
    /// `Stop` がこれを使う。猶予時間を待たない唯一の出口である。
    released: bool,
}
```

待機はポーリングではなく条件変数で行うので、何もしていない writer を残しておくコストはない。

```rust
pub fn wait_until_idle(&self) {
    let mut state = self.lock();
    loop {
        if state.released {
            return;
        }
        match state.idle_since {
            // 誰かが接続している。状況が変わるまで行うことはない。
            None => state = self.wait(state),
            Some(since) => match self.grace.checked_sub(since.elapsed()) {
                None => return,
                Some(remaining) => state = self.wait_for(state, remaining),
            },
        }
    }
}
```

これを独立した型として切り出しておくと、<strong>socket を一切使わずにテストできる</strong>。lease を取り、手放し、待機がいつ返るかを確かめればよい。

## writer の座を巡る競合

writer の一生のもう一方の端、つまり起動の側も同じ形をしている。writer を必要とするプロセスが同時に二つあれば、両方が起動を試み、負けた方は引き下がらなければならない。

この勝敗を socket ファイルの有無で決めることはできない。socket ファイルは、それを作ったプロセスより長く残るからである。ファイルが存在することは、そこで誰かが待ち受けていることを何も意味しない。pid ファイルはもっと悪い。pid の再利用がまた顔を出すからで、そこに書かれた番号は、読んだ時点では別のプロセスのものになっているかもしれない。

代わりに、writer が生きている間ずっと保持する<strong>アドバイザリロック (`flock`)</strong> で決める。カーネルがこのロックを解放するのは、それを参照する最後の fd が閉じられたときである。ここでも数えているのはファイルではなく fd なので、子が引き継いだ複製が残っていれば、ロックを取ったプロセスが去った後もロックは保たれる。ロックを取り、それを誰にも渡さないプロセスにとっては、解放される瞬間は自分が死んだ瞬間であり、どう死んだかは問われない。これは socket とまったく同じ規則で、偶然ではない。この設計の両端は同じカウント——一つの対象を参照する fd の数——に乗っており、数えているのも同じカーネルである。

アドバイザリとは、ロックを取りに行ったプロセスしか拘束しないという意味だが、ここではそれで十分である。決めたいのはどちらが writer になるかであり、候補は両方ともロックを取りに来ているからである。この範囲では、pid ファイルは常に疑ってかからねばならないのに対し、ロックが古びることはない。

writer であることの始まりと終わり——writer になること、writer をやめること——は、どちらもカーネルが維持している事実に乗っている。理由は両方とも同じである。

## writer を経由しない reader

単一 writer の設計では、一つの不変条件がほとんどの仕事をしている。そしてこれは最適化ではなく設計上の選択である。<strong>reader は writer を経由しない。</strong>

読み取りにロックは要らないので、reader はストアを直接開く。何プロセスから同時に開いても構わない。socket が運ぶのは書き込み要求、状態の問い合わせ、commit の通知だけで、クエリが流れることはない。

これによって writer は<em>依存先ではなく、あってもなくてもよいインフラ</em>になる。writer が止まっていても、固まっていても、バージョンが一つ古くても、読み取りは答えを返す。本来よりいくらか古いストアから返すだけである。存在すら知らないバックグラウンドプロセスの不調が理由でエラーになる、という失敗はそもそも起こらない。同じ理由で、writer プロセスは読み取り経路に一切手を触れずに段階的に導入でき、また取り外せる。

## 予告なき終了の検証

肝心のテストはプロセス内では書けない。確かめたいのは<strong>終了時に一行もコードが走らなかった場合</strong>の挙動だからである。そこで、接続して眠るだけの小さなヘルパーバイナリを用意し、テストはこれを kill する。

```rust
let mut held = Command::new(env!("CARGO_BIN_EXE_holds_a_connection"))
    .arg(&fixture.endpoint.socket)
    .spawn()
    .unwrap();
until("the killable client to be counted", || {
    probe.status().unwrap().clients == Some(2)
});

// ここから先、writer を支えているのは kill される側のみである。
drop(probe);
std::thread::sleep(GRACE * 2);
assert!(!gone(&fixture.endpoint.socket), "クライアントが居るのに writer が止まった");

held.kill().unwrap();
until("the writer to stop", || gone(&fixture.endpoint.socket));
```

効いているのは最初の待機である。これがないと、ヘルパーが接続を終える前に probe を落としてしまいうる。そうなると writer は数えるべきクライアントを失い、「まだ生きているはずだ」と検証しようとしているテストの目の前でカウントダウンを始める。この待機が保証するのは<strong>カーネルがヘルパーを数え終えている</strong>ことだけだが、それによって probe を落とした後は、writer を支えているのがヘルパーだけになる。以降の記述はこの前提の上に成り立っている。

## 規則

プロセス自身の寿命は、ユーザーコードで維持できる参照カウントではない。問題になる瞬間はユーザーコードが走らない瞬間であり、問題になる境界はデストラクタが越えられない境界である。その両端——誰が writer になるか、writer がいつ終了するか——はカーネルの領分である。カーネルは自分の都合で、すでにそのカウントを取っている。
