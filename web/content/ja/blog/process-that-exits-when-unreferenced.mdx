書き手を一つしか許さず、読み手は何プロセスからでも同時に読めるストアがある。[tantivy](https://github.com/quickwit-oss/tantivy) のインデックスがそうであり、LMDB の書き込みトランザクションも、単一書き手ロックで守られたものは何であれそうである。この制約はプロセス単位ではなく大域的である。マシン上の全プロセスを通じて書き手は一つであり、それを決めるのは、いずれかのプロセスの内部に持たれる何かではなく、書き手たちの間でディスク上のファイルに対して取られるロックである。

書き手をいずれかの参加者の内部に置けば、その参加者が稼働している限りストアはその専有物となる。他のものは書き込めず、二つ目のインスタンスは拒否され、書き込みを行うコマンドラインツールも拒否される。逃れる道は、書き手に固有のプロセスを与えることである。

そこで問いが生じる。<strong>そのプロセスはいつ終了するのか。</strong>

## 要件を参照カウントとして述べる

書き手は、必要とされている間は存在し、そうでなければ存在すべきではない。ログイン時に起動すべきではなく、launchd や systemd への登録も行うべきではない。存在するために登録を要するプロセスとは、人の手で探し出し停止させることを要するプロセスだからである。

この形は参照カウントである。関心を持つ主体一つにつきカウント一つを持たせ、ゼロに達した時点でプロセスを終了する。同一アドレス空間においては `Arc` であり、その全体が Rust で三行である。

プロセスを跨ぐ場合は成立しない。

## デストラクタが届かない範囲

`Drop` について——そしてデストラクタ、`defer`、`finally`、その他あらゆる言語レベルの巻き戻し機構について——二つの事実がこれを決定する。

1. <strong>`Drop` は `SIGKILL` では実行されない。</strong>OOM killer、segfault、電源断のいずれでも実行されない。クライアントが秩序立った終了を行った場合にのみ正しいカウントとは、<strong>まさにそれを要する場面で誤っている</strong>カウントである。書き手を永久に走らせ続ける事態とは、まさに後始末のコードが一行も実行されない事態だからである。
2. <strong>`Drop` はアドレス空間を越えない。</strong>クライアント側のデストラクタは、書き手側のカウンタを減算できない。クライアントが退出時に何を実行しようと、書き手がそれを知るのはプロセス境界を越える何かを通じてのみである。

直截な修復案はいずれもどこかで破綻する。

- <strong>ハートビート</strong>は境界を越えるが、厳密な事実をタイムアウト付きの推測に変える。死が認識されるのはタイムアウトの経過後であり、単に多忙なだけのクライアントは死んだものとして扱われる。
- <strong>クライアントの pid の監視</strong>は pid の再利用と競合する。確認から結論までの間に、その番号は別のものに属しうる。
- <strong>`PR_SET_PDEATHSIG`</strong> は、<em>親</em>の死に際して子へシグナルを届ける機構であり、ここでは向きが逆である。書き手は起動元より長く存続せねばならない。起動元は一秒後に終了する一回限りのコマンドでありうるが、書き手は次の呼び出しのために残ることが求められる。

## カーネルがすでに数えているもの

カーネルはすでにこのカウントを維持している。しかもまさにこの意味論においてである。

<strong>unix socket の接続はカーネルが参照カウントしている。</strong>数えられているのはプロセスではなく fd である。プロセスが終了すれば——終了の態様を問わず、ユーザーコードが一行も走らない場合を含めて——その fd は閉じられ、その側の最後の fd が消えた時点で反対側は end-of-stream を読む。したがって数えられている量は「生存しているクライアント数」ではなく「保持されている接続数」である。一つのプロセスが接続を二本開けば二と数えられ、子が引き継いだ fd は、それを開いたプロセスの終了後も接続を保つ。そもそも要るのは後者の量である——書き手が起動されたままである理由はそれだからである——そしてその量は `kill -9` に対して正しい。<strong>ユーザー空間のいずれの主体も、その維持を要求されていない</strong>ためである。

これは socket に限らず一般化でき、本記事から持ち帰るに足る規則はここにある。<strong>あるプロセスの生存を別のプロセスが観測せねばならない場合、カーネルが維持するものを用いる</strong>——開いた接続、アドバイザリロック、読み側が EOF を報告するパイプ——そして言語側の型は、その上の RAII の顔以上のものであってはならない。プロセスが退出時に忘れずに行わねばならない処理とは、時として行えない処理である。

すなわち、モデルは `Arc`、実装はカーネルであり、Rust が双方に形を与える。

## lease の形

書き手側の lease は通常の RAII 型である。設計上の判断として作用しているのは一点、<strong>接続を処理する関数が値で受け取る</strong>ことである。

```rust
/// 接続一本を、その接続が終わるまで処理する。
///
/// `lease` は値で受け取り、他へ渡さない。この関数が返ることが解放である。
/// 接続を終わらせるのは通常クライアント側の socket が閉じることであり、
/// クライアントがどのような終わり方をしようと、閉じるのはカーネルである。
/// こちら側から終わらせることもある。`Stop` の処理と、読まれなくなった
/// 相手への書き込みがそれである。
fn serve_client(&self, stream: UnixStream, lease: Lease) -> Result<()> {
    let mut reader = BufReader::new(stream);
    while let Some(request) = read_frame::<Request>(&mut reader)? {
        // ...
    }
    Ok(()) // ここで lease が落ちる
}
```

lease を保持せずにクライアントを処理する方法はなく、処理の終了後に保持し続ける方法もない。解放は遺漏しうる手順ではない。そもそも手順ではないためである。

## 参照カウントを `Arc` としない理由

実務上は猶予時間が要る。シェルスクリプト中の二つのコマンドが一秒の間隔で実行されたとき、書き手の起動の代償を二度支払うべきではない。そこで書き手は、最後のクライアントが去ってから待機したうえで終了する。ここでは 90 秒である。

これは「最後の drop で終了する」という定式を崩す。`Arc` は<strong>カウントがゼロに達した事実のみを伝えて消滅し、その時点で動き出したものを呼び戻す手段ごと失う</strong>。猶予時間中に到来したクライアントはカウントダウンを中止させる必要があるが、中止のための手掛かりが残っていない。

したがって、カウントとゼロに達した時刻を明示的に保持する。

```rust
struct State {
    live: usize,
    /// 最後にカウントがゼロになった時刻。誰かが lease を持っている間は `None`。
    /// 保留中のシャットダウンをクライアントが取り消せるのは、これがあるため。
    idle_since: Option<Instant>,
    /// `release` が立てる。カウントが何であれ待機を終わらせる。`Stop` が
    /// これであり、猶予時間を待たない唯一の出口である。
    released: bool,
}
```

また待機はポーリングではなく条件変数によるため、処理のない書き手を保持する代償はない。

```rust
pub fn wait_until_idle(&self) {
    let mut state = self.lock();
    loop {
        if state.released {
            return;
        }
        match state.idle_since {
            // 誰かが接続している。状況が変わるまで行うことはない。
            None => state = self.wait(state),
            Some(since) => match self.grace.checked_sub(since.elapsed()) {
                None => return,
                Some(remaining) => state = self.wait_for(state, remaining),
            },
        }
    }
}
```

これを独立した型として切り出すことの利点は、<strong>socket を一切用いずに試験できる</strong>点にある。lease を取得し、解放し、待機が復帰する時点を検証すれば足りる。

## 書き手の座を得る側の競合

書き手の生涯のもう一方の端も同じ形をしている。書き手を要求するプロセスが二つあれば、双方が起動を試み、敗れた側は引き下がらねばならない。

この判定を socket ファイルの有無に求めることはできない。socket ファイルは、それを作成したプロセスより長く残存するためである。ファイルが見つかったことは、そこで誰かが待ち受けていることを何も意味しない。pid ファイルはさらに悪い。pid の再利用を再び持ち込むためであり、そこに書かれた番号は、読まれた時点では全く別のものに属しうる。

代わりに、書き手の生存中を通じて保持される<strong>アドバイザリロック (`flock`)</strong> が判定する。このロックもまた、保持者の死の態様を問わずカーネルが解放する。アドバイザリとは、ロックを取りに行ったプロセスのみを拘束するという意味であるが、ここではそれが対象の全体である。調停されるのはどちらが書き手となるかであり、双方とも取りに行っているためである。その範囲において、pid ファイルは疑ってかかることを要するが、ロックが古びることはない。

書き手の存在の両端——書き手となること、書き手であることをやめること——はいずれも、カーネルが維持する事実に依拠する。理由はどちらも同一である。

## 書き手を経由しない読み手

単一書き手の設計では、一つの不変条件がほとんどの作用を担っている。そしてそれは最適化ではなく選択である。<strong>読み手は書き手を経由しない。</strong>

読み取りにロックは要らないため、読み手はストアを直接開く。同時に任意の数のプロセスから開いてよい。socket が運ぶのは書き込み要求、状態の問い合わせ、および commit された旨の通知であり、クエリを運ぶことはない。

これが書き手を<em>依存ではなく任意のインフラ</em>たらしめている。停止していても、応答不能でも、バージョンが一つ古くとも、読み取りは答える。本来より幾分古いストアからではあるが、答える。読み手がその存在を認識してもいないバックグラウンドプロセスの不調を理由にエラーを受け取る、という失敗様態は存在しない。同じ条件により、読み取り経路に一切触れることなく、書き手プロセスの段階的な導入も撤去も可能である。

## 予告なき終了の検証

要点となる試験はプロセス内では記述できない。主張の対象が<strong>退出時に一行のコードも実行できなかった場合</strong>の挙動だからである。そこで、接続して休眠するのみの小さなヘルパーバイナリを用意し、試験はこれを kill する。

```rust
let mut held = Command::new(env!("CARGO_BIN_EXE_holds_a_connection"))
    .arg(&fixture.endpoint.socket)
    .spawn()
    .unwrap();
until("the killable client to be counted", || {
    probe.status().unwrap().clients == Some(2)
});

// ここから先、書き手を支えているのは kill される側のみである。
drop(probe);
std::thread::sleep(GRACE * 2);
assert!(!gone(&fixture.endpoint.socket), "クライアントが居るのに書き手が止まった");

held.kill().unwrap();
until("the writer to stop", || gone(&fixture.endpoint.socket));
```

作用しているのは最初の待機である。これを欠くと、ヘルパーが接続を終える前に probe を落としうる。その時点で書き手は数えるべきクライアントを失い、まだ存在するはずだと検証しようとしている試験を前にカウントダウンを始める。待機が確立するのは<strong>カーネルがヘルパーを数え終えている</strong>という一点であり、それによって probe を落とした以降、書き手を支えているのはヘルパーのみとなる。以降の記述はその前提の上に立っている。

## 規則

プロセス自身の寿命は、ユーザーコードが維持できる参照カウントではない。問題となる瞬間はユーザーコードが走らない瞬間であり、問題となる境界はデストラクタが越えない境界である。その両端——誰が書き手となるか、書き手がいつ終了するか——はカーネルに属する。カーネルは自身の都合で、すでにそのカウントを取っている。
