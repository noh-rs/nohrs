あるプログラムがファイルを開いているとします。`open` が返した番号、すなわちディスクリプタを保持しており、その番号はディスク上の特定の一つの実体を曖昧さなく指しています。ここで、そのプログラムが当の実体を削除しようとします。

できません。該当する呼び出しが用意されていないからではなく、<strong>その要求が何も指定していない</strong>からです。理由を辿ると、パスとは何か、ディスクリプタとは何か、そして「削除」が実際には何を対象とする操作なのか、という三点の整理になります。

以下の記述はすべて Linux 6.18 上で実際に測定したものであり、出力はそのまま引用しています。

## 名前と実体

ディレクトリは、ファイルを格納する容器ではありません。名前と番号という二列からなる表です。

この番号を inode 番号と呼びます。ファイルについての実質的な情報——サイズ、パーミッション、更新時刻、そして内容を保持するブロックへの参照——はすべて inode 側にあります。ディレクトリにあるのは名前だけです。inode は自身の名前を知らず、自身を名指しているディレクトリへ遡る手がかりも持ちません。

以降 inode 番号を同一性の判定に用いるため、一点だけ断っておきます。inode 番号が一意なのは単一のファイルシステム内に限られ、解放された番号は再利用されます。本記事の実行例はすべて単一ファイルシステム上の一つのディレクトリ内で完結しており、その範囲では番号だけの比較で妥当です。実際にエントリを比較するコードはデバイス ID と組にした `(st_dev, st_ino)` を用います。本記事の末尾で扱う後始末の処理が保持しているのも、この組です。

ファイルを削除するシステムコールが `delete` ではなく `unlink` と呼ばれるのは、この構造のためです。取り除かれるのはリンク、すなわち表の一行です。実体が回収されるのは、それを参照するものが一つも残らなくなった時点——どのディレクトリにもエントリがなく、かつ実行中のプロセスが開いたディスクリプタもメモリマッピングも保持していない状態——に限られます。

一つの実体に二つの名前を作り、その一方にディスクリプタを開いたうえで、その名前を削除するプログラムの出力です。

```text
one/a   inode=1908771
one/b   inode=1908771
fd 3    inode=1908771

unlink('one/a')
  one/b exists   True
  one/b contents 'payload'
  fd 3 inode    1908771
  fd 3 read     b'payload'
```

## 「ディスクリプタを削除する」が意味をなさない理由

ここで、上の二つの事実を重ね合わせます。

ディスクリプタが指すのは実体です。`unlink` が取り除くのは名前です。上の実行では実体に二つの名前があり、`unlink` の後は一つになりました。仮に「このディスクリプタを削除せよ」と要求されていたなら、カーネルは誰も指定していない問いに答えねばなりません。<strong>どちらの名前を、という問いです。</strong>

これは API の不足ではありません。<strong>操作として解決しない要求</strong>です。三つの名前を持つ実体は、一つ削除した時点で「四分の三だけ削除された」のではありませんし、ディスクリプタの削除を「すべての名前の削除」と解釈すべき根拠もありません。それは呼び出し元が要求したものとは別の、はるかに破壊的な操作です。

<Callout title="Linux に無いというだけの話ではありません">
FreeBSD には `funlinkat` があります。ただし、その実際の仕様を見る価値があります。この呼び出しは<strong>ディスクリプタと名前の両方</strong>を取り、その名前がディスクリプタと同一のファイルを指している場合に限り名前を削除します。つまり<strong>検証付きの unlink</strong> であって、ディスクリプタによる unlink ではありません。削除対象はやはり名前です。

Linux に相当するものはありません。`AT_EMPTY_PATH` 付きの `linkat` はディスクリプタに新しい名前を与えられるので抜け道に見えますが、`CAP_DAC_READ_SEARCH`——実質的に root——を要求するため、通常のプログラムからは利用できません。
</Callout>

したがって、Unix 系システムにおいて、あらゆる削除は何らかの名前を指定します。そして名前を指定するとは、パスを解決するということです。

<Callout title="Windows はこの問いを拒まずに答えている">
右の限定は実質的な意味を持っており、その例外は知っておく価値があります。Windows は開いているハンドルを通じた削除を許可します。`SetFileInformationByHandle` に `FileDispositionInfo` を指定する方法では、パスは一切渡さず、`DELETE` アクセス権付きで開いたハンドルのみを渡します。

これは反例というより、もうひとつの答え方です。曖昧さは Windows でも同様に存在し——NTFS にもハードリンクはあります——Windows はハンドルが「開かれた際の名前」を保持することでこれを解決しています。すなわち「このハンドルを削除する」は「その名前を削除する」を意味します。POSIX はこの対応関係を記録しないことを選んでおり、だからこそ同じ要求が一方では指示対象を持たず、他方では持ちます。ファイルシステムの法則ではなく、設計上の選択です。

（本記事の他の記述は Linux 6.18 上で実測したものですが、この項目は文書に基づく記述であり、実測ではありません。）
</Callout>

## パスが解決するものと、ディスクリプタが参照するもの

パスの解決は一連の検索です。`work/report` は、現在のディレクトリで `work` を引き、得られた inode がディレクトリであることを確認し、その中で `report` を引く、という手順を意味します。各成分は、<strong>その時点のファイルシステムの状態</strong>に対して解決されます。

カーネルは呼び出しをまたいでこの解決結果をキャッシュしません。同じパスに対する連続した二回の呼び出しは独立した二回の解決であり、その間にファイルシステムが変化しうることは妨げられていません。

ディスクリプタはこれと異なります。特定の inode を一度だけ解決し、以後それを保持します。上位にある名前が変更されても、参照先は変わりません。

ディレクトリに対してディスクリプタを保持したまま、そのディレクトリをパスの下から rename してみます。

```text
renamed work -> work2
  unlink('work/report')        -> ENOENT
  unlinkat(dirfd,'report')     -> ok
  work2/report gone            -> True
```

パスは解決しなくなりました。`work` はもう存在しません。ディスクリプタはその影響を受けていません。参照していたのは `work` という名前ではなく、ディレクトリそのものだからです。

## 別のプログラムが同じ名前を取得した場合

上の rename では呼び出しが失敗しただけです。条件を一つ変えると、データの損失が生じます。ディレクトリを退避させた後に、別のプログラムが元の名前で新しいディレクトリを作成した場合です。

```text
path  w/report   inode=1908833 'THEIRS'
dirfd report     inode=1908802 'mine'

unlink('w/report')   -> ok
  removed           'THEIRS'
  their file left?  False
```

プログラムが削除を要求したのは自分のファイルです。使用したパスは、確認した時点では正しいものでした。`unlink` が実行される時点では同じパスが別のプログラムのファイルを指しており、削除されたのはそちらです。

特殊な条件は何も必要としません。プログラムは API を誤用していません。パスによる削除を使用し、確認と呼び出しの間にファイルシステムが変化しただけです。これは<strong>パスを確認してから操作し、その間の競合に負ける</strong>という一群の不具合の一般形であり、カーネルが対象を指定する二つ目の方法を提供している理由でもあります。

## `*at` ファミリが短縮するもの

`openat`、`unlinkat`、`renameat`、`fstatat`、`mkdirat`。いずれもディレクトリディスクリプタと名前を取り、ルートからではなくそのディスクリプタを基点として名前を解決します。

得られるものは明確です。`a/b/c/d/report` をパスで解決すれば五回の検索が発生し、そのいずれもが呼び出しの合間に差し替えられうる。`a/b/c/d` のディスクリプタを保持して `report` を要求すれば、検索は<strong>一回</strong>です。最後の成分より上のすべてが、攻撃者にとっても——あるいは単に並行して動いている別のプログラムにとっても——差し替えの対象でなくなります。

一方で、その最後の一回は取り除けません。`unlinkat(dirfd, "report", 0)` は、固定されたディレクトリの中で `report` という名前を解決しますし、確認から削除までの一瞬に何かがそれを置き換えることは依然としてありえます。これが下限であり、最初の節と同じ下限です。削除は名前に対する操作だからです。

## `rmdir` にある非対称性

残った一回の検索によって、問題は元のままであるように見えます。ディレクトリに関してはほぼそうではなく、その理由は既存の一つの制約にあります。

`rmdir` は、中身のあるディレクトリの削除を拒否します。

```text
  rmdir('full')   -> ENOTEMPTY
  rmdir('empty')  -> ok
  unlink on a dir -> EISDIR
```

したがって、ツリーを安全に削除したいプログラムは次の手順を取れます。ディスクリプタを辿って降りながら中身を空にし——この過程で名前を参照することはありません——最後にはじめて `rmdir` に名前を渡す。その時点で、対象としているディレクトリは空です。

その最後の時点で名前が差し替えられていたとしても、`rmdir` が成功しうる相手は<strong>別の空ディレクトリ</strong>だけです。最悪の事態は「別のプログラムの中身の詰まったツリーを削除する」から「別のプログラムの空ディレクトリを削除する」に変わります。損失であることに変わりはありませんが、規模は実質的に小さく、しかも元から存在した制約から得られます。

ファイルにはこれに相当する制約がありません。`unlink` はその名前にあるものを削除します。窓はシステムコール二回分の幅で開いており、実在します。

<Callout title="正確に述べると">
これは窓を狭める操作であり、閉じる操作ではありません。「自分が作成したものだけを削除する」と称する設計は、Linux において、プラットフォームが提供していない保証を主張していることになります。残存する露出がどこにあるかを明記するほうが、成立しない保証を述べるよりも後の読み手の役に立ちます。
</Callout>

## フラグの選択

この一連の処理でエントリを開く操作は、`open(path, O_RDONLY)` とは少し異なります。四つのフラグが関与します。

- `O_DIRECTORY` — ディレクトリでなければ失敗させる。別のものを開いてから気づく事態を避けます
- `O_CLOEXEC` — ディスクリプタを子プロセスへ漏らさない
- `O_NOFOLLOW` — 最終成分のシンボリックリンクを辿らない
- `O_NONBLOCK` — 開く対象を待たずに `open` から復帰する

無条件に指定するのは `O_CLOEXEC` だけです。`O_DIRECTORY` は基点を開く処理に限って付けます。エントリを開く処理は、その型が何であるかを判定するために存在するからです。残りの二つには注意を要します。いずれも基点に付けるべきものに見えますが、どちらも該当せず、その理由は異なります。基点に付けた `O_NOFOLLOW` は正当な場合を妨げ、基点に付けた `O_NONBLOCK` は効果を持ちません。

まず `O_NOFOLLOW` から述べます。誤った位置に指定しても正しく見えるため、正確に述べる必要があります。

これは<strong>削除対象のエントリ</strong>に付けるものです。そこではリンクがその指す先の代わりになることを防ぎます。<strong>親ディレクトリに付けるものではありません</strong>。シンボリックリンク経由で到達するディレクトリに利用者が入っていることは正当にあり、その親を開くのを拒否しても保護にはならず、処理が放棄されるだけです。そこでリンクを辿ることが安全なのは別の理由によります。エントリに対する同一性の照合は、到達したディレクトリが実際にそのエントリを保持している場合にしか通らないからです。

<Callout title="フラグを足すと errno が変わる">
この点を検証する過程で、記録しておくべき結果が得られました。`O_NOFOLLOW` の下でシンボリックリンクに対して報告されるエラーは、`O_DIRECTORY` が同時に指定されているかどうかで変わります。

| flags | `adir` | `afile` | ディレクトリへのリンク | ファイルへのリンク | 切れたリンク |
| --- | --- | --- | --- | --- | --- |
| `O_RDONLY` | ok | ok | ok | ok | `ENOENT` |
| `O_RDONLY\|O_NOFOLLOW` | ok | ok | `ELOOP` | `ELOOP` | `ELOOP` |
| `O_RDONLY\|O_DIRECTORY` | ok | `ENOTDIR` | ok | `ENOTDIR` | `ENOENT` |
| `O_RDONLY\|O_DIRECTORY\|O_NOFOLLOW` | ok | `ENOTDIR` | `ENOTDIR` | `ENOTDIR` | `ENOTDIR` |

同一の条件——名前にシンボリックリンクがあり、`O_NOFOLLOW` が指定されている——が、二行目では `ELOOP`、四行目では `ENOTDIR` として報告されます。`O_DIRECTORY` が先に評価され、`O_NOFOLLOW` が考慮される前に結果が決まるためです。

「リンクだったので開かずに削除する」という場合を扱うコードは、したがって<strong>両方</strong>のエラーを受け付ける必要があります。片方しか挙げていないコメントは、規則ではなく特定の構成を記述していることになります。
</Callout>

`O_NONBLOCK` は別の方向で成立しません。基点に付ける理由づけ自体は妥当に見えます。その名前に FIFO が置かれていれば `open` 自体が、来ないかもしれない書き手を待つことになり、無期限に停止する処理は失敗する処理より望ましくない、というものです。理由づけは妥当ですが、結論は導かれません。すでに `O_DIRECTORY` が指定されているからです。

| フラグ | 書き手のいない FIFO |
| --- | --- |
| `O_RDONLY` | 無期限に停止 |
| `O_RDONLY\|O_NONBLOCK` | 開ける |
| `O_RDONLY\|O_DIRECTORY` | 即座に `ENOTDIR` |
| `O_RDONLY\|O_DIRECTORY\|O_NONBLOCK` | 即座に `ENOTDIR` |

一行目が危険、二行目がその対処、そして三行目は、その対処が別のフラグによって既に与えられていることを示しています。`O_DIRECTORY` は FIFO が停止しうるより先にそれを拒否するため、`O_DIRECTORY` を伴う open において `O_NONBLOCK` は効果を持ちません。

このフラグが該当するのは<strong>削除対象のエントリ</strong>を開く処理、すなわち `O_NOFOLLOW` を付けるべき対象と同じ処理です。そこでは `O_DIRECTORY` を指定できません。理由は上に述べたとおりで、対象はファイル・ディレクトリ・FIFO のいずれでもありえ、そのいずれであるかを判定することがその open の目的だからです。`O_DIRECTORY` はディレクトリ以外を拒否する形でその判定を打ち切ってしまいます。したがって保護は `O_NONBLOCK` が担うほかなく、そこでは復帰しない `open` を防ぐ唯一の手段となります。

以上より、二つのフラグは同じ open に付きます。根拠も共通で、基点はディレクトリであることが既知であるのに対し、エントリの型は開くまで不明だからです。

一点補足します。本記事の末尾でコードを全文引用しているためです。Nohrs の基点を開く処理は、それでも `O_NONBLOCK` を付けています。これは意図的であり、コメントに理由が記録されています。「隣のフラグがあるので冗長である」と「誤りである」は別の主張であり、上の議論が示したのは前者だけです。冗長なフラグの代償はビットマスクの 1 ビットであり、評価順序についての推論が誤っていた場合にそれが防ぐのは、貼り付け中に無期限に停止するファイルマネージャです。

もう一つ、依拠すべきでない値があります。`readdir` が返す `d_type` フィールド、すなわちエントリがディレクトリかどうかを示す値です。いくつかのファイルシステムはここに `DT_UNKNOWN` を入れ、確認は呼び出し側に委ねます。`openat` に `O_DIRECTORY` を渡すことがその確認にあたり、しかも同じ呼び出しで、再帰的な walk が次に必要とするディスクリプタが手に入ります。

## この問題が生じた事例

ここまでの内容は、このブログが属するファイルマネージャ [Nohrs](https://github.com/noh-rs/nohrs) に存在した不具合の説明です。対象は、貼り付けが途中で失敗した後に実行される後始末の処理です。

新しい名前へのコピーが途中で失敗した場合、書きかけの結果は除去しなければなりません。残す選択肢は成立しません。一覧上では未完成であることを示す手掛かりのない通常のディレクトリとして現れ、しかもその名前を占有するため、以後の再試行はすべて `report (2)` に配置されます。ただし後始末が除去してよいのは<strong>その操作自身が作成したもの</strong>だけであり、たまたま同じ名前を持つエントリであってはなりません。

以前の実装は、判断と除去を二つの独立した手順として実行していました。まず宛先がその操作自身の書きかけであることを `stat` で確認し、次に `remove_dir_all(dst)` を呼びます。この第二の呼び出しは `dst` を再びパス名から解決します。これは本記事で前述した隙間が、出荷済みのコードに存在していた状態です。二回の解決に対して判断は一回であり、その間に別の書き手がその名前へ別のエントリを置きえます。`stat` は所有を確認し、除去はその時点で存在するものを対象とします。

この窓は狭いものです。到達するには、一度その名前の獲得に失敗した別の書き手が、二つのシステムコールの間に同じ名前を獲得する必要があります。一定期間、パスによる除去が意図的な選択であった程度には狭いものでした。代替案——書きかけを保持して報告する——は競合状態ではなく確実に発生する問題だからです。

修正は `*at` の方式に従います。親ディレクトリを一度だけ解決してディスクリプタを保持し、以降はそれを基準に処理します。

```rust
let (parent, name) = parent_and_name(dst)?;
let parent = open_directory(parent)?;
// 獲得した当のエントリである間に限り、それを返す。
let Some(entry) = open_claimed(&parent, name, claimed)? else {
    return Ok(());
};
if entry.metadata()?.is_dir() {
    empty_dir(&entry)?;
    already_gone_is_fine(unlinkat(&parent, name, AtFlags::REMOVEDIR))?;
} else {
    already_gone_is_fine(unlinkat(&parent, name, AtFlags::empty()))?;
}
```

この中の三点は、選好ではなくここまでの議論からの帰結です。

- 同一性の照合は<strong>開いたディスクリプタを通じて</strong>行います。名前を介した照合では意味を持たず、同じ競合にさらされる検索が一つ増えるだけです
- 除去が返す `ENOENT` は成功として扱います。エントリが存在しないことは要求された結果そのものであり、別のプロセスが先に到達しただけです。これを失敗として扱えば、後始末が許容すべき競合を理由に後始末自体を放棄することになります
- 最後の `unlinkat` は依然として `name` を取ります。解決するのは一成分であり、その相手はこのコードが保持していて差し替えられないディレクトリです。この方式が提供できる範囲はここまでです

## 狭めることと、閉じること

表題の主張は「Linux に呼び出しが一つ足りない」よりも強いものです。「このディスクリプタを削除せよ」は機能要望ではありません。ディスクリプタが指すのは実体であり、削除が作用するのは名前であり、一つの実体は複数の名前を持ちうるからです。

そこから導かれる帰結は以下のとおりです。

- あらゆる削除は名前を解決する。したがってあらゆる削除に窓がある
- ディレクトリディスクリプタの保持は、最終成分を除く解決のすべてを取り除く
- ディレクトリについては、`rmdir` が空でない対象を拒否することで、その最後の窓が招きうる被害が小さくなる
- それ以外については窓は残る。適切な対応は、窓がどこにあるかを記録することである

この手法を解決策として提示することは正確ではありません。ディスクリプタを基点とした処理はパスを再解決するより厳密に優れており、`*at` 系の呼び出しはそのために存在します。ただし最後の検索はインタフェース設計上の見落としではなく、削除という操作の構成要素そのものです。
