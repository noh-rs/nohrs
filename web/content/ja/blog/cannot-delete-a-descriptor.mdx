あるプログラムがファイルを開いており、`open` が返した番号すなわちディスクリプタを保持しているとする。この番号はディスク上の特定の一つの実体を曖昧さなく指す。このプログラムが当の実体を削除しようとする場合を考える。

これは不可能である。該当する呼び出しが存在しないためではなく、<strong>その要求が何も指定していない</strong>ためである。理由の把握には、パスとは何か、ディスクリプタとは何か、そして削除が実際に何を対象とする操作なのか、という三点の整理を要する。

以下の記述はすべて Linux 6.18 上で測定したものであり、出力は得られたまま引用する。

## 名前と実体

ディレクトリは、ファイルを格納する容器ではない。名前と番号という二列からなる表である。

この番号を inode 番号と呼ぶ。ファイルについての実質的な情報——サイズ、パーミッション、更新時刻、および内容を保持するブロックへの参照——はすべて inode 側にある。ディレクトリが保持するのは名前のみである。inode は自身の名前を持たず、自身を名指すディレクトリへ遡る手がかりも持たない。

なお、以降 inode 番号を同一性の判定に用いる。inode 番号が一意であるのは単一のファイルシステム内に限られ、解放された番号は再利用される。本記事の実行例はいずれも単一ファイルシステム上の一つのディレクトリ内で完結しており、その範囲では番号のみの比較で妥当である。実際にエントリを比較するコードはデバイス ID と組にした `(st_dev, st_ino)` を用いる。本記事の末尾で扱う後始末の処理が保持するのもこの組である。

ファイルを削除するシステムコールが `delete` ではなく `unlink` と呼ばれるのは、この構造による。取り除かれるのはリンク、すなわち表の一行である。実体が回収されるのは、それを参照するものが一つも残らない時点——どのディレクトリにもエントリがなく、かつ実行中のプロセスが開いたディスクリプタもメモリマッピングも保持しない状態——に限られる。

以下は、一つの実体に二つの名前を作成し、その一方にディスクリプタを開いたうえで、当該の名前を削除するプログラムの出力である。

```text
one/a   inode=1908771
one/b   inode=1908771
fd 3    inode=1908771

unlink('one/a')
  one/b exists   True
  one/b contents 'payload'
  fd 3 inode    1908771
  fd 3 read     b'payload'
```

## 「ディスクリプタを削除する」が意味をなさない理由

上記の二つの事実を組み合わせる。

ディスクリプタが指すのは実体であり、`unlink` が取り除くのは名前である。上の実行では実体に二つの名前があり、`unlink` の後は一つとなった。仮に「このディスクリプタを削除せよ」と要求された場合、カーネルは<strong>どちらの名前を削除するか</strong>を決定せねばならないが、要求はその情報を含まない。

これは API の不足ではなく、<strong>操作として解決しない要求</strong>である。三つの名前を持つ実体は、一つを削除した時点で部分的に削除された状態にはならない。また、ディスクリプタの削除をすべての名前の削除と定義すれば、呼び出し元が要求したものより実質的に破壊的な操作となる。

<Callout title="Linux に存在しないという問題ではない">
FreeBSD には `funlinkat` が存在する。ただし、その仕様の確認を要する。この呼び出しは<strong>ディスクリプタと名前の両方</strong>を取り、当該の名前がディスクリプタと同一のファイルを指す場合に限り名前を削除する。すなわち<strong>検証付きの unlink</strong> であり、ディスクリプタによる unlink ではない。削除対象は名前である。

Linux に相当するものはない。`AT_EMPTY_PATH` 付きの `linkat` はディスクリプタに新しい名前を与えられるため回避手段に見えるが、`CAP_DAC_READ_SEARCH`——実質的に root——を要求するため、通常のプログラムからは利用できない。
</Callout>

したがって Unix 系システムにおいて、あらゆる削除は何らかの名前を指定する。そして名前の指定とは、パスの解決である。

<Callout title="Windows における別の解決">
上記の限定は実質的な意味を持つ。Windows は開いているハンドルを通じた削除を許可する。`SetFileInformationByHandle` に `FileDispositionInfo` を指定する方法では、パスは渡さず、`DELETE` アクセス権付きで開いたハンドルのみを渡す。

これは反例ではなく、同一の曖昧さに対する別の解決である。曖昧さは Windows にも存在し、NTFS もハードリンクを備える。Windows はハンドルが開かれた際の名前を保持することでこれを解決しており、ハンドルを通じた削除は当該の名前を削除する。POSIX はこの対応関係を記録しない。同一の要求が POSIX では指示対象を持たず Windows では持つのは、この差による。両者の差はファイルシステム一般の性質ではなく、設計上の決定である。

（本記事の他の記述は Linux 6.18 上で実測したものであるが、この項目は文書に基づく記述であり、実測ではない。）
</Callout>

## パスが解決するものと、ディスクリプタが参照するもの

パスの解決は一連の検索である。`work/report` は、現在のディレクトリで `work` を引き、得られた inode がディレクトリであることを確認し、その中で `report` を引く手順を意味する。各成分は<strong>その時点のファイルシステムの状態</strong>に対して解決される。

カーネルは呼び出しをまたいでこの解決結果をキャッシュしない。同じパスに対する連続した二回の呼び出しは独立した二回の解決であり、その間のファイルシステムの変化は妨げられない。

ディスクリプタはこれと異なる。特定の inode を一度だけ解決し、以後それを保持する。上位にある名前が変更されても参照先は変わらない。

ディレクトリに対してディスクリプタを保持したまま、当該ディレクトリをパスの下から rename した場合の出力を示す。

```text
renamed work -> work2
  unlink('work/report')        -> ENOENT
  unlinkat(dirfd,'report')     -> ok
  work2/report gone            -> True
```

パスは解決しなくなり、`work` は存在しない。ディスクリプタはその影響を受けない。参照していたのは `work` という名前ではなく、ディレクトリそのものだからである。

## 別のプログラムが同じ名前を取得した場合

上の rename では呼び出しが失敗したのみである。条件を一つ変えると、データの損失が生じる。ディレクトリを退避させた後に、別のプログラムが元の名前で新しいディレクトリを作成した場合である。

```text
path  w/report   inode=1908833 'THEIRS'
dirfd report     inode=1908802 'mine'

unlink('w/report')   -> ok
  removed           'THEIRS'
  their file left?  False
```

プログラムが削除を要求したのは自身のファイルである。使用したパスは、確認した時点では正しい。`unlink` の実行時点では同じパスが別のプログラムのファイルを指しており、削除されたのはそちらである。

特殊な条件は要しない。プログラムは API を誤用しておらず、パスによる削除を使用し、確認と呼び出しの間にファイルシステムが変化したのみである。これは<strong>パスを確認してから操作し、その間の競合に負ける</strong>という一群の不具合の一般形であり、カーネルが対象を指定する二つ目の方法を提供する理由でもある。

## `*at` ファミリが短縮するもの

`openat`、`unlinkat`、`renameat`、`fstatat`、`mkdirat`。いずれもディレクトリディスクリプタと名前を取り、ルートからではなく当該ディスクリプタを基点として名前を解決する。

効果は明確である。`a/b/c/d/report` をパスで解決すれば五回の検索が発生し、そのいずれもが呼び出しの合間に差し替えられうる。`a/b/c/d` のディスクリプタを保持して `report` を要求すれば、検索は<strong>一回</strong>である。最後の成分より上のすべてが、攻撃者にとっても、並行して動作する別のプログラムにとっても、差し替えの対象でなくなる。

一方で、その最後の一回は取り除けない。`unlinkat(dirfd, "report", 0)` は固定されたディレクトリの中で `report` という名前を解決し、確認から削除までの間に何かがそれを置き換える可能性は残る。これが下限であり、最初の節で述べた下限と同一である。削除は名前に対する操作だからである。

## `rmdir` にある非対称性

残った一回の検索により、問題は元のままであるように見える。ディレクトリに関してはほぼそうではなく、その理由は既存の一つの制約にある。

`rmdir` は、中身のあるディレクトリの削除を拒否する。

```text
  rmdir('full')   -> ENOTEMPTY
  rmdir('empty')  -> ok
  unlink on a dir -> EISDIR
```

したがって、ツリーを安全に削除するプログラムは次の手順を取りうる。ディスクリプタを辿って降りながら中身を空にし——この過程で名前を参照しない——最後に `rmdir` へ名前を渡す。その時点で対象のディレクトリは空である。

その最後の時点で名前が差し替えられていた場合でも、`rmdir` が成功しうる相手は<strong>別の空ディレクトリ</strong>に限られる。最悪の事態は「別のプログラムの中身の詰まったツリーの削除」から「別のプログラムの空ディレクトリの削除」に変わる。損失である点は変わらないが規模は実質的に小さく、かつ元から存在した制約から得られる。

ファイルにはこれに相当する制約がない。`unlink` は当該の名前にあるものを削除する。窓はシステムコール二回分の幅で開いており、実在する。

<Callout title="正確な定式化">
これは窓を狭める操作であり、閉じる操作ではない。「自分が作成したものだけを削除する」と称する設計は、Linux においてプラットフォームが提供しない保証を主張することになる。残存する露出の所在を明記するほうが、成立しない保証を述べるより後の読み手の役に立つ。
</Callout>

## フラグの選択

この一連の処理でエントリを開く操作は `open(path, O_RDONLY)` と異なる。四つのフラグが関与する。

- `O_DIRECTORY` — ディレクトリでなければ失敗させる。別の種類のものを開いた後に判明する事態を避ける
- `O_CLOEXEC` — ディスクリプタを子プロセスへ漏らさない
- `O_NOFOLLOW` — 最終成分のシンボリックリンクを辿らない
- `O_NONBLOCK` — 開く対象を待たずに `open` から復帰する

無条件に指定するのは `O_CLOEXEC` のみである。`O_DIRECTORY` は基点を開く処理に限って指定する。エントリを開く処理は、その型の判定を目的とするためである。残りの二つは注意を要する。いずれも基点に指定すべきものに見えるが該当せず、その理由は相異なる。基点に指定した `O_NOFOLLOW` は正当な場合を妨げ、基点に指定した `O_NONBLOCK` は効果を持たない。

まず `O_NOFOLLOW` を扱う。誤った位置に指定しても正しく見えるため、正確な記述を要する。

これは<strong>削除対象のエントリ</strong>に指定するものであり、リンクがその指す先の代わりになることを防ぐ。<strong>親ディレクトリに指定するものではない</strong>。シンボリックリンク経由で到達するディレクトリに利用者が位置することは正当にありえ、その親を開くことを拒否しても保護にはならず、処理の放棄を招くのみである。そこでリンクを辿ることが安全であるのは別の理由による。エントリに対する同一性の照合は、到達したディレクトリが実際に当該エントリを保持する場合にしか成立しないためである。

<Callout title="フラグを足すと errno が変わる">
この点の検証により、記録すべき結果が得られた。`O_NOFOLLOW` の下でシンボリックリンクに対して報告されるエラーは、`O_DIRECTORY` の同時指定の有無で変わる。

| flags | `adir` | `afile` | ディレクトリへのリンク | ファイルへのリンク | 切れたリンク |
| --- | --- | --- | --- | --- | --- |
| `O_RDONLY` | ok | ok | ok | ok | `ENOENT` |
| `O_RDONLY\|O_NOFOLLOW` | ok | ok | `ELOOP` | `ELOOP` | `ELOOP` |
| `O_RDONLY\|O_DIRECTORY` | ok | `ENOTDIR` | ok | `ENOTDIR` | `ENOENT` |
| `O_RDONLY\|O_DIRECTORY\|O_NOFOLLOW` | ok | `ENOTDIR` | `ENOTDIR` | `ENOTDIR` | `ENOTDIR` |

同一の条件——名前にシンボリックリンクがあり、`O_NOFOLLOW` が指定されている——が、二行目では `ELOOP`、四行目では `ENOTDIR` として報告される。`O_DIRECTORY` が先に評価され、`O_NOFOLLOW` が考慮される前に結果が確定するためである。

「リンクであったため開かずに削除する」という場合を扱うコードは、<strong>両方</strong>のエラーを受け付ける必要がある。片方のみを挙げるコメントは、規則ではなく特定の構成を記述していることになる。
</Callout>

`O_NONBLOCK` は別の理由で成立しない。基点に指定する理由づけ自体は妥当に見える。当該の名前に FIFO が置かれていれば `open` 自体が、到来しない可能性のある書き手を待つことになり、無期限に停止する処理は失敗する処理より望ましくない、というものである。理由づけは妥当であるが、結論は導かれない。すでに `O_DIRECTORY` が指定されているためである。

| フラグ | 書き手のいない FIFO |
| --- | --- |
| `O_RDONLY` | 無期限に停止 |
| `O_RDONLY\|O_NONBLOCK` | 開ける |
| `O_RDONLY\|O_DIRECTORY` | 即座に `ENOTDIR` |
| `O_RDONLY\|O_DIRECTORY\|O_NONBLOCK` | 即座に `ENOTDIR` |

一行目が危険、二行目がその対処であり、三行目は当該の対処が別のフラグによって既に与えられていることを示す。`O_DIRECTORY` は FIFO が停止しうるより先にこれを拒否するため、`O_DIRECTORY` を伴う open において `O_NONBLOCK` は効果を持たない。

このフラグが該当するのは<strong>削除対象のエントリ</strong>を開く処理、すなわち `O_NOFOLLOW` を指定すべき対象と同一の処理である。そこでは `O_DIRECTORY` を指定できない。理由は前述のとおりで、対象はファイル・ディレクトリ・FIFO のいずれでもありえ、そのいずれであるかの判定が当該 open の目的だからである。`O_DIRECTORY` はディレクトリ以外を拒否する形でその判定を打ち切る。したがって保護は `O_NONBLOCK` が担うほかなく、そこでは復帰しない `open` を防ぐ唯一の手段となる。

以上より、二つのフラグは同一の open に指定される。根拠も共通であり、基点はディレクトリであることが既知であるのに対し、エントリの型は開くまで不明だからである。

一点補足を要する。本記事の末尾でコードを全文引用しているためである。Nohrs の基点を開く処理は `O_NONBLOCK` を指定している。これは意図的であり、コメントに理由が記録されている。「隣のフラグがあるため冗長である」と「誤りである」は別の主張であり、上記の議論が示すのは前者のみである。冗長なフラグの代償はビットマスクの 1 ビットであり、評価順序についての推論が誤っていた場合にそれが防ぐのは、貼り付け中に無期限に停止するファイルマネージャである。

もう一つ、依拠すべきでない値がある。`readdir` が返す `d_type` フィールド、すなわちエントリがディレクトリであるかを示す値である。一部のファイルシステムはここに `DT_UNKNOWN` を設定し、確認を呼び出し側に委ねる。`openat` への `O_DIRECTORY` の指定がその確認にあたり、同じ呼び出しで、再帰的な走査が次に必要とするディスクリプタも得られる。

## この問題が生じた事例

ここまでの内容は、このブログが属するファイルマネージャ [Nohrs](https://github.com/noh-rs/nohrs) に存在した不具合の説明である。対象は、貼り付けが途中で失敗した後に実行される後始末の処理である。

新しい名前へのコピーが途中で失敗した場合、書きかけの結果は除去を要する。残す選択肢は成立しない。一覧上では未完成であることを示す手掛かりのない通常のディレクトリとして現れ、かつその名前を占有するため、以後の再試行はすべて `report (2)` に配置される。ただし後始末が除去してよいのは<strong>当該の操作自身が作成したもの</strong>に限られ、同じ名前を持つ別のエントリであってはならない。

以前の実装は、判断と除去を二つの独立した手順として実行していた。まず宛先が当該の操作自身の書きかけであることを `stat` で確認し、次に `remove_dir_all(dst)` を呼ぶ。この第二の呼び出しは `dst` を再びパス名から解決する。これは本記事で前述した隙間が出荷済みのコードに存在していた状態である。二回の解決に対して判断は一回であり、その間に別の書き手が当該の名前へ別のエントリを置きうる。`stat` は所有を確認し、除去はその時点で存在するものを対象とする。

この窓は狭い。到達には、一度その名前の獲得に失敗した別の書き手が、二つのシステムコールの間に同じ名前を獲得することを要する。一定期間、パスによる除去が意図的な選択であった程度には狭い。代替案——書きかけを保持して報告する——は競合状態ではなく確実に発生する問題だからである。

修正は `*at` の方式に従う。親ディレクトリを一度だけ解決してディスクリプタを保持し、以降はそれを基準に処理する。

```rust
let (parent, name) = parent_and_name(dst)?;
let parent = open_directory(parent)?;
// 獲得した当のエントリである間に限り、それを返す。
let Some(entry) = open_claimed(&parent, name, claimed)? else {
    return Ok(());
};
if entry.metadata()?.is_dir() {
    empty_dir(&entry)?;
    already_gone_is_fine(unlinkat(&parent, name, AtFlags::REMOVEDIR))?;
} else {
    already_gone_is_fine(unlinkat(&parent, name, AtFlags::empty()))?;
}
```

この中の三点は、選好ではなくここまでの議論からの帰結である。

- 同一性の照合は<strong>開いたディスクリプタを通じて</strong>行う。名前を介した照合は意味を持たず、同じ競合にさらされる検索が一つ増えるのみである
- 除去が返す `ENOENT` は成功として扱う。エントリが存在しないことは要求された結果そのものであり、別のプロセスが先に到達したにすぎない。これを失敗として扱えば、後始末が許容すべき競合を理由に後始末自体を放棄することになる
- 最後の `unlinkat` は依然として `name` を取る。解決するのは一成分であり、その相手はこのコードが保持しており差し替えられないディレクトリである。この方式が提供する範囲はここまでである

## 狭めることと、閉じること

表題の主張は「Linux に呼び出しが一つ足りない」より強い。「このディスクリプタを削除せよ」は機能要望ではない。ディスクリプタが指すのは実体であり、削除が作用するのは名前であり、一つの実体は複数の名前を持ちうるからである。

そこから導かれる帰結は以下のとおりである。

- あらゆる削除は名前を解決する。したがってあらゆる削除に窓がある
- ディレクトリディスクリプタの保持は、最終成分を除く解決のすべてを取り除く
- ディレクトリについては、`rmdir` が空でない対象を拒否することで、その最後の窓が招きうる被害が小さくなる
- それ以外については窓は残る。適切な対応は、窓がどこにあるかを記録することである

この手法を解決策として提示することは正確ではない。ディスクリプタを基点とした処理はパスを再解決するより厳密に優れており、`*at` 系の呼び出しはそのために存在する。ただし最後の検索はインタフェース設計上の見落としではなく、削除という操作の構成要素である。
