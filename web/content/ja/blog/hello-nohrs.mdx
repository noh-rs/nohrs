ファイルに費やしている時間のほとんどは、ファイルに対して何かをしている時間ではありません。ファイルにたどり着くまでの時間です。標準の macOS では、ウィンドウを開き、階層をたどり、階層が目的地を知らないと分かった時点でそれを諦めて、別のアプリの検索窓に切り替えることになります。

一つひとつは、気づかない程度に小さな操作です。合計すると、それが仕事の中身になっています。

## 1 つの問題の、2 つの側面

ランチャーとファイルマネージャは、たいてい別々の製品として扱われます。Raycast や Alfred はランチャーで、Finder・Path Finder・Marta はファイルマネージャです。両方を使うということは、同じファイルシステムに対する 2 つのメンタルモデルを行き来するということで、あいだを埋めるプラグインを入れても、それは橋のままです。

Nohrs が両者を 1 つのアプリにまとめているのは、これが 1 つの問題だからです。**いま頭に浮かんでいるものまで連れて行って、そこで操作させてほしい**。グローバルホットキーで呼び出し、名前を途中まで打ち、プレビュー・リネーム・移動・オープンができるウィンドウに着地する。その前にどこか別の場所へ寄る必要はありません。

## なぜ Rust で、なぜ gpui か

「速く、確実に」は README に書くのは簡単で、守るのは高くつきます。4 万件のディレクトリで引っかかるファイルマネージャは、唯一の仕事に失敗しています。

Rust では、速い経路と安全な経路が同じ経路になります。スクロールの途中で GC が止まることもなければ、性能と引き換えに抱え込むメモリバグの分類もありません。gpui は、まさにこの種の情報密度が高くキーボード中心のインターフェースのために作られた GPU アクセラレーテッドな描画基盤で、同じ制約のもとでエディタを出荷している人たちが書いています。

## 「信用してくれ」と言わない拡張

ファイルマネージャの面白い部分は、誰にも先回りできないところにあります。1 日に 20 回走らせる変換や、自分のリポジトリでしか意味を持たないステータス列がそれです。そういうものは拡張であるほかありません。

拡張はふつう、作者を信用してほしいという要求と一緒にやってきます。Nohrs はその要求をしません。プラグインは、環境的な権限を一切持たないサンドボックス内の WASM コンポーネントです。ファイルシステムもネットワークもサブプロセスも、個別に許可されるまで届きません。プラグインは「ホームディレクトリを読まないと約束する」ことができません。そもそも到達できないからです。

## 公開の場で

設計上の判断は、コードより先に ADR としてリポジトリに入ります。議論して採用しなかった案も含めてです。検索インデックスがなぜ OS のインデックスではなく SQLite と Tantivy なのかを知りたければ、その理由はマーケティングページの 1 文ではなく、読めるファイルとして置いてあります。

ソースは [noh-rs/nohrs](https://github.com/noh-rs/nohrs) にあります。まだ早い段階です。異論を言うには、いちばん良い時期です。
