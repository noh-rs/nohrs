Nohrs は自前の検索インデックスを持っています。仕事用のディレクトリを OS のインデクサが見ることを許されていたかどうかに、ファイルが見つかるかどうかを左右されないためです。実体は [tantivy](https://github.com/quickwit-oss/tantivy) のインデックスで、tantivy の writer は**プロセスを跨いで 1 つしか存在できません**。

しばらくは一番素朴な形で動かしていました。アプリが起動時に writer を開き、終了まで持ち続ける。これは他の誰かが書きたくなるまでは問題ありません。アプリを開いたままターミナルで `noh index build` を打つと拒否されます — 設計どおり、tantivy の仕様どおり、正しく、そして無意味に。インデックスは、先にそこへ着いたプロセスの私物になっていました。

では、writer はどこに置くべきか。

## 「どうせ常駐プロセスがある」

素直な答えはランチャーです。Nohrs にはグローバルホットキーがあるので、ウィンドウが開いているかに関わらずプロセスは常駐しています。そこに writer を置いても、新しく常駐するものは増えません。

これは間違った答えで、その理由は「常駐かどうか」の話ではない、という点で書き留めておく価値があります。

ランチャーには**レイテンシ予算**があります。ホットキーからウィンドウまで 100ms 未満、キー入力から結果まで 50ms 未満。インデックス作成はまったく別種の仕事です。スループット律速で、IO が重く、これからもっと重くなります — いまは 50MB ヒープの tantivy writer とそのマージスレッド、ベクトル検索に手を付ければ数百 MB の embedding モデル。この 2 つを同じアドレス空間に置くと、アロケータとスレッドプールと**運命**を共有します。索引中の OOM kill は、ユーザーのホットキーごと持っていきます。

もう一つ、小さくて鋭い事実があります。**ランチャーはそのインデックスを引いていません。** キーストロークの経路が見ているのはファイル**名**のインメモリ索引で、tantivy のインデックスが答えるのは内容検索です。同居させて得るものは何もありません。

## 「でもデーモンは嫌われる」

嫌われます。しかも Nohrs の README には "no dependency on the OS search daemon" と書いてあります。その隣に自前のログイン項目が並ぶのは、さすがに格好がつきません。

ただ、嫌われているのは本当はデーモンではありません。**ログイン時から起動し、見えないところで何かを消費し、見つけ方も止め方も分からず、存在するために launchd や systemd への登録を要求してくるプロセス**が嫌われています。必要なときに起動して、不要になったら消えるプロセスは別物で、みんな文句も言わずに何十個も走らせています。

`nohrs-indexd` はその後者です。インストールするものは何もありません。インデックスを最新に保ちたい最初のプロセスが起動し、最後のクライアントが去って 90 秒経つと自分で終了します。ランチャーはどのみち常駐しているので、実際にはデーモンの寿命はアプリの寿命と一致します。nohrs を終了すれば両方消える。探すものも、止めるものも、ログイン項目に並ぶものもありません。

残るのは 1 つの問いで、そこが面白いところです。

## どうやって「死ぬとき」を知るのか

「最後のクライアントが去ったら終了」は `Arc` です。クライアント 1 人につき 1 つ持たせ、去るときに落とし、最後の 1 つが落ちたらプロセスごと終わる。同一アドレス空間なら Rust で 3 行です。

プロセスを跨ぐとそうはいきません。理由は `Drop` にあります。

1. **`Drop` は `SIGKILL` では走りません。** OOM killer でも、segfault でも、電源断でも走りません。行儀よく終了したときだけ正しい参照カウントは、**まさに必要な場面で間違っている**参照カウントです。
2. **`Drop` はアドレス空間を越えません。** クライアント側のデストラクタは、デーモン側のカウンタを減らせません。

ハートビートは 1 つ目を誤魔化せますが 2 つ目を解決しません。クライアントの pid を監視する案は pid 再利用とレースします。`PR_SET_PDEATHSIG` は子を親に紐づけるものですが、このデーモンは**起動元より長生きするのが仕様**です — 起動元は 1 秒後に終了する一発コマンドかもしれません。

答えは、**カーネルがすでにこれをやっている**ことです。しかも、まさにこの意味論で。**unix socket の接続はカーネルが参照カウントしており**、プロセスが終了すると — どんな終わり方であれ — その fd は閉じられます。反対側は end-of-stream を読みます。「生きているクライアント数」と「開いている接続数」は同じ数であり、その数は `kill -9` に対して正しい。**ユーザー空間の誰も、それを維持するよう頼まれていないから**です。

つまり、**モデルは `Arc`、実装はカーネル、Rust が両側に形を与える**。

## その「形」

デーモン側の lease はごく普通の RAII 型です。設計上の判断で効いているのは 1 点だけで、**接続を捌く関数が値で受け取る**ことです。

```rust
/// 接続 1 本を、クライアント側の socket が閉じるまで捌く。
///
/// `lease` は値で受け取り、どこにも渡さない。この関数が返ることが解放であり、
/// この関数が返るのはクライアント側が閉じたとき — クライアントがどうなろうと
/// カーネルが閉じてくれる、あの合図のときである。
fn serve_client(&self, stream: UnixStream, lease: Lease) -> Result<()> {
    let mut reader = BufReader::new(stream);
    while let Some(request) = read_frame::<Request>(&mut reader)? {
        // ...
    }
    Ok(()) // ここで lease が落ちる
}
```

lease を持たずにクライアントを捌く方法はなく、捌き終えたあとも持ち続ける方法もありません。解放は「忘れうる手順」ではない。そもそも手順ではないからです。

## なぜ素の `Arc` にしないのか

猶予時間が欲しかったからです。シェルスクリプト中の `noh index build` の 1 秒後にもう 1 回叩かれたとき、2 つ目のデーモンを起動し直すコストを払いたくない。そこで、最後のクライアントが去ってから 90 秒待ちます。

これが「最後の drop で終了」を壊します。理由は正確に言う価値があります。`Arc` は**カウントがゼロになったことだけを伝えて消え、そのとき動き出したものを呼び戻す方法ごと忘れます**。猶予時間中に来たクライアントはカウントダウンを中止させる必要があるのに、中止させる手がかりが残っていません。

なので、カウントとゼロになった時刻を明示的に持ちます。

```rust
struct State {
    live: usize,
    /// 最後にカウントがゼロになった時刻。誰かが lease を持っている間は `None`。
    /// 保留中のシャットダウンをクライアントが取り消せるのは、これがあるから。
    idle_since: Option<Instant>,
}
```

待ちはポーリングではなく条件変数にしてあるので、何もしていないデーモンを置いておくコストはゼロです。

```rust
pub fn wait_until_idle(&self) {
    let mut state = self.lock();
    loop {
        match state.idle_since {
            // 誰か繋がっている。状況が変わるまでやることはない。
            None => state = self.wait(state),
            Some(since) => match self.grace.checked_sub(since.elapsed()) {
                None => return,
                Some(remaining) => state = self.wait_for(state, remaining),
            },
        }
    }
}
```

これを独立した型として切り出しておくと嬉しいのは、**socket を一切使わずにテストできる**ことです。lease を取って、落として、待ちがいつ返るかを見るだけで済みます。

<Callout title="もう半分">
  デーモンを欲しがったクライアントが 2 つ同時にいれば、2 つとも起動しようとします。負けた方は引き下がる必要がありますが、その判定を「socket ファイルがあるか」でやることはできません。socket ファイルは、それを作ったプロセスより長生きするからです。代わりに、デーモンが生存中ずっと保持する**アドバイザリロック (`flock`)** が決めます — そしてこのロックも、保持者がどう死のうとカーネルが解放します。pid ファイルなら疑ってかかる必要がありますが、ロックは嘘をつけません。
</Callout>

## そもそもデーモンにしてよい理由

ここでは 1 つの不変条件がほとんどの仕事をしています。**検索はデーモンを通らない。**

読み手は tantivy のインデックスを直接開きます。何プロセスからでも同時に。読むのにロックは要らないからです。socket が運ぶのは、書き込み要求と、状態の問い合わせと、commit されたという通知だけ。**クエリは一度も通りません。**

これは最適化ではありません。デーモンを**依存ではなく任意のインフラ**にしているのがこの条件です。落ちていても、固まっていても、バージョンが 1 つ古くても、検索は答えます — 本来より少しだけ古いインデックスから。ユーザーがクエリを打ったのに、知りもしないバックグラウンドプロセスの機嫌が悪いせいでエラーが返る、という失敗モードが存在しません。おかげで、読み取り経路に一切触れないまま、段階的に入れることも外すこともできます。

## kill をテストする

肝心のテストはプロセス内では書けません。主張そのものが「**退出時にコードを 1 行も実行できなかったとき**に何が起きるか」だからです。そこで、接続して眠るだけの小さなヘルパーバイナリを用意し、テストがそれを kill します。

```rust
let mut held = Command::new(env!("CARGO_BIN_EXE_holds_a_connection"))
    .arg(&fixture.endpoint.socket)
    .spawn()
    .unwrap();
until("the killable client to be counted", || {
    probe.status().unwrap().clients == Some(2)
});

// ここから先、デーモンを支えているのは kill される側だけ。
drop(probe);
std::thread::sleep(GRACE * 2);
assert!(!gone(&fixture.endpoint.socket), "クライアントが居るのにデーモンが止まった");

held.kill().unwrap();
until("the daemon to stop", || gone(&fixture.endpoint.socket));
```

働いているのは最初の待機です。これが無いと、**ヘルパーがそもそも接続に失敗したときにもテストが通ります** — 初回の実行でまさにそうなりました。何の意味もない green の典型です。

## 現在地

writer とファイル watcher は `nohrs-indexd` に同居しています。おかげで「インデックスはファイルシステムに追従しているか」を訊く先が 1 箇所になりました。答えが 1 つになったわけではありません。デーモンが生きていることは、watcher が動いていることを意味しません — watcher の設置に失敗してもデーモンは終了しない仕様です。ライブ更新を失うのは鮮度の問題であって、次回起動時のパスが追いつくからです。なので `noh index status` はそのどれなのかを言います — `watching` か、`running but not watching` か、そもそも動いていないか。推し量らせません。ログイン時に起動するものは無く、システムに登録するものも無く、人間が終了させるものは nohrs だけです。

ベクトル検索が来て、インデックス作成が数百 MB のモデルウェイトを欲しがり始めたとき、その置き場所は**あなたのホットキーを握っているプロセスではない**場所にあります。
