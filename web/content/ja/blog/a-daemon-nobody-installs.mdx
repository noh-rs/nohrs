Nohrs は自前の検索インデックスを保持する。ファイルが見つかるか否かを、作業用のディレクトリを OS のインデクサが走査することを許可されていたか否かに依存させないためである。実体は [tantivy](https://github.com/quickwit-oss/tantivy) のインデックスであり、tantivy が許す writer は<strong>全プロセスを通じて一つ</strong>である。

当初の構成は最も単純なものであった。アプリケーションが起動時に writer を開き、終了まで保持する。これは他のものが書き込みを要求するまでは成立する。アプリケーションを開いたままターミナルから `noh index build` を実行すると拒否される——設計どおり、tantivy の仕様どおり、正しく、そして無益に。インデックスは、先に到達したプロセスの専有物となっていた。

したがって問題は、writer をどこに置くかである。

## 候補としてのランチャー

直截な答えはランチャーである。Nohrs はグローバルホットキーを備えるため、ウィンドウの開閉に関わらずプロセスは常駐しており、そこに writer を置いても新たに常駐するものは生じない。

この答えは誤りである。ただし、常駐の可否が理由ではない。

ランチャーには<strong>レイテンシ予算</strong>がある。ホットキーからウィンドウまで 100ms 未満、キー入力から結果まで 50ms 未満である。インデックス作成はまったく別種の作業であり、スループット律速で IO が重く、かつ今後さらに重くなる。現時点では 50MB のヒープを持つ tantivy の writer とそのマージスレッドであり、ベクトル検索に着手すれば数百 MB の embedding モデルが加わる。この二つを同一のアドレス空間に置けば、アロケータとスレッドプール、および<strong>運命</strong>を共有することになる。索引中の OOM kill は、利用者のホットキーを巻き添えにする。

そして<strong>ランチャーは当該のインデックスを参照していない。</strong>キーストロークの経路が参照するのはファイル<em>名</em>のインメモリ索引であり、tantivy のインデックスが答えるのは内容検索である。同居によって得られるものはない。

## デーモンへの忌避が対象とするもの

デーモンは忌避される。加えて Nohrs の README には "no dependency on the OS search daemon" と記載があり、その隣に自前のログイン項目が並ぶことは体裁を欠く。

ただし忌避の対象はデーモンそのものではない。<strong>ログイン時に起動し、不可視のうちに資源を消費し、所在も停止手段も与えられず、存在するために launchd あるいは systemd への登録を要求するプロセス</strong>が忌避されている。必要になった時点で起動し、不要になれば終了するプロセスは別種のものであり、その種のプロセスは何十と実行されながら問題視されていない。

`nohrs-indexd` は後者である。インストールを要するものはない。インデックスの追従を要求する最初のプロセスがこれを起動し——それはアプリケーションとは限らず、CLI のコマンドもこれを要求する——最後のクライアントが去って 90 秒が経過した時点で自ら終了する。ランチャーはいずれにせよ常駐しているため、実際には nohrs の稼働中は起動しており、終了後も猶予時間の間は残る。ログイン項目に並ぶものはない。停止は必須でもなく、また隠されてもいない。放置すれば自ら終了し、`noh index stop` を打てば直ちに終了する。

残る問いは一つである。

## 終了時点の判定

「最後のクライアントが去った時点で終了する」は `Arc` の記述である。クライアント一つにつき一つを保持し、離脱時に落とし、最後の一つが落ちた時点でプロセスを終える。同一アドレス空間においては Rust で三行である。

プロセスを跨ぐ場合は成立しない。理由は `Drop` にある。

1. <strong>`Drop` は `SIGKILL` では実行されない。</strong>OOM killer、segfault、電源断のいずれでも実行されない。クライアントが秩序立った終了を行った場合にのみ正しい参照カウントとは、<strong>まさにそれを要する場面で誤っている</strong>参照カウントである。
2. <strong>`Drop` はアドレス空間を越えない。</strong>クライアント側のデストラクタは、デーモン側のカウンタを減算できない。

ハートビートは第一の点を糊塗するにとどまり、第二の点を解決しない。クライアントの pid を監視する方式は pid の再利用と競合する。`PR_SET_PDEATHSIG` は子を親に紐づけるものであるが、このデーモンは<strong>起動元より長く存続することを仕様とする</strong>。起動元が一秒後に終了する一回限りのコマンドである場合があるためである。

解決は、<strong>カーネルがすでに同一の処理を行っている</strong>ことにある。しかもまさにこの意味論においてである。<strong>unix socket の接続はカーネルが参照カウントしており</strong>、プロセスが終了すれば——終了の態様を問わず——その fd は閉じられ、反対側は end-of-stream を読む。「生存しているクライアント数」と「開いている接続数」は同一の量であり、その量は `kill -9` に対して正しい。<strong>ユーザー空間のいずれの主体も、その維持を要求されていない</strong>ためである。

すなわち、モデルは `Arc`、実装はカーネルであり、Rust が双方に形を与える。

## lease の形

デーモン側の lease は通常の RAII 型である。設計上の判断として作用しているのは一点、<strong>接続を処理する関数が値で受け取る</strong>ことである。

```rust
/// 接続一本を、クライアント側の socket が閉じるまで処理する。
///
/// `lease` は値で受け取り、他へ渡さない。この関数が返ることが解放であり、
/// この関数が返るのはクライアント側が閉じた時点である。クライアントが
/// どのような終わり方をしようと、閉じるのはカーネルである。
fn serve_client(&self, stream: UnixStream, lease: Lease) -> Result<()> {
    let mut reader = BufReader::new(stream);
    while let Some(request) = read_frame::<Request>(&mut reader)? {
        // ...
    }
    Ok(()) // ここで lease が落ちる
}
```

lease を保持せずにクライアントを処理する方法はなく、処理の終了後に保持し続ける方法もない。解放は遺漏しうる手順ではない。そもそも手順ではないためである。

## 参照カウントを `Arc` としない理由

猶予時間を要したためである。シェルスクリプト中の `noh index build` の一秒後に再度実行された場合に、二つ目のデーモンを起動する代償を支払うべきではない。そこでデーモンは、最後のクライアントが去ってから 90 秒待機したうえで終了する。

これは「最後の drop で終了する」という定式を崩す。`Arc` は<strong>カウントがゼロに達した事実のみを伝えて消滅し、その時点で動き出したものを呼び戻す手段ごと失う</strong>。猶予時間中に到来したクライアントはカウントダウンを中止させる必要があるが、中止のための手掛かりが残っていない。

したがって、カウントとゼロに達した時刻を明示的に保持する。

```rust
struct State {
    live: usize,
    /// 最後にカウントがゼロになった時刻。誰かが lease を持っている間は `None`。
    /// 保留中のシャットダウンをクライアントが取り消せるのは、これがあるため。
    idle_since: Option<Instant>,
}
```

また待機はポーリングではなく条件変数によるため、処理のないデーモンを保持する代償はない。

```rust
pub fn wait_until_idle(&self) {
    let mut state = self.lock();
    loop {
        match state.idle_since {
            // 誰かが接続している。状況が変わるまで行うことはない。
            None => state = self.wait(state),
            Some(since) => match self.grace.checked_sub(since.elapsed()) {
                None => return,
                Some(remaining) => state = self.wait_for(state, remaining),
            },
        }
    }
}
```

これを独立した型として切り出すことの利点は、<strong>socket を一切用いずに試験できる</strong>点にある。lease を取得し、解放し、待機が復帰する時点を検証すれば足りる。

<Callout title="もう一方の半分">
  デーモンを要求するクライアントが二つ同時に存在すれば、双方が起動を試みる。敗れた側は引き下がる必要があるが、その判定を socket ファイルの有無に求めることはできない。socket ファイルは、それを作成したプロセスより長く残存するためである。代わりに、デーモンの生存中を通じて保持される<strong>アドバイザリロック (`flock`)</strong> が判定する。このロックもまた、保持者の死の態様を問わずカーネルが解放する。pid ファイルは疑ってかかることを要するが、ロックは誤りを報告しえない。
</Callout>

## デーモン化を許容する条件

ここでは一つの不変条件がほとんどの作用を担っている。<strong>検索はデーモンを経由しない。</strong>

読み手は tantivy のインデックスを直接開く。同時に任意の数のプロセスから開いてよい。読み取りにロックを要さないためである。socket が運ぶのは書き込み要求、状態の問い合わせ、および commit された旨の通知であり、クエリを運ぶことはない。

これは最適化ではない。デーモンを<em>依存ではなく任意のインフラ</em>たらしめているのがこの条件である。停止していても、応答不能でも、バージョンが一つ古くとも、検索は答える。本来より幾分古いインデックスからではあるが、答える。利用者がクエリを実行した結果、その存在を認識してもいないバックグラウンドプロセスの不調を理由にエラーが返る、という失敗様態は存在しない。同じ条件により、読み取り経路に一切触れることなく、段階的な導入も撤去も可能である。

## 予告なき終了の検証

要点となる試験はプロセス内では記述できない。主張の対象が<strong>退出時に一行のコードも実行できなかった場合</strong>の挙動だからである。そこで、接続して休眠するのみの小さなヘルパーバイナリを用意し、試験はこれを kill する。

```rust
let mut held = Command::new(env!("CARGO_BIN_EXE_holds_a_connection"))
    .arg(&fixture.endpoint.socket)
    .spawn()
    .unwrap();
until("the killable client to be counted", || {
    probe.status().unwrap().clients == Some(2)
});

// ここから先、デーモンを支えているのは kill される側のみである。
drop(probe);
std::thread::sleep(GRACE * 2);
assert!(!gone(&fixture.endpoint.socket), "クライアントが居るのにデーモンが止まった");

held.kill().unwrap();
until("the daemon to stop", || gone(&fixture.endpoint.socket));
```

作用しているのは最初の待機である。これを欠くと、<strong>ヘルパーが接続に失敗した場合にも試験が通過する</strong>。初回の実行において実際にそうなった。何も立証しない green の典型である。

## 結果として得られた構成

writer とファイル watcher は `nohrs-indexd` に同居する。これにより「インデックスはファイルシステムに追従しているか」を問う先が一箇所に定まる。答えが一つに定まったのではない。デーモンの生存は watcher の動作を含意しない。watcher の設置に失敗してもデーモンは終了しない仕様である。ライブ更新の喪失は鮮度の問題にとどまり、次回起動時のパスが追いつくためである。したがって `noh index status` はいずれの状態であるかを明示する——`watching` か、`running but not watching` か。推測に委ねることはしない。なお、問うこと自体がデーモンを必要とする理由にあたるため、動作していなければこのコマンドが起動する。第三の答えである「動作していない」は、起動できずインデックスをこのプロセスで読んだ場合に報告される。ログイン時に起動するものはなく、システムに登録するものもない。人が終了させる必要があるのは nohrs のみであり、猶予時間を待ちたくない場合のために `noh index stop` がある。

ベクトル検索が導入され、インデックス作成が数百 MB のモデルウェイトを要求し始めた時点で、その置き場所は<strong>ホットキーを保持するプロセスではない</strong>場所にある。
