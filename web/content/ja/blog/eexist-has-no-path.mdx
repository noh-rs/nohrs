ファイラーにおいて、既存のフォルダの上に同じ名前のフォルダをペーストし、「置き換えますか」という確認に「はい」と応答する。Finder でもエクスプローラでも日常的に行われている操作です。

この操作を正しく実装しようとすると、<strong>途中で失敗したときに何を削除してよく、何を削除してはならないか</strong>という問題に突き当たります。そして OS の構造上、その判断に必要な情報は<strong>失敗が呼び出し元に届いた時点で既に失われています</strong>。

本稿は Nohrs でこの問題を扱った記録ですが、内容は OS とファイルシステムの一般論です。本プロダクトの知識は必要ありません。前提となる事項は順に説明します。

## 名前と実体の分離

前提となる構造から述べます。ディレクトリは、ファイルを格納している箱ではありません。ディレクトリは<strong>名前から番号への対応表</strong>にすぎません。

この番号を inode 番号と呼びます。サイズ、更新時刻、パーミッションといったメタデータと、データ本体が置かれたブロックへの参照は、すべて inode 側が保持しています。ディレクトリ側にあるのは名前だけです。言い換えれば、<strong>inode は自身の名前を知りません</strong>。

この構造から、ファイルを削除するシステムコールが `unlink`、すなわち「リンクを外す」という名称である理由が導かれます。削除されるのは名前のほうです。実体が解放されるのは、<strong>参照が一つも残らなくなった時点</strong>です。ディレクトリエントリだけでなく、実行中のプロセスが保持している開いたディスクリプタやメモリマッピングも参照に含まれます。最後の名前が消えても、まだ開いているプロセスがあれば内容はそのまま残ります。

ここから、本稿で繰り返し用いる二つの帰結が得られます。

- <strong>異なるパスが同一のファイルを指しうる。</strong>「コピー元とコピー先はパスが異なるので安全である」という推論は成り立ちません。
- <strong>同一のパスが異なるファイルを指しうる。</strong>先ほど確認したパスと、これから書き込もうとしているパスが同じ実体を指しているとは限りません。

特に重要なのは二点目です。<strong>パスは名前であって、それが指す対象の身元ではありません</strong>。後述する「削除する前に身元を照合する」という設計の必要性は、ここに由来します。

## rename(2) の原子性と暗黙の上書き

`rename(2)` はファイルを移動するシステムコールです。ただし前節を踏まえると、実際に行われているのは<strong>対応表の書き換え</strong>だけです。データは 1 バイトも移動しません。同一ファイルシステム内であれば、100GB のファイルであっても瞬時に完了するのはこのためです。

重要なのは、この書き換えが<strong>原子的（atomic）</strong>であることです。書き換えの途中という状態を他のプロセスが観測することはありません。名前は古い番号を指しているか、新しい番号を指しているかのいずれかであり、その中間は存在しません。

### 暗黙の上書きが仕様である理由

`rename` は、移動先に既にファイルが存在していても、何も確認せずに上書きします。一見すると危険な挙動ですが、これは意図された仕様であり、かつこの性質に依存する重要な仕組みが存在します。

テキストエディタが上書き保存を行う際の手順を検討します。最も単純な手順は、`notes.txt` を開き、内容を空にし、新しい内容を書き込むというものです。

```text
# 最も単純な上書き保存。途中で電源が落ちると……
open("notes.txt", O_WRONLY|O_TRUNC)   ← この時点で内容が失われる
write("新しい内容の前半")               ← ★ここで停止

# 残るファイル: 「新しい内容の前半」のみ。
# 古い内容も完全な新しい内容も、どこにも存在しない。
```

`O_TRUNC` はファイルを空にしてから開くフラグです。書き込みが 1 バイトも完了していない段階で、古い内容は既に失われています。

正しい手順は、別名ですべて書き込んでから `rename` によって差し替えることです。

```text
# atomic save。どの時点で停止しても破損しない
write("notes.txt.tmp", 新しい内容の全体)   ← 停止しても notes.txt は無傷
fsync("notes.txt.tmp")
rename("notes.txt.tmp", "notes.txt")      ← 原子的に差し替わる
fsync("notes.txt" の親ディレクトリ)          ← 差し替え自体もクラッシュに耐える

# notes.txt は古い内容のままか、新しい内容か。中間状態は存在しない。
```

最後の行は省略されがちですが必要です。`rename` は戻った時点で他プロセスに対しては原子的である一方、書き換えたディレクトリエントリがディスクに到達しているとは限りません。この `fsync` がなければ、クラッシュ後に古い名前のまま復帰しうるということです。原子的であることと永続化されることは別の性質です。

そしてこの手順全体が成立するのは、`rename` が<strong>上書きを拒否しない</strong>ためです。拒否する仕様であれば、削除してから rename するという二段階の手順が必要になり、その間隙で停止した場合にファイルが失われます。

### 上書きを拒否する rename

一方で、上書きされては困る場面も存在します。ゴミ箱から復元する際に、元の場所に既に別のファイルが存在していれば、それを黙って破壊するわけにはいきません。ペースト先の名前が空いているはずの場合も同様です。

このために、上書きを拒否する rename が用意されています。Linux では `renameat2(RENAME_NOREPLACE)`、macOS では `renamex_np(RENAME_EXCL)` です。移動先が空いていれば移動し、埋まっていれば `EEXIST` で失敗するという動作を、原子的に実行します。

### ドライバ実装に起因する制約

この点には注意が必要です。このフラグはカーネルの共通層を経由して、最終的に<strong>個々のファイルシステムのドライバ</strong>に到達します。そして、ドライバが実装しているとは限りません。

- `renameat2` 自体を持たないカーネル（Linux 3.15 より前）は `ENOSYS` を返します
- フラグを受け付けないドライバは `EINVAL` を返します。システムコール自体は 3.15 から存在しますが、`RENAME_NOREPLACE` が多くのファイルシステムに行き渡ったのは 4.9 です
- APFS 以外の macOS ボリュームは `ENOTSUP` を返します

この区別は errno を読むときに効いてきます。`ENOSYS` はカーネルが「その呼び出しは存在しない」と言っているのに対し、`EINVAL` はドライバが「そのフラグは受け取らない」と言っている状態です。

<Callout title="overlayfs で実際に測った">
本稿の初稿では、ここに「overlayfs は `EINVAL` を返す」と書いていました。レビューで疑義が出たので実際に測ったところ、間違いでした。

overlayfs は、複数のディレクトリを重ねて一つに見せるファイルシステムです。下位レイヤ (lower) は読み取り専用で、書き込みは上位レイヤ (upper) に溜まり、利用者にはその合成結果だけが見えます。下位レイヤにあるファイルを変更しようとすると、まず上位レイヤへ複製され (copy-up)、以後はそちらが使われます。Docker のイメージとコンテナの関係がこれで、コンテナの作業ディレクトリは多くの場合 overlayfs です。

Linux 6.18 上に overlayfs をマウントし、`renameat2(RENAME_NOREPLACE)` を直接呼んだ結果です。

| 操作 | 結果 |
| --- | --- |
| 宛先が空いている | 成功 |
| 宛先が埋まっている | `EEXIST` |
| 下位レイヤにあるディレクトリの移動 | `EXDEV` |

上の二行は ext4 と同じです。フラグは受け付けられています。そして三行目の `EXDEV` は `EINVAL` とはまったく別の分岐に入ります。overlayfs は結局フォールバックを通るのですが、<strong>フラグ非対応としてではなく、クロスデバイスの分岐から</strong>通るわけです。

<strong>ただし、その `EXDEV` は実際には何もまたいでいません。</strong>上の計測では、移動元も移動先も同じ overlayfs マウントの中にあります。`EXDEV` は本来「デバイスをまたぐリンク」を意味する値ですが、ここでは overlayfs が「この rename は自分では実行できないので、コピーで済ませてほしい」と言うために使っています。コードはそれで正しく動きます——フォールバックはまさに求められている応答です。しかし「利用者が別のボリュームへ移動した」と読むと外します。

errno から状況を推測すると外す、というのが本稿の主題です。本稿は、確かめずに書いた一行でそれを一度外し、その訂正文でもう一度外しました。`EXDEV` を「ファイルシステムをまたいだ証拠」と書いたのがそれで、これもレビューに拾われています。errno は整数一つで、その意味を決めるのはドライバです。
</Callout>

したがって、上書きを拒否する rename は、利用できれば有用ではあるものの、<strong>存在すると仮定してはなりません</strong>。利用できない環境ではフォールバックが必要になります。最も単純なフォールバックは、コピーしてから元を削除するというものです。

これは<strong>移動</strong>が辿りうる経路です。ここは正確に書く必要があります。ext4 や APFS なら以降の話とは無縁だ、と読めてしまうためです。確かに<strong>同一ボリューム内の</strong>移動であれば、rename 一回で完了しフォールバックは実行されません。

しかし<strong>コピー</strong>にはその近道がありません。ツリーを複製する rename は存在しないので、コピーは常にツリーを歩き、各エントリを確保していきます。ext4 でも APFS でも同じです。したがって以降で扱う問題は、通常のコピーペーストについてはあらゆる環境で発生し、移動については `EXDEV`（別ボリューム、あるいは overlayfs の下位レイヤのようにドライバが rename を断った場合）か、no-replace な rename が無いときに発生します。

<Callout title="補足: 原子的でない処理">
もう一つ、原子的ではない処理を挙げておきます。ディレクトリツリーを一括して削除する `remove_dir_all` は、内部のファイルを一つずつ削除していきます。途中で失敗した場合、<strong>ツリーは一部だけが削除された状態で残ります</strong>。この性質は後述の節で問題となります。
</Callout>

## 確認と書き込みの分離が生む競合

素朴に記述した場合のコードを示します。

```rust
if !dst.exists() {        // ← 確認
    write(dst, data);     // ← 書き込み
}
```

この二行の<strong>間</strong>に、別のプロセスが `dst` を作成することができます。そして `write` がそれを破壊します。

これは TOCTOU（Time-of-check to time-of-use）と呼ばれる古典的な競合状態です。確認した時点で成立していた事実が、書き込む時点でも成立していると仮定してしまっています。

これほど短い区間に他のプロセスが割り込む余地はないように思われるかもしれませんが、この区間が短いとは限りません。数万ファイルからなるツリーをコピーしている最中であれば、<strong>この窓は数秒から数分にわたって開いたままになります</strong>。同期クライアント、バックアップツール、ビルドスクリプト、あるいは同一アプリケーションの別ウィンドウなど、競合しうる主体は数多く存在します。

対策は、確認を行わないことです。代わりに、<strong>取得できれば成功し、既に取得されていれば失敗する</strong>呼び出しを用います。

- `open(O_CREAT|O_EXCL)` はファイルを作成し、既に存在すれば `EEXIST` を返します
- `mkdir` はディレクトリを作成し、既に存在すれば `EEXIST` を返します
- `symlink` はシンボリックリンクを作成し、既に存在すれば `EEXIST` を返します

いずれも、存在の確認と作成がカーネル内部で一体の操作として行われるため、その間に割り込む余地がありません。以降、この操作を<strong>確保（claim）</strong>と呼びます。

Nohrs における上書きを行わないコピーと移動は、すべてこの方針に基づいています。さらに、<strong>ツリー内のすべてのエントリ</strong>を確保します。ルートのみを確保するのでは不十分です。ツリーを書き込んでいる数秒の間に、その内部に同名のエントリを作成されうるためです。

### 誤読の代償の非対称性

この二つを取り違えた場合に生じる結果を整理します。

- <strong>(b) を (a) として読む場合。</strong>これが実際の挙動でした。自らの作成途中のツリーを他者のものとして残します。するとロールバックが、そこに何かが存在するという理由で失敗します。利用者の手元には<strong>破損した宛先と、隠しパスに置かれた原本</strong>が残ります。データは失われていませんが、失われたようにしか見えません。
- <strong>(a) を (b) として読む場合。</strong>他者が作成したディレクトリを<strong>内容ごと削除</strong>します。これは回復できません。

したがって、失敗したら常に宛先を削除するという素朴な修正は、最初の不具合を解消すると同時に<strong>より深刻な不具合を生みます</strong>。

> 回復可能な中途半端さと、回復不能な削除は、等価ではない。

## 実装方針: 失敗位置の保持

採りうる方針は一つです。<strong>エラーの内容を参照することをやめる</strong>ことです。代わりに、<strong>どこで失敗したか</strong>によって判断します。これは操作自身が知っている情報であり、知っていながら捨てていたにすぎません。

そこで、コピー処理を<strong>確保する段階（claim）</strong>と<strong>内容を書き込む段階（fill）</strong>に分割しました。確保の呼び出し、すなわち `create_dir`、`create_new`、`symlink` より前で失敗したのであれば、宛先は自らのものになっていません。それより後で失敗したのであれば、そこにあるのは自らが書きかけたものです。エラーの種類に一切依存せず、位置のみによって決まる判定になります。

### 三値を採用した理由

最初の実装は bool でした。宛先を確保したか、していないかの二値です。これで十分であると考えていました。レビューにおいて、CodeRabbit と cubic の双方から同じ箇所を指摘されました。

先に述べた前提がここで関係します。フォールバックによる移動は、コピーしてから元を削除する処理です。その削除に用いる `remove_dir_all` は<strong>原子的ではありません</strong>。途中で失敗した場合、コピー元は<strong>既に一部が欠けた状態</strong>になっています。

私はこの失敗を、宛先は自らのものであると報告していました。すると新たに追加した後片付け処理が、その宛先、すなわち<strong>唯一の完全なコピー</strong>を削除しようとします。コピー元は一部が欠け、コピーは削除されるという結果になります。

<Callout title="変更自体が生んだリグレッション">
回復不能な削除を避けることを目的とした変更の中で、私は別の経路で回復不能な削除を作り込んでいました。しかも、直前のコミットで同一の理屈を明文化したばかりでした。
</Callout>

ここから導かれるのは、<strong>削除不可には二つの異なる理由がある</strong>という点です。`Nothing` は他者のものであるため、`WholeDestination` は唯一の完全なコピーであるためです。理由が正反対であるため、bool にまとめると区別が失われます。そこで三値としました。

同時に、述語の名称も変更しました。`took_the_destination()`（宛先を確保したか）ではなく、`left_a_partial_destination()`（作成途中のものを残したか）です。<strong>何を行ったかではなく、削除を許可する条件を名指しする</strong>名称にしました。前者の名称を採っていたために見落としが生じた、と考えています。

### パス名ではなくエントリ識別子による照合

`PartialDestination` であっても、まだ不十分です。削除してよいのは、そのパスに現在存在するものではなく、<strong>確保した時点のエントリ</strong>です。最初の節で述べた帰結の二つ目、すなわち同一のパスが異なるファイルを指しうるという性質が、ここで問題となります。

ツリーを書き込んでいる数秒の間に、別のプロセスが自らの作成途中のものを削除し、そこに自身のものを配置することができます。パス名のみを根拠に削除すれば、相手のものを削除することになります。それは、この変更が防ごうとしている事象そのものです。

そこで、確保した直後に `dev` と `ino` の組、すなわちデバイス番号と inode 番号の対を記録し、削除する前に照合します。inode 番号が一意なのは同一デバイスの中だけなので、デバイス番号と対にして初めてエントリの身元になります。照合が一致しなければ何も行いません。

<strong>ただし、これは窓を狭めるだけであり、閉じてはいません。</strong>その点も明記しておく必要があります。

- <strong>照合と削除は別々の呼び出しです。</strong>その間隙を突かれれば通過します。std には、開いているハンドルを経由してディレクトリツリーを削除する API が存在しません。
- <strong>inode 番号は再利用されます。</strong>作成途中のものを削除してから同名で作り直された場合、同一の番号が返されることがあります。その場合は区別がつきません。

<Callout title="テストの間欠的な失敗が示したもの">
二点目については、自ら記述したテストによって判明しました。照合のテストでは、他のプロセスの振る舞いを「作成途中のものを削除してから同名で作成する」という手順で再現していたのですが、この作り直しが<strong>確保した番号をそのまま取得する</strong>場合がありました。約 20% の確率で失敗します。

テストを、作成途中のものが存在するうちに別の場所で作成し、`rename` によって差し込む手順に変更しました。この手順であれば同一の番号になることはありませんし、実際のプロセスが行う操作としても自然な手順です。30 回連続で安定しました。

そして<strong>この不安定さは、照合そのものの限界を示す報告だった</strong>ため、その内容をドキュメントに記載しました。テストを修正して沈黙させることが、最も避けるべき対応です。
</Callout>

ファイル側については、確保に用いる `create_new` が<strong>開いたハンドルを返す</strong>ため、パスを再度 `stat` するのではなく、ハンドルから `fstat` する実装に変更しました。これは正確です。そのハンドルは、この呼び出しが作成したエントリそのものを指しているためです。ディレクトリ側は `mkdir` がハンドルを返さないため、パス経由の窓が残ります。残ることをコメントに明記しました。

### 未証明と証明済みの区別

もう一点、指摘を受けた箇所があります。照合を次のように記述していました。

```rust
if ENTRY_IDENTITIES_AVAILABLE && entry_identity(dst) != self.claimed {
    return Ok(());   // 一致しない場合は削除しない
}
delete_permanent(dst)
```

`claimed` が `None`、すなわち確保時に読み取れなかった場合で、現在も `None`、すなわちそこに何も存在しない場合、`None != None` は false になります。条件を通過して削除へ進みます。

私はこの点に気づいており、そこに何も存在しないのであれば削除は `NotFound` で失敗するだけであり無害であると判断していました。<strong>ただしそれは、パスが空のままであればという条件付きです。</strong>照合と削除は別々の呼び出しであるため、その間に他のプロセスが何かを作成すれば、それを削除します。一度も確保を証明できていない状態で、です。

条件を次のように書き直しました。

```rust
if ENTRY_IDENTITIES_AVAILABLE
    && !self.claimed.is_some_and(|claimed| entry_identity(dst) == Some(claimed))
{
    return Ok(());
}
delete_permanent(dst)
```

何を拒むかではなく、<strong>何を要求するか</strong>によって記述しました。両辺が実在する識別子であり、かつ一致すること。それ以外はすべて、削除しない側に分類されます。

二重の `None` が見落とされたのは、前者の書き方を採っていたためです。危険な組み合わせを列挙して排除する形の条件式は、<strong>列挙し忘れたものを通過させます</strong>。安全な条件を満たすことを要求する形であれば、想定しなかったものは排除される側に分類されます。同一の関数において、この違いにより二度誤りました。

## 削除の可否と、削除の要否

ここまでで答えたのは、<strong>削除してよいか</strong>という問いです。<strong>削除すべきか</strong>は別の問いであり、最初の修正では意図的に手を付けなかった箇所が三つ残っていました。新しい名前、すなわちまだ誰も待っていない名前に書き込む経路です。

そこでは、作成途中のものが残っても何も壊れません。ロールバックがその名前を待っていないためです。したがって正しさの問題ではなく、<strong>方針の問題</strong>になります。失敗したペースト自身の出力をどう扱うか、という問いです。

残す側に十分な理由はない、というのが結論です。

- 一覧には<strong>通常のフォルダとして並びます</strong>。途中で停止したことを示す表示はどこにもありません。
- そして<strong>名前を占有します</strong>。次に同じものをペーストすると、番号付けが既存の名前を避けるため `report (2)` になります。以後 `report` は残存部分のものとなります。

削除によって失われるのは、既に費やした時間だけです。<strong>再開する仕組みは存在しない</strong>ため、残しておいても次の試行は最初から書き直します。Finder も GNOME Files も削除します。

### 未解決の競合状態の扱い

身元の照合には、`stat` と削除が別々の呼び出しであるという窓が依然として残っています。レビューでもこの点を指摘されました。パス名による削除をやめ、残して報告する方針に変更してはどうか、という内容です。

この提案は採用しませんでした。<strong>残して報告することは、本節で解消したばかりの挙動そのもの</strong>だからです。残存部分が名前を占有し続けることは確実に発生する事象であり、一方の窓は、一度その名前の取得に失敗した別のプロセスが、二つのシステムコールの間隙で再び同じ名前を取得するという条件を要します。<strong>確実な悪化と、狭い競合状態を交換する取引</strong>になっています。

代わりに、この窓を閉じるために何が必要かを issue に記載しました。親ディレクトリの fd に対する `unlinkat`、ディレクトリの場合は `openat` によって降下する自前の再帰処理です。std にはいずれも存在しません。<strong>修正できないから記載しないのではなく、修正方法を記載して残しておく</strong>という方針です。

## 再現不能な条件の扱い

この不具合の中核部分は再現できません。コピーがツリーを書き込んでいる数秒の間に、別のプロセスが宛先ツリーの内部へ同名のエントリを作成する必要があるためです。他者の都合で起きる競合であり、テストが待てるものではありません。

移動については条件が変わります。同一ボリューム内なら rename 一回で完了し、コピーのコードは実行されません。ボリュームをまたげば実行されますが、CI のテンポラリディレクトリは単一のファイルシステム上にあるため、そこは通りません。実際 CI が通しているのは `copy_path_no_replace` の側であり（`the_fallback_move_claims_the_destination_before_writing_to_it` など）、`move_path_no_replace` がクロスデバイスのフォールバックへ落ちる経路そのものは通っていません。<strong>記述した環境で実行されないテストは、テストとして機能しません。</strong>

そこで、中核部分の代わりに<strong>それを決定している性質そのもの</strong>を固定しました。すなわち、確保の成否はどこで失敗したかによって決まり、エラーの種類によっては決まらないという性質です。

コピー元に Unix ドメインソケットを配置します。ソケットはファイルとして `open` できないため、コピーは必ず失敗します。しかも<strong>宛先を作成した後の、既知の一点で</strong>停止します。入れ子の衝突が該当するのと同じ側です。決定的に再現でき、両プラットフォームで実行されます。

後半で修正した分岐についても同様です。`WholeDestination` に到達するには、`rename` が別ボリュームであると報告し、<strong>かつ</strong>コピーが完走し、<strong>かつ</strong> `remove_dir_all` が途中で中断する必要があります。この三つをテンポラリディレクトリの中で同時に成立させることはできません。

そして、網羅できなかった範囲は PR とコードのコメントに記載しました。<strong>テストが存在しないことと、テストが存在しないと認識していないことは異なります。</strong>前者は判断であり、後者は事故です。

## 判断の基準

設計上の判断を一行にまとめると、次のようになります。

> コストが非対称であれば、扱いも非対称にする。

中途半端な状態は後から修正できますが、削除は修正できません。したがって、判断に迷う場合は触れない側を選択します。

ただし、これを徹底しすぎるとロールバックが機能しなくなります。それが<strong>当初の不具合そのもの</strong>でした。触れないことを既定とするだけでは不十分です。

したがって解は、触れるか触れないかの閾値を調整することではなく、<strong>判断できない領域そのものを減らすこと</strong>でした。判断に必要な情報を、失われる前に保持すること。エラーの種類からの推測をやめ、操作自身に報告させること。

さらに、記述の仕方に関する論点が三点あります。

- <strong>述語は、許可の条件を名指しする。</strong>確保したかではなく、削除してよいかを名前にします。
- <strong>条件式は、要求として記述する。</strong>危険を排除する形ではなく、安全を証明する形にします。
- <strong>分類を再利用する際は、それが答える問いをすべて確認する。</strong>その時点で念頭にある問いのみを立て直すと、同じ値の別の側面が見落とされます。

この三点は、レビューで指摘された事項のうち三件の<strong>直接の原因</strong>でした。名称と条件式と分類の扱い方が、見落としを許すかどうかを決定していたことになります。設計の適否を論じる以前の段階で、<strong>記述の仕方が誤りの余地を生んでいた</strong>ことになります。

最後に、本稿の要点を一文にまとめます。<strong>errno から状況を推測しているコードは、多くの場合、推測できないものを推測しています。</strong>その値は単一の整数であり、必要とする情報の大半は含まれていません。
