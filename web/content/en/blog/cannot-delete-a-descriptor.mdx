Suppose a program has a file open. It holds a descriptor — the number `open` handed back — and that number identifies, without ambiguity, one particular thing on the disk. Now the program wants to delete that thing.

It cannot. Not because the call is missing, but because **the request does not name anything**. Establishing why requires three things: what a path is, what a descriptor is, and what deletion operates on.

Everything below was measured on Linux 6.18 rather than recalled, and the output is quoted as it came back.

## Names and bodies

A directory is not a container. It is a table with two columns: a name, and a number.

The number is the inode number. Everything that is actually *about* the file — its size, its permissions, its modification time, and the references to the blocks holding its contents — lives on the inode. The directory holds only the name. An inode does not know its own name, and nothing in it points back to the directory that names it.

One caveat before the inode number starts doing work as an identity below: it is only unique within a single filesystem, and numbers are reused once freed. Every run in this article stays inside one directory on one filesystem, where comparing the number alone is sound. Code that compares entries for real pairs it with the device ID — `(st_dev, st_ino)` — which is what the cleanup at the end of this article actually stores.

That table is why the system call that deletes a file is called `unlink` rather than `delete`. It removes a link — one row of the table. The body is reclaimed only once nothing refers to it at all: no directory entry anywhere, and no open descriptor or memory mapping held by a running process.

A program creates two names for one body, opens a descriptor on one of them, and removes that name. This is what it printed:

```text
one/a   inode=1908771
one/b   inode=1908771
fd 3    inode=1908771

unlink('one/a')
  one/b exists   True
  one/b contents 'payload'
  fd 3 inode    1908771
  fd 3 read     b'payload'
```

## Why "delete this descriptor" has no meaning

Now put those two facts together.

A descriptor names a body. `unlink` removes a name. In the run above, the body had two names; after the `unlink` it has one. Asked instead to "delete the descriptor", the kernel would have to determine **which of the names to remove**, and the request does not supply that.

This is not a gap in the API. It is a request that does not resolve to an action. Removing one of three names does not leave a file partly deleted, and defining the operation as removing all of them would make it a substantially more destructive call than the caller requested.

<Callout title="It is not merely absent on Linux">
FreeBSD does offer `funlinkat`, and it is worth seeing what it actually does: it takes *both* a descriptor and a name, and removes the name only if it still refers to the same file as the descriptor. It is a **verified** unlink, not an unlink by descriptor. The name is still the thing removed.

Linux has no equivalent. `linkat` with `AT_EMPTY_PATH` can give a descriptor a new name, which looks like a way in, but it requires `CAP_DAC_READ_SEARCH` — effectively root — so it is not available to an ordinary program.
</Callout>

So on a Unix-like system every removal names something. And naming something means resolving a path.

<Callout title="Windows resolves the ambiguity differently">
The qualification in that sentence is deliberate, and the exception is worth knowing. Windows does permit deletion through an already-open handle: `SetFileInformationByHandle` with `FileDispositionInfo` takes no path, only a handle opened with `DELETE` access.

This is not a counterexample but an alternative resolution. The ambiguity exists on Windows as well, since NTFS supports hard links, and Windows resolves it by having the handle retain the name it was opened through, so that deleting through the handle removes that name. POSIX does not record this association, which is why the request has no referent under POSIX and does have one under Windows. The difference is a design decision rather than a property of filesystems in general.

(Documented behaviour rather than measured: everything else in this article was run on Linux 6.18, and this was not.)
</Callout>

## What a path resolves, and what a descriptor refers to

Resolving a path is a sequence of lookups. `work/report` means: look up `work` in the current directory, obtain an inode, verify it is a directory, then look up `report` inside it. Each component is resolved against whatever the filesystem contains *at that instant*.

The kernel does not cache that resolution between calls. Two successive calls on the same path perform two independent resolutions, and the filesystem may change in between.

A descriptor works the other way. It refers to one specific inode, resolved once and retained. Changes to the names above it do not affect what it refers to.

Hold a descriptor on a directory, then rename that directory out from under the path:

```text
renamed work -> work2
  unlink('work/report')        -> ENOENT
  unlinkat(dirfd,'report')     -> ok
  work2/report gone            -> True
```

The path no longer resolves, because there is no `work` any more. The descriptor is unaffected: it never referred to the name `work`, only to the directory itself.

## When another program takes the name

The rename above only caused the call to fail. Changing one detail causes data loss instead: after the directory is moved aside, another program creates a new directory at the old name.

```text
path  w/report   inode=1908833 'THEIRS'
dirfd report     inode=1908802 'mine'

unlink('w/report')   -> ok
  removed           'THEIRS'
  their file left?  False
```

The program requested the deletion of its own file. The path was correct at the time it was checked. By the time `unlink` executed, the same path referred to another program's file, and that is the file that was removed.

Nothing here depends on unusual conditions. The program did not misuse the API; it used a path-based removal, and the filesystem changed between the check and the call. This is the general form of a large class of defects — check a path, then act on it, and lose the race in between — and it is why the kernel provides a second way to designate the target.

## What the `*at` family shortens

`openat`, `unlinkat`, `renameat`, `fstatat`, `mkdirat`: each takes a directory descriptor plus a name, and resolves the name relative to that descriptor instead of from the root.

The gain is exact. Resolving `a/b/c/d/report` by path is five lookups, any of which can be swapped between one call and the next. Holding a descriptor on `a/b/c/d` and asking for `report` is **one**. Every component above the last stops being something an attacker — or an ordinary concurrent program — can redirect.

What it does not do is remove that last lookup. `unlinkat(dirfd, "report", 0)` still resolves the name `report` inside the pinned directory, and something can still replace it in the instant between checking and removing. That is the floor, and it is the same floor as the first section: removal operates on names.

## The asymmetry in `rmdir`

That remaining lookup appears to leave the problem unchanged. For directories it very nearly does not, because of one existing restriction.

`rmdir` refuses to remove a directory that has anything in it:

```text
  rmdir('full')   -> ENOTEMPTY
  rmdir('empty')  -> ok
  unlink on a dir -> EISDIR
```

So a program that wants to remove a tree safely can do this: walk down through descriptors, emptying as it goes — none of which consults the name again — and only at the very end ask `rmdir` for the name. By then the directory it means is empty.

If something replaces the name in that final instant, `rmdir` can only succeed against **another empty directory**. The worst case changes from removing another program's populated tree to removing another program's empty directory. That is still a loss, but a materially smaller one, and it follows from a restriction that already existed.

For a file there is no equivalent restriction. `unlink` removes whatever is at the name. The window is two system calls wide, and it is real.

<Callout title="Stated precisely">
This narrows the window; it does not close it. A design that claims to remove only what it created, on Linux, claims a guarantee the platform does not provide. Stating where the remaining exposure lies is more useful to a later reader than asserting a guarantee that does not hold.
</Callout>

## The flags

Opening an entry through this machinery is not quite `open(path, O_RDONLY)`. Four flags come into it:

- `O_DIRECTORY` — fail unless it really is a directory, rather than opening something else and discovering it later.
- `O_CLOEXEC` — do not leak the descriptor into a child process.
- `O_NOFOLLOW` — do not follow a symbolic link at the final component.
- `O_NONBLOCK` — return from `open` rather than waiting on the thing being opened.

`O_CLOEXEC` is the only one that applies unconditionally; every open here requires it. `O_DIRECTORY` applies to the anchor open and only there, since the entry open exists in order to determine the entry's type. The remaining two require more care, because both appear to belong on the anchor open and neither does, for different reasons. `O_NOFOLLOW` on the anchor open prevents a legitimate case; `O_NONBLOCK` on the anchor open has no effect.

Consider `O_NOFOLLOW` first, since applying it in the wrong position still appears correct.

It belongs on **the entry being removed**, where following a link would allow a link to substitute for its target. It does **not** belong on the parent directory. A user may legitimately have navigated into a directory reached through a symbolic link, and refusing to open it provides no protection while abandoning the operation. Following the link there is safe for a separate reason: the identity check on the entry passes only when the directory reached is the one that actually holds it.

<Callout title="The errno moves when you add a flag">
Verifying the above produced a result worth recording. The error reported for a symbolic link under `O_NOFOLLOW` depends on whether `O_DIRECTORY` is also set:

| flags | `adir` | `afile` | link to dir | link to file | dangling link |
| --- | --- | --- | --- | --- | --- |
| `O_RDONLY` | ok | ok | ok | ok | `ENOENT` |
| `O_RDONLY\|O_NOFOLLOW` | ok | ok | `ELOOP` | `ELOOP` | `ELOOP` |
| `O_RDONLY\|O_DIRECTORY` | ok | `ENOTDIR` | ok | `ENOTDIR` | `ENOENT` |
| `O_RDONLY\|O_DIRECTORY\|O_NOFOLLOW` | ok | `ENOTDIR` | `ENOTDIR` | `ENOTDIR` | `ENOTDIR` |

The same condition — a symbolic link at the name, with `O_NOFOLLOW` set — reports `ELOOP` on the second row and `ENOTDIR` on the fourth. `O_DIRECTORY` is evaluated first and determines the result before `O_NOFOLLOW` is considered.

Code that treats "it was a link, so remove it without opening it" as a case must therefore accept **both** errors. A comment naming only one describes a particular configuration rather than the rule.
</Callout>

`O_NONBLOCK` fails in the other direction. The reasoning for applying it to the anchor open is plausible: a FIFO at that name would cause `open` itself to wait for a writer that may never arrive, and an operation that blocks indefinitely is worse than one that fails. The reasoning is sound, but the conclusion does not follow, because `O_DIRECTORY` is already present:

| flags | a FIFO with no writer |
| --- | --- |
| `O_RDONLY` | blocks indefinitely |
| `O_RDONLY\|O_NONBLOCK` | opens |
| `O_RDONLY\|O_DIRECTORY` | `ENOTDIR`, immediately |
| `O_RDONLY\|O_DIRECTORY\|O_NONBLOCK` | `ENOTDIR`, immediately |

The first row is the hazard, the second is the fix, and the third shows that the fix is already supplied by another flag. `O_DIRECTORY` rejects the FIFO before it can block, so on an open that carries it, `O_NONBLOCK` has no remaining effect.

The flag does apply to the open of **the entry being removed**, which is also where `O_NOFOLLOW` belongs. That open cannot carry `O_DIRECTORY`, for the reason given above: the entry may be a file, a directory or a FIFO, and determining which is the purpose of the open. `O_DIRECTORY` would resolve that by rejecting everything that is not a directory. The protection must therefore come from `O_NONBLOCK`, which there is the only thing preventing an `open` that does not return.

Both flags thus apply to the same open, for the same reason: the anchor is known to be a directory, whereas the entry's type is unknown until it is opened.

One qualification, since the code at the end of this article is quoted in full: the anchor open in Nohrs sets `O_NONBLOCK` regardless. This is deliberate, and its comment records the reason. "Redundant given the flag beside it" and "incorrect" are distinct claims, and the argument above establishes only the first. The cost of a redundant flag is one bit in a bitmask; the failure it would prevent, were the reasoning about evaluation order wrong, is a file manager that blocks indefinitely during a paste.

One further value not to rely on is the `d_type` field returned by `readdir`, which reports whether an entry is a directory. Several filesystems set it to `DT_UNKNOWN` and require the caller to check. Passing `O_DIRECTORY` to `openat` performs that check and returns, in the same call, the descriptor a recursive walk requires next.

## The case this came from

The preceding sections describe a defect in [Nohrs](https://github.com/noh-rs/nohrs), the file manager this blog belongs to. The affected operation is the cleanup performed after a paste fails partway through.

When a copy into a new name fails partway, the partial result must be removed. Retaining it is not viable: it appears in the listing as an ordinary directory with no indication that it is incomplete, and it occupies the name, so every subsequent retry is placed at `report (2)`. The cleanup must, however, remove **only what this operation created**, never an entry that merely shares the name.

The previous implementation performed the decision and the removal as two separate steps: a `stat` to confirm that the destination was this operation's own partial result, then `remove_dir_all(dst)`, which resolved `dst` by pathname a second time. This is the gap described earlier in this article, present in shipped code. Two resolutions, one decision, and between them another writer can place a different entry at that name; the `stat` confirms ownership, and the removal then operates on whatever is present at that moment.

The window is narrow. Reaching it requires a second writer to claim the same name between two system calls, having already lost that name once. It was narrow enough that removing by path was a deliberate choice for a period, because the alternative — retaining the partial result and reporting it — is not a race condition but a certainty.

The fix follows the `*at` pattern: resolve the parent once, retain the descriptor, and perform everything else relative to it.

```rust
let (parent, name) = parent_and_name(dst)?;
let parent = open_directory(parent)?;
// Hands the entry back only while it is still the one that was claimed.
let Some(entry) = open_claimed(&parent, name, claimed)? else {
    return Ok(());
};
if entry.metadata()?.is_dir() {
    empty_dir(&entry)?;
    already_gone_is_fine(unlinkat(&parent, name, AtFlags::REMOVEDIR))?;
} else {
    already_gone_is_fine(unlinkat(&parent, name, AtFlags::empty()))?;
}
```

Three details there follow from the preceding sections rather than from preference:

- The identity comparison is performed **through the open descriptor**. Performed by name it would provide nothing, being one further lookup subject to the same race.
- `ENOENT` from the removal is treated as success. The entry is gone, which is the requested outcome, and another process reached it first; treating it as an error would abandon the cleanup because of the race the cleanup exists to tolerate.
- The final `unlinkat` still takes `name`. It resolves one component, against a directory this code holds and which cannot be substituted. That is the limit of what the technique provides.

## Narrowing and closing

The claim in the title is stronger than "Linux is missing a call". "Delete this descriptor" is not a feature request, because a descriptor refers to a body, deletion operates on names, and one body may have several.

The consequences are as follows:

- Every removal resolves a name, so every removal has a window.
- A retained directory descriptor eliminates every part of the resolution except the final component.
- For directories, `rmdir` refusing a non-empty target limits what that remaining window can cost.
- For everything else the window remains, and the appropriate response is to record where it is.

Presenting the technique as a solution would be inaccurate. Descriptor-relative work is strictly preferable to re-resolving a path, and it is what the `*at` calls exist for, but the final lookup is not an oversight in the interface. It is what deletion consists of.
