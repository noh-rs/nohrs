Nohrs maintains a search index of its own, so that whether a file can be found does not
depend on whether the operating system's indexer was permitted to examine the directory the
work is kept in. The index is a [tantivy](https://github.com/quickwit-oss/tantivy) index,
and tantivy admits exactly one writer across all processes.

The initial arrangement was the simplest available: the application opened a writer at
launch and held it until it quit. This suffices until something else requires write access.
Invoking `noh index build` from a terminal while the application is open is refused — by
design, by tantivy, correctly, and to no purpose. The index had become the property of
whichever process reached it first.

The question is therefore where the writer belongs.

## The launcher as a candidate

The immediate answer is the launcher. Nohrs provides a global hotkey, so a process is
resident whether or not a window is open, and placing the writer there introduces nothing
that is not already running.

This answer is incorrect, and the reason merits statement, because it does not concern
residency.

The launcher operates under a latency budget: under 100ms from hotkey to window, under 50ms
from keystroke to results. Indexing is work of an entirely different kind — throughput-bound,
IO-heavy, and due to become heavier still. At present it is a tantivy writer with a 50MB
heap and its merge threads; once vector search is addressed, an embedding model of several
hundred megabytes. Two such workloads in one address space share an allocator, a thread pool
and a fate. An out-of-memory kill during indexing removes the hotkey with it.

A second and narrower fact applies: **the launcher does not read that index**. Its keystroke
path consults an in-memory index of file *names*, whereas the tantivy index answers content
queries. Co-location yields nothing.

## What the objection to daemons concerns

Daemons are disliked, and the Nohrs README states "no dependency on the OS search daemon",
which would read poorly beside a login item of its own.

The objection, however, is not to daemons as such. It is to processes that start at login,
consume resources invisibly, offer no means of being located or stopped, and require
registration with launchd or systemd in order to exist. A process that starts when it is
wanted and exits when it is not is a different matter, and processes of that kind are run by
the dozen without complaint.

`nohrs-indexd` is of the latter kind. Nothing installs it. The first process that requires
the index to be kept current starts it, and it exits once its last client has been absent for
ninety seconds. The launcher is resident in any case, so in practice the daemon's lifetime
coincides with the application's: quitting nohrs ends both. There is nothing to locate,
nothing to stop, and nothing added to the login items.

One question remains, and it is the substantive one.

## Determining when to exit

"Exit when the last client departs" describes `Arc`. One is held per client and dropped when
that client leaves, and the final drop terminates the process. Within a single address space
this is three lines of Rust.

Across processes it is not, and `Drop` is the reason.

1. **`Drop` does not run on `SIGKILL`**, nor on an out-of-memory kill, a segfault, or a power
   failure. A refcount that is correct only when clients exit in an orderly fashion is a
   refcount that is incorrect precisely where it is required.
2. **`Drop` does not cross an address space.** A destructor in the client cannot decrement a
   counter in the daemon.

A heartbeat conceals the first and does not address the second. Monitoring client pids races
against pid reuse. `PR_SET_PDEATHSIG` binds a child to its parent, whereas this daemon
outlives whatever started it by design: the starter may be a one-shot command that exits a
second later.

The resolution is that the kernel already performs this accounting, and with precisely these
semantics. **A unix socket connection is refcounted by the kernel**, and when a process ends
— by whatever means — its descriptors are closed and the other end reads end-of-stream. "How
many clients are alive" and "how many connections are open" are the same quantity, and that
quantity is correct under `kill -9` because nothing in userspace was asked to maintain it.

The model is therefore `Arc`, the implementation is the kernel, and Rust supplies the shape
on both sides.

## The shape of the lease

On the daemon's side the lease is an ordinary RAII type, and the one design decision that
carries weight is that it is **taken by value by the function that serves the connection**:

```rust
/// Serves one client until its end of the socket closes.
///
/// `lease` is taken by value and never handed on: this function returning is what
/// releases it, and this function returns when the client's end closes — which the
/// kernel does whatever became of the client.
fn serve_client(&self, stream: UnixStream, lease: Lease) -> Result<()> {
    let mut reader = BufReader::new(stream);
    while let Some(request) = read_frame::<Request>(&mut reader)? {
        // ...
    }
    Ok(()) // the lease drops here
}
```

There is no means of serving a client without holding a lease, and none of retaining one
after the serving ends. Release is not a step that can be omitted, because it is not a step.

## Why the count is not an `Arc`

A grace period was required. A `noh index build` in a shell script, followed a second later
by another, should not incur the cost of starting a second daemon, so the daemon waits ninety
seconds after the last client departs before it goes.

This breaks the pure last-drop formulation, and the reason merits precision: `Arc` reports
that the count reached zero and then discards everything, **including the means of recalling
whatever that set in motion**. A client arriving during the countdown must cancel it, and
nothing remains with which to do so.

The count and the moment it reached zero are therefore held explicitly:

```rust
struct State {
    live: usize,
    /// When the count last reached zero, and `None` while anyone holds a lease.
    /// This is what lets a client cancel a shutdown that is pending.
    idle_since: Option<Instant>,
}
```

and the wait is a condition variable rather than a poll, so a daemon with nothing to do costs
nothing to retain:

```rust
pub fn wait_until_idle(&self) {
    let mut state = self.lock();
    loop {
        match state.idle_since {
            // Somebody is connected. Nothing to do until that changes.
            None => state = self.wait(state),
            Some(since) => match self.grace.checked_sub(since.elapsed()) {
                None => return,
                Some(remaining) => state = self.wait_for(state, remaining),
            },
        }
    }
}
```

Extracting this as a type of its own has the property that it can be tested without a socket
in sight: take a lease, drop it, and assert on when the wait returns.

<Callout title="The other half">
  Two clients that both require a daemon will both attempt to start one, and the loser must
  stand down. The determination cannot rest on the presence of a socket file, since a socket
  file outlives the process that created it. An advisory lock (`flock`), held for the
  daemon's entire life, decides instead — and the kernel releases *that* when the holder
  dies, by whatever means it dies. A pid file would require second-guessing; a lock cannot
  misreport.
</Callout>

## The condition that makes a daemon acceptable

One invariant performs most of the work here: **searches do not pass through the daemon**.

Readers open the tantivy index directly, from any number of processes at once, because
reading requires no lock. The socket carries write requests, enquiries about state, and
notices that something has been committed. It never carries a query.

This is not an optimisation. It is what makes the daemon *optional infrastructure* rather
than a dependency. If it is down, wedged, or a version behind, searches still answer — from
an index somewhat staler than it would otherwise be. No failure mode exists in which a query
returns an error because a background process the user is unaware of is in difficulty. The
same condition also permits the component to be introduced in stages, and withdrawn again,
with the read path untouched throughout.

## Testing termination without notice

The test that matters cannot be written in-process, since the claim concerns what occurs when
a process executes no code at all on the way out. A small helper binary therefore connects
and sleeps, and the test kills it:

```rust
let mut held = Command::new(env!("CARGO_BIN_EXE_holds_a_connection"))
    .arg(&fixture.endpoint.socket)
    .spawn()
    .unwrap();
until("the killable client to be counted", || {
    probe.status().unwrap().clients == Some(2)
});

// From here the killable client is the only thing holding the daemon up.
drop(probe);
std::thread::sleep(GRACE * 2);
assert!(!gone(&fixture.endpoint.socket), "the daemon stopped while a client still held it");

held.kill().unwrap();
until("the daemon to stop", || gone(&fixture.endpoint.socket));
```

The first wait is what earns its place. Without it the test passes when the helper fails to
connect at all — which is what occurred on the first run, and is the kind of green that
establishes nothing.

## The resulting arrangement

The writer and the file watcher now reside together in `nohrs-indexd`, which gives "is the
index keeping up with the filesystem?" a single place to be asked. Not a single answer: the
daemon being up does not entail that the watcher is working. It outlives a watcher it failed
to install, deliberately, because losing live updates costs freshness and the pass at the
next start recovers it. `noh index status` therefore states which case obtains — `watching`,
`running but not watching`, or not running at all — rather than leaving it to be inferred.
Nothing starts at login, nothing is registered with the system, and the only thing a person
has to quit is nohrs.

When vector search arrives and indexing begins to require hundreds of megabytes of model
weights, it has somewhere to go that is not the process holding the hotkey.
