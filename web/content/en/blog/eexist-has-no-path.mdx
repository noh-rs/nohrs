In a file manager, you paste a folder onto another folder with the same name. It asks whether to replace, and you say yes. Someone does this every day, in Finder and in Explorer alike.

Implement it properly and you hit a question: **when it fails partway, what may be deleted and what must not be?** And because of how the OS is built, the information needed to answer it **is already gone by the time the failure reaches you**.

What follows is a record of dealing with that in Nohrs, but the substance is general — you do not need to know this product to read it. Every prerequisite is built up below.

## The separation of name and body

First premise. A directory is *not a box holding files*. A directory is nothing but **a table of name → number**.

The number is the inode number. Everything file-like — the contents, the size, the modification time, the permissions — lives on the inode. Only the name lives in the directory. Which means, from the other side: **an inode does not know its own name**.

This structure is why the system call that deletes a file is named `unlink`. What it removes is the name. The body is reclaimed only once **nothing refers to it at all** — no directory entry, and no open descriptor or mapping held by a running process. A file whose last name is gone while a process still has it open keeps its contents until that process closes it.

Two consequences fall out, and both come back repeatedly below.

- **Different paths can name the same file.** "The source and the destination have different paths, so this is safe" does not hold.
- **The same path can name a different file.** The path you looked at a moment ago and the path you are about to write to are not necessarily the same thing.

The second one is the heavy one. **A path is a name, not the identity of what it names.** There is a step later where an entry's identity is checked before deleting it; this is where that requirement comes from.

## The atomicity of rename(2) and its silent replacement

`rename(2)` is the system call that moves a file. Given the section above, though, all it does is **rewrite the table**. Not one byte of data moves. That is why a 100GB file moves instantly — within one filesystem.

What matters is that the rewrite is **atomic**. No other process ever observes a halfway state. The name points at the old number or at the new one, and there is nothing in between.

### Why silent replacement is specified behaviour

`rename` replaces whatever is already at the destination without asking. This appears hazardous, but it is deliberate, and an important mechanism depends on it.

Consider how a text editor saves over a file. The simplest procedure is to open `notes.txt`, empty it, and write the new contents.

```text
# The naive overwrite. If the power goes out partway...
open("notes.txt", O_WRONLY|O_TRUNC)   <- the contents are gone at this instant
write("first half of the new text")   <- ★ stops here

# What is left: "first half of the new text", and nothing else.
# Neither the old contents nor the new ones exist anywhere.
```

`O_TRUNC` empties the file as it opens it. The old contents are already lost before a single byte of the new ones is written.

The correct sequence writes the whole thing under another name and swaps it in with `rename`.

```text
# Atomic save. Stopping anywhere leaves nothing broken.
write("notes.txt.tmp", the whole new contents)   <- notes.txt is untouched if this dies
fsync("notes.txt.tmp")
rename("notes.txt.tmp", "notes.txt")             <- swaps atomically
fsync(directory of "notes.txt")                  <- and the swap itself survives a crash

# notes.txt is either the old contents or the new ones. No halfway state exists.
```

The last line is the one most often left out. `rename` is atomic against other processes the moment it returns, but the directory entry it rewrote is not necessarily on disk: without that `fsync`, a crash can come back with the old name still in place. Atomic and durable are separate properties.

All of it works **because `rename` does not refuse to replace**. If it did, the sequence would need a delete first, and a crash in the gap between the delete and the rename would take the file with it.

### Renames that refuse to replace

There are also cases in which replacing is precisely the wrong behaviour. Restoring from the trash must not quietly flatten whatever now sits at the original location. Neither must a paste to a name that was supposed to be free.

So there is a rename that refuses to replace: `renameat2(RENAME_NOREPLACE)` on Linux, `renamex_np(RENAME_EXCL)` on macOS. "Move if the destination is free, fail with `EEXIST` if it is taken" — atomically.

### Constraints imposed by the filesystem driver

This requires care. The flag travels through the kernel's common layer and ends up at **the individual filesystem's driver**, and the driver does not necessarily implement it.

- **A kernel with no `renameat2` at all** (Linux before 3.15) → `ENOSYS`
- **A filesystem whose driver does not take the flag** → `EINVAL`. The syscall has existed since 3.15, but `RENAME_NOREPLACE` reached many filesystems only in 4.9.
- **non-APFS volumes on macOS** → `ENOTSUP`

The distinction matters when reading the errno: `ENOSYS` is the kernel saying the call does not exist, `EINVAL` is a driver saying it will not take that flag.

<Callout title="What overlayfs actually does, measured">
The first draft of this post named overlayfs here as the filesystem that returns `EINVAL`. Review questioned it, so I measured, and it was wrong.

overlayfs presents several directories stacked as one. The lower layer is read-only, writes collect in the upper layer, and the viewer sees only the merged result. Changing a file that lives in the lower layer copies it up to the upper one first (copy-up), and that copy is what is used from then on. This is the relationship between a Docker image and a container, and it is usually what a container's working directory sits on.

Mounting an overlayfs on Linux 6.18 and calling `renameat2(RENAME_NOREPLACE)` directly:

| operation | result |
| --- | --- |
| destination free | success |
| destination taken | `EEXIST` |
| moving a directory that lives in the lower layer | `EXDEV` |

The first two rows are what ext4 does. The flag is accepted. And the third, `EXDEV`, takes an entirely different branch from `EINVAL`. overlayfs does reach the fallback, but **through the cross-device branch, not as an unsupported flag**.

**That `EXDEV` does not mean anything was crossed, though.** In the measurement above, the source and the destination are both inside the same overlayfs mount. `EXDEV` nominally means "cross-device link", but here it is overlayfs saying "I cannot carry out this rename myself; do it by copying". The code is right to act on it — the fallback is exactly the response being asked for. Reading it as "the user moved across volumes" is not.

Inferring a situation from an errno gets it wrong: that is this post's subject. The post got it wrong once in a line written without checking, and then again in the sentence correcting it — calling `EXDEV` proof of a filesystem crossing, which review caught too. An errno is a single integer, and what it means is up to the driver.
</Callout>

A no-replace rename is therefore useful where available, but **must not be assumed to exist**. Where it is missing, a fallback is required. The simplest fallback is to **copy, then delete the original.**

This is where a **move** can end up. Worth being precise about, because it is easy to conclude that ext4 and APFS are exempt from everything below: a move **within one volume** does finish in a single rename, and the fallback never runs.

A **copy** has no such shortcut. There is no rename that duplicates a tree, so a copy always walks it, claiming every entry as it goes — on ext4 and APFS exactly as anywhere else. So the problem below reaches an ordinary copy-paste everywhere, and reaches a move on `EXDEV` — another volume, or a driver declining the rename as overlayfs does for a lower layer — or where the no-replace rename is missing.

<Callout title="Note: an operation that is not atomic">
One further operation is **not** atomic. `remove_dir_all`, which deletes a whole directory tree, removes the files inside one at a time. If it fails partway, **the tree is left partly removed.** This property becomes significant in a later section.
</Callout>

## Claiming in place of check-then-write

The following is the shape of code written first.

```rust
if !dst.exists() {        // <- check
    write(dst, data);     // <- use
}
```

**Between** those two lines, another process can create `dst`. And `write` will flatten it.

This is TOCTOU — time-of-check to time-of-use — a classic race. It assumes a fact observed at check time still holds at write time.

It may appear that no other process could enter so small a gap, but the gap is not necessarily small. In the middle of copying a tree of tens of thousands of files, **that window stays open for seconds or minutes**. Sync clients, backup tools, build scripts, and the application's own second window are all candidates.

The fix is to stop checking. Use calls that **succeed if they took the name and fail if it was taken** instead.

- `open(O_CREAT|O_EXCL)` — create a file; `EEXIST` if it exists
- `mkdir` — create a directory; `EEXIST` if it exists
- `symlink` — create a symlink; `EEXIST` if it exists

In each, "look whether it exists" and "create it" are one thing inside the kernel, with no room to interleave. Call that **claiming**.

Every no-replace copy and move in Nohrs is written this way. And it claims **every entry in the tree**, not just the root — because during the seconds it takes to write a tree, somebody can create a colliding name inside it.

Why can they not be told apart? Because errno is **just an integer**. `EEXIST` is 17. "Failure number 17 occurred" is the whole of what comes back from the kernel. Which path it happened at is nowhere in it.

Rust's `std::io::Error` carries no path either, when it comes from `std::fs`. Passing errors upward with `?` for convenience, **the information about where it failed has been thrown away**.

### The asymmetry of the misreading cost

Confusing the two produces the following results.

- **Reading (b) as (a)** — which is what the code did — leaves our own half-copy in place as "somebody else's". The rollback then fails because something is in the way, and the user is left with **a broken destination and their original at a hidden path**. No data is lost, but there is no way to tell that from looking.
- **Reading (a) as (b)** — deletes a directory somebody else created, **contents and all**. There is no undoing that.

Which is why the naive fix — always delete the destination on failure — fixes the first bug and **opens a worse one**.

> A recoverable mess and an unrecoverable deletion are not equivalent.

## Implementation: preserving the point of failure

Only one approach is available: **stop inspecting what the error says.** Decide on **where it failed** instead — something the operation itself knows, and was throwing away.

So the copy is split into a **claim** stage and a **fill** stage. Fail before the claiming call — `create_dir` / `create_new` / `symlink` — and the destination never became ours. Fail after it, and what is there is our own half-written work. The test depends on position alone, and not at all on the kind of error.

And a failure now returns what it left behind, alongside the error.

```rust
pub enum Leftover {
    Nothing,             // never taken — someone else's entry
    PartialDestination,  // our half-written work; the source is intact
    WholeDestination,    // the copy landed; only removing the source failed
}
```

### The rationale for three values

The first implementation was a bool — whether the destination had been taken. I considered that sufficient. In review, CodeRabbit and cubic both pointed at the same place.

The property noted earlier now applies. The fallback move is copy-then-delete-the-original, and the `remove_dir_all` performing that deletion **is not atomic**. Fail partway and **the source is already partly gone**.

I was reporting that failure as "the destination is ours". So the cleanup I had just added would go and delete that destination — **the only complete copy there was**. The result is a source with parts missing and a deleted copy.

<Callout title="A regression introduced by the change itself">
Inside a change whose purpose was to avoid unrecoverable deletions, I had created an unrecoverable deletion by another route — having written out that exact reasoning one commit earlier.
</Callout>

This showed that **"hands off" has two distinct reasons**. `Nothing` is somebody else's. `WholeDestination` is the only complete copy. The reasons are opposites, so a bool collapses them. Hence three values.

I renamed the predicate at the same time: not `took_the_destination()` but `left_a_partial_destination()`. **Name the condition that permits the deletion, not the thing that happened.** The earlier name is what allowed the oversight, and I regard it as the cause.

### Verification by entry identity rather than pathname

`PartialDestination` is still not enough. What may be removed is not "whatever is at that path" but **the entry we claimed**. The second consequence from the first section — the same path can name a different file — bites here.

During the seconds it takes to write a tree, another process can delete our half-copy and put its own thing at that name. Delete by pathname and we delete theirs. Which is the very thing this change exists to prevent.

So the `dev`/`ino` pair is recorded right after the claim and compared before deleting. No match, no deletion.

**This narrows the window without closing it, though,** and that needs writing down too.

- **The check and the removal are separate calls.** Anything aimed at the gap gets through. Nothing in `std` removes a directory tree through an already-open handle.
- **Inode numbers get reused.** Remove the half-copy and recreate it under the same name, and the same number can come back. Then the two are indistinguishable.

<Callout title="What the intermittent test failure indicated">
The second was established by my own test. It played the other process as remove-then-create at the same name — and the recreation sometimes got handed the very number that had been claimed. A 20% failure rate.

I changed the test to build the replacement elsewhere while the half-copy is still alive and `rename` it into place. That can never land on the same number, and it is also what a real process does. Thirty consecutive runs were stable.

And because **the flakiness was a report about the limits of the check itself**, it went into the documentation. Correcting the test and saying nothing would have been the worst outcome.
</Callout>

For the file branch, `create_new` — the call that claims — **returns an open handle**, so the identity is read with `fstat` through that handle rather than by `stat`ing the path again. That one is exact: the handle names the entry this call created. The directory branch gets no handle from `mkdir`, so the path-shaped window remains there. That it remains is written in the comment.

### The distinction between unproven and proven

One further review finding. The comparison was written as follows.

```rust
if ENTRY_IDENTITIES_AVAILABLE && entry_identity(dst) != self.claimed {
    return Ok(());   // no match -> do not delete
}
delete_permanent(dst)
```

If `claimed` is `None` (unreadable at claim time) and the current identity is also `None` (nothing is there), then `None != None` is false. The condition is slipped past and the deletion proceeds.

I had noticed this and judged it harmless: nothing is there, so the deletion merely fails with `NotFound`. **That holds only while the path stays empty.** The check and the deletion are separate calls, so if somebody creates something in between, that is what gets deleted — with the claim never once proven.

Rewritten:

```rust
if ENTRY_IDENTITIES_AVAILABLE
    && !self.claimed.is_some_and(|claimed| entry_identity(dst) == Some(claimed))
{
    return Ok(());
}
delete_permanent(dst)
```

Write what is **required**, not what is rejected. Both sides must be real identities, and they must match. Everything else falls on the do-not-delete side.

The double `None` could hide because of the first form. A condition that enumerates dangerous combinations and rejects them **lets through whatever you forgot to enumerate**. A condition that demands a safe one be met puts everything unanticipated on the rejected side. The same function demonstrated this twice.

## Permission to delete, and the decision to delete

What was answered above is **may this be deleted**. **Should it** is a different question, and three call sites were deliberately left alone in the first fix: the paths that write to a *fresh* name — one nothing is waiting on.

A half-copy left there breaks nothing, because no rollback is waiting to come back to that name. So it is not a correctness question but **a policy one**: what should happen to a failed paste's own output?

There is insufficient reason to keep it.

- It **appears in the listing as an ordinary folder**, with nothing anywhere to say it stopped partway.
- And it **takes the name.** Paste the same thing again and the numbering steps around what is sitting there, so it lands at `report (2)` — and `report` belongs to the wreckage from then on.

Removing it costs only the time already spent. **There is no resume**, so keeping it does not save the retry a single byte of work. Finder and GNOME Files both remove it.

### Two questions answered by one value

At this point the same location produced a second error of the same kind.

When I added the cleanup, I thought about `WholeDestination` purely in terms of **visibility**: the destination is the name the user asked for, so unlike a hidden scratch path nothing has gone missing, and therefore no logging earns its place.

That reasoning is correct, but it stops one step short. Returning it as an error also means the source **goes back into the retry queue**. And the retry finds the destination name taken — **by the entry this very call just wrote.**

### Handling of the remaining race

The identity check still has that window where the `stat` and the deletion are separate calls. Review pointed at it: stop deleting by pathname, and fall back to retaining and reporting instead.

The proposal was not adopted. **Retaining and reporting is precisely the behaviour this section removed.** The wreckage holding the name is a certainty; the window needs another process, having already lost the race for that name once, to take it again in the gap between two system calls. This amounts to **trading a certain regression for a narrow race**.

What I did instead was write down what closing it takes, in an issue: `unlinkat` relative to a parent directory fd, and for a directory a hand-written recursion descending through `openat`. `std` offers neither. The policy is not to omit what cannot be fixed, but to **record how it would be fixed and leave that record in place**.

## Handling conditions that cannot be reproduced

The central case of this defect cannot be reproduced. It needs another process to create a colliding name inside the destination tree during the seconds the copy is writing it — a race, on someone else's schedule, that a test cannot wait for.

A move changes the conditions. Within one volume it finishes in a single rename and the copying code never runs; across volumes it does run, but CI's temporary directories all sit on one filesystem, so that path is never taken there. What CI does exercise is the `copy_path_no_replace` side — `the_fallback_move_claims_the_destination_before_writing_to_it` among others — and not `move_path_no_replace` dropping into its cross-device fallback. **A test that does not run where it was written is not a test.**

In place of the central case, the test pins **the property that determines it** — that a claim is determined by where it failed, never by the kind of error.

A Unix-domain socket is placed in the source. A socket cannot be `open`ed as a file, so the copy always fails — and it stops **at a known point after the destination was created**, the same side of the claim a nested collision falls on. The failure is deterministic and runs on both platforms.

The branch fixed in the second half is subject to the same constraint. Reaching `WholeDestination` needs a `rename` that reports cross-device **and** a copy that completes **and** a `remove_dir_all` that gives up partway. These three conditions cannot be staged together inside a temporary directory.

The range that remained uncovered was recorded in the PR and in the code comments. **"There is no test" and "not knowing there is no test" are different things.** The first is a decision; the second is an accident.

## The basis for the decisions

The design judgement in one line:

> When the costs are asymmetric, the handling should be too.

An incomplete state can be corrected later; a deletion cannot. Where the judgement is uncertain, the side that does not touch it is chosen.

Applied without limit, however, this prevents the rollback from working, which was **the original defect itself**. Defaulting to "do not touch" is not sufficient on its own.

The answer was therefore not to tune the threshold between touching and not touching, but to **reduce the region that cannot be decided**. Carry the information the decision needs back before it is lost. Stop inferring from the kind of error and make the operation say it.

Three further points concern how the code is written.

- **Name a predicate after the condition that permits the action.** Not "did we take it" but "may we delete it".
- **Write conditions as requirements.** Not a shape that rejects danger, but one that proves safety.
- **When reusing a classification, check every question it answers.** Re-ask only the question currently in your head and another face of the same value walks straight through.

These three were **the direct cause** of three of the review findings. How the names, the conditions and the classification were written is what determined whether an oversight was possible. Before the design could be judged sound or unsound, **the writing had created the room for the error**.

A final summary of the argument. **Code that infers a situation from errno is usually inferring something that cannot be inferred.** The value is a single integer, and most of the required information is not contained in it.
